# DeepSeek Harness 前端交接

把“技术与教学内容正确”和“页面实现有效”接起来，不把任务简化成发送一句需求后等待。项目分工来自用户明确要求；模型选择来自用户要求，不是性能排名结论。

## 角色与执行范围

- **Codex 主导源码分析**：阅读固定源码、检索资料、整理机制与实例，交代用户目标、技术事实和改动边界；完成后核对事实、功能与范围，并向用户呈现结果。
- **本机 DeepSeek Harness 主导前端工作**：自主分析现有表达、提出修改意见、选择视觉方案，负责 HTML/CSS/JS、SVG/动画、页面布局与导航、相关生成器和前端测试，以及返修。Codex 不自行接管，也不以自己的子代理代替。
- **交接说明要做什么，方案由 Harness 决定。** 不预先指定布局、图形结构、动效路径或逐项改写其设计意见；视觉参考是资料，不是指定答案。除用户明确要求外，不因个人审美或另一种同样可行的表达要求返工。需要用户确认方案时，保留 Harness 的建议与理由，由用户选择。
- **Codex 负责最终效果呈现**：将 Harness 的方案图、交互小样或实际页面效果直接展示给用户，附上可操作的预览入口与 Harness 的建议理由；明确哪些是待确认方案、哪些已经实施。逐项审阅时先展示当前项，再由用户决定。不能只报告进度或列出文件路径；呈现不需要激活 Harness 桌面窗口。
- **如果正在 DeepSeek Harness 内收到任务**：你就是实现者，读取交接包和项目教学规则后直接执行，不再把任务转交给另一份 Harness。只做交接包授权的范围。
- 纯资料、Skill 和项目协作规则可由 Codex 维护。发布需要当次明确授权；前端委派本身不包含推送、部署或修改外部源码。

## 1. 核对实际运行环境

按 [本机接入与配置核验](references/runtime.md) 检查：

1. 使用已安装的官方 DeepSeek Harness；记录应用/CLI 版本、实际工作区和会话。
2. 使用 **DeepSeek-V4.1-Flash-1017 + Max**。后台 CLI 核对组合后的 provider、model、reasoningEffort 及官方版本映射；桌面会话核对实际设置。不要只在提示词中要求模型自称使用该模型。发任务、恢复会话或切换预设后检查实际选择。
3. `deepseek-flash` 是服务端路由名称，不能单凭这个名称证明永久固定到 1017。若标签/官方版本映射已变化，明确说明，不静默切换到 Pro、其他版本或较低推理档位。
4. **本项目默认后台 CLI，不激活桌面窗口、不操控用户正在使用的浏览器。** 已按官方 overlay 验证 headless 可复用现有账号，方法见 runtime 文档；默认裸 headless 仍不会读取 GUI 登录。只有用户明确要求桌面操作才使用 UI；CLI 受阻时说明实际问题，不自动切回桌面打断用户。`dsh --version` 成功不等于模型调用成功。

权限选适合本任务的工作区写入范围，保留原有安全设置。不要为获得更高性能安装来源不明插件、扩大访问范围或复制账号凭据。

## 2. 默认用精简目标交接

使用 [交接模板](assets/handoff-template.md)：**目标与完成结果、必要边界、少量资料入口**。不为普通任务填满长表单，不重述已加载的项目规则，不预先指挥布局、实现步骤或工具次序。没有字数硬指标：目标清楚即可，影响正确性的条件不能省。

用户已授权实施时，让 Harness 自主分析、实现、自测并交付一版可验收结果；不额外增加“先写方案 → Codex 逐条改方案 → 再实现”的往返。用户明确要求先确认方案时仍只交付方案。这里的“一次交接”允许 Harness 内部多次工具调用和自我修正，不等于一次 API 请求、保证一次成功或无限运行。

Codex 将复杂技术事实放进按需读取的资料文件：固定源码锚点、必要算例、条件与边界，区分事实、简化和推断。只发送本任务相关的入口，不把详细手册藏在附件里又要求全文读完。给出原有脏工作区和允许修改范围；验收约束描述读者应看懂什么、行为应满足什么，不代替 Harness 做视觉设计。

学习页面按需使用项目 `skills/sglang-interactive-learning/SKILL.md` 及相关参考。已读且未变化的规则复用结论；确需新增 Skill 时核实 Harness 可发现、相关内容未被截断。设计/GSAP/浏览器 Skill 只加载任务需要的部分。

## 3. 按任务组织会话与工具

默认使用 **Standard（标准模式）** 做本项目页面实现；这属于当前工作流选择。PTC 用于确有大量独立查询、过滤或批处理、且该安装实际支持的任务；先看效果，再决定是否沿用。不把社区“更快、更省 token”的体验当成所有任务的保证，也不因此降低用户指定的 Max。

**按可验收的任务阶段组织会话，不按项目无限续聊。** 审核方案、批准后的实施、新增需求分别开启新会话；当前受管工具也用新会话和短检查点接续返修。跨会话保留已批准决策、文件状态、未解决问题与验证证据，不复制完整聊天、不 fork 整段历史。整站工作先解决共享依赖，再按可独立验收的课程或功能拆分；一个文件同一时间只有一个写入者。

旧会话诊断使用 [上下文与调用预算](references/context-budget.md) 的只读检查；不要因为模型支持百万上下文或缓存命中就继续追加。达到轮换条件时由 Codex 根据已落盘结果整理交接，开启受管新会话继续已授权任务，无需再次向用户申请。运行中预算由工具检查，达到检查点先让任务安全收尾，不强杀写入中的进程。

**新实施批次使用 [有预算的后台任务工具](references/guarded-jobs.md) 启动**，由 Harness 内部钩子执行预警、检查点交接和调用上限，不只依赖提示词。等待交给一个本地 watcher，工具超时后等待同一执行会话，不反复 `sleep → 读日志`。未加载钩子的旧进程只能先接入事件等待，完成迁移后才受预算工具管理。

阶段拆分用于隔离已完成工作和新目标，不把一个可独立交付的小任务机械拆成多轮。首次交接后给 Harness 完整执行空间；只有事实错误、权限边界、实际阻断或用户改变目标需要及时介入。

先确认当前 workspace 就是交接包对应的代码；现有脏工作区不要 reset/stash/clean。需要隔离时保留正在审阅的未提交内容，不能只从远程 main 开始而漏掉本地最新页面。

交接前保存当前 status 和受影响文件的内容基线或摘要，验收比较本次交接前后，而不把相对旧 HEAD 的全部差异算作 Harness 新修改。临时目录先用 `git check-ignore` 确认；没有合适的忽略目录时用系统临时目录并给出路径，不假定 `output/` 自动被忽略。

通过当前可用且经过核验的界面/CLI/API 发送任务。UI 操作读取新状态后定位，不固定旧元素编号；不要使用未公开内部端点或提取浏览器凭据来代替登录。提交后确认消息进入正确会话并开始执行。

## 4. 等待、检查与返修

### 浏览器检查的生命周期

Harness 和 Codex 各自负责自己启动的自动化浏览器。每个检查批次开始前记录会话名（直接脚本则用唯一批次标识）、控制进程与浏览器 PID、独立 profile；每批使用完立即关闭，不等整个开发任务结束。启动和 context/page 创建也须纳入 `try/finally` 或等效清理保护；异常、超时、取消及 `SIGINT`/`SIGTERM` 都须执行清理，外层强制终止时由启动方兜底。

优先关闭自己创建的 browser/context 或按会话名关闭 Playwright CLI；复查控制进程、浏览器主进程和辅助进程。残留经 PID、命令行和 profile 核实归属后先 `SIGTERM`，仍存活才 `SIGKILL`；确认退出后删除不再需要的临时 profile。禁止无差别 `killall` / `pkill`，不得影响用户原有浏览器或其他任务。用户手动停止的检查不得立即自动重试。

交付记录必须列出清理结果与剩余目标进程数；关闭调用成功或仅关标签页不算验证。只有用户明确要求保留浏览器时才保留并说明；用于用户审阅的 HTTP 预览服务单独管理。调度方验收时再次核对，不只采信 Harness 的完成文字。

记录会话标识或唯一标题、工作目录、模型/档位、任务范围。观察进度与完成状态；暂停、等待输入、工具失败和正文里写“完成”不能直接当作成功。避免在同一会话仍运行时重复提交整份任务。

Harness 完成后，Codex 必须独立：

1. 对比交接前后的文件变化，确认无关内容、源码基线和课程证据未被覆盖。
2. 执行与改动对应的构建、模型/交互测试和生成一致性检查。
3. 实际查看页面，核对关键状态和数值，操作暂停/恢复/回看、条件切换和重置；记录可复现的错误及其依据。学习图的布局／遮挡问题按项目教学 Skill 的 [布局与过程可读性](../sglang-interactive-learning/references/visual-readability.md) 分别验收语义、过程和理解效果，补查实际视口高度及事件边界。视觉方案和教学表达的取舍由 Harness 说明并向用户呈现。
4. 核验本地链接、相关移动端、主题和键盘行为；保留用户审阅所需的预览服务。

源码事实、功能、明确需求或改动范围有误时，先合并本批已知问题，再提交“复现操作 → 实际表现 → 对应依据/预期结果”的短反馈；由 Harness 决定修复方法。是否恢复原会话由阶段与预算检查决定，不能无条件续聊。不要为进度询问发送模型消息，也不要在对方仍实现时逐条插入尚未汇总的返修。对前端意见有不同看法时先区分事实错误与方案取舍，不把主观判断升级为必须返修。

遮挡返修附场景／参数、播放位置、视口宽高、主题和缩放状态，以及关键截图或可见缺陷说明；明确需要恢复的身份、数值或阅读关系，不预先指定坐标与动效。几何告警先复核可见内容，再集中交接；同类问题跨多课出现时检查共享布局及各渲染类型，不只修用户圈出的那一帧。验收沿用对应版本的证据，避免重复整批截图和只追求告警归零。

返修优先运行受影响的检查；同一版本已有可复用结果时保留证据，只在改动或未解决疑点需要时重跑。共享组件改变后仍须做相关回归，Codex 仍须独立核验最终效果。完整日志与截图集留在文件中，只向模型提供失败摘要、代表截图和读取入口，避免把所有中间帧反复加入上下文。

测试通过不等于教学表达通过。只有内容准确、关键语义可见、操作可用，才呈现本地链接及修改说明。若 Harness 被登录、模型可用性或服务问题阻断，说明实际阻断并保留交接包，不冒充已委派或自行换模型完成。

## 5. 优化效果的依据

以通过验收的结果和返工量为首要标准，再关注耗时、工具回合与可取得的用量。按需记录实际观测，不把一次样例的速度或成本泛化。优先减少重复搜索、过长日志、无关工具和会话污染，不用减少必要验证来换取表面速度。

后续真实任务记录首版验收情况、外部返修次数、总模型调用及输入/输出；不只比较首条提示词长度。不为证明“短提示更好”额外启动付费 A/B 任务，未测量前不宣称已提升质量或节省比例。

查版本或调整策略时阅读 [来源与取舍](references/research.md)。它区分官方机制、社区经验和本项目选择；不需要每次前端任务重复读取全部研究。
