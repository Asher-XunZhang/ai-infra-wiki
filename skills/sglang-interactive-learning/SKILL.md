# SGLang 交互教学

让读者通过改变条件，看到系统状态和数据如何变化，并解释变化的原因。服务于浏览器中的学习过程，保留可长期阅读的正文和可回查的源码依据。

首要标准是初学者一眼能认出动画在解释什么、发生了什么关键变化。先确定这个概念不可丢失的动作、关系与结果，再围绕它们安排画面和节奏；背景、重复过程及实现细节可以弱化、概括或按需展开。完整指核心语义完整，不是所有细节同等突出。简化后仍须能解释该概念最重要的特征，以及它与相邻概念的区别。

## 1. 确定本次改造边界

先读当前仓库的 `AGENTS.md`、相关课程正文和页面实现，检查工作区状态。用户当前指令优先；保留无关改动。已经授权的安装、修复、设计与实现持续推进，不另设确认关卡。

在 ai-infra-wiki 中，先按 [仓库工作流](references/repository-workflow.md) 核对课程、构建入口和验证方式。不要把 GitHub Pages 的静态托管误称为没有动态交互：HTML/CSS/JS 可以在浏览器中运行完整的教学模拟。

整站复核或把成功案例推广到其他课时，按 [逐章复核与迁移规则](references/lesson-review.md) 盘点每个子机制，记录保留、补过程、重画或整合的判断和验收依据。不要把所有页面强行改成成功案例的布局。

按任务选择粒度：

- 整站改造：盘点学习入口、先修关系、已有交互和源码基线，确定共享视觉语言与导航，再迁移各课；先验证一个代表性机制，继续完成用户授权的全站范围。
- 单课改造：保留课程定位及前后衔接，聚焦读者最难理解的因果关系。
- 交互修复：追踪模型状态到图形表现，修复实际行为并验证受影响路径。
- 仅评审或仅规划：交付具体问题、场景与验收条件，不擅自改代码。

## 2. 先设计学习过程，再设计画面

为每课明确一个主问题和可观察的学习结果，例如“修改 KV 容量后，解释为什么排在前面的请求仍未被接纳”。确认必要先修，术语第一次出现时用普通语言解释。

先解释为什么需要、解决什么问题，再讲机制、取舍和必要背景。短定义、函数职责和动画里的操作顺序不能代替设计动机：让读者知道没有这一步会遇到什么具体困难，再用小例子连接输入、操作和结果，说明收益依赖什么、增加什么成本。可参考优秀教程的讲解方式，关键事实回查原论文、官方文档或固定源码；历史只选帮助理解的代表性节点，不编造唯一发明者、必然演进顺序或作者未说明的设计意图。

补充概念与设计动机时，必须主动查阅相关官方文档、项目作者的技术文章或原论文，不能仅根据源码推演来写“为什么”。优秀教程用于借鉴讲解，技术结论回到第一手资料；就近区分“概念与设计说明”和“本课实现核对”，记录来源时间或版本。当前文档、历史作者文章与课程固定提交可能不同，不把新版本参数、性能结果或其他引擎实现混入本课。资料未明确的动机应标为基于约束的解释，不写成作者声明。

实现章重点解释引擎为什么需要某种对象、分层、队列、资源管理与完成条件，通用数学原理链接基础章。区分“源码实际执行了什么”和“根据约束可以怎样理解其作用”；保留已有充分解释，补齐缺口，不为每课重复增加一整套模板。逐章检查方法见 [概念深度与实现动机](references/lesson-review.md#概念深度与实现动机)。

术语与图例按以下标准执行：

- 使用准确的专业术语，首次出现时同时给出必要的英文名称或全称、中文名称和简短解释。用普通语言说明术语的作用，不用含糊的方位词代替正式对象名称；例如使用“PP Stage 0 / Stage 1（流水线阶段）”，并说明各自负责的模型层。
- 图中缩写、字母和编号必须就近定义：说明代表什么对象、数字表示身份还是位置，以及所属范围。例如 MB1 / MB2 表示两个 microbatch（微批次），R1 / R2 表示请求；stage、进程组 rank、GPU 和槽位分别解释。图例应在看图时可见，不能仅藏在源码说明或某一播放步骤中。
- 同一概念在正文、主动画、参数实验和自测中保持一致。不同课程必须沿用不同编号时，在入口明确对应关系；教学简化中的一一对应不写成通用定义。
- 学习资料面向没有参与对话的读者，使用独立、正面的定义。不要把用户或助手交流中的口误、猜测、纠正回复和修改过程写入正文或图例；纠正术语时直接给出准确名称与含义。只有与学习目标相关、具有独立教学价值的概念区别才保留，不因一次对话误称而增加反驳句。

基础章的主图聚焦概念本身：只保留定义该概念所必需的对象、动作、结果和约束，直接呈现数据或状态怎样变化。不要把辅助排版、特定实现算法或部署细节包装成概念必经的中间阶段；例如通信语义直接展示复制、分发、收集、归约或等待，不额外经过独立交接区。必要的参与者、载荷与边界用短标注交代，相关实现细节链接到对应章节。解释动机与背景可以保留，但不能让概念之外的行为混入主动画。具体取舍与验收见 [基础章的概念边界](references/lesson-review.md#基础章的概念边界)。

先排查知识跳步：读者是否知道输入是什么、为什么需要这一步、执行了什么操作、结果怎样用于下一步？首次出现的关键转换应能在图里追踪；例如 tokenize 不能只展示最终 ID，Attention 不能只给最终权重。基础知识在基础章建立，实现章通过先修入口衔接，再展开实现特有的对象、约束和源码，不重复整套基础演示。

用一条小请求或少量资源走完整条链路：提出问题 → 展示最小场景 → 暴露约束 → 引入机制 → 改变一个条件 → 对比结果 → 解释原因与边界。不是每课都需要七个独立板块。

先让读者预测，再操作验证；错误预测应得到与当前图形对应的解释。给出下一步阅读或实验入口。正文、图形、按钮和自测围绕同一学习目标，避免把页面做成字段展示面板。

把机制导航与实验条件分层：先选择“学哪种策略/机制”，再呈现该机制下的场景与参数。存在两个语义层级时，不把“策略名 + 场景 + 条件”堆进一个长下拉框。少量并列机制适合可见的按钮组或标签页；下级控件只列当前机制适用的选项，用简短标签和独立说明。切换上级时同步重置合法场景、说明与动画，保留键盘可用性和可恢复链接。不要为只有一个条件的简单示例强行增加层级。

## 3. 把机制变成可交互模型

先确定需要解释的关系，再按 [机制场景与验收样例](references/mechanism-patterns.md) 选择图形：查表与数值贡献、空间地址、时间依赖、对象引用分别需要不同表达。共享配色和播放控件，不等于共享三列卡片模板。**先按机制选择表达，再设计动画；不得为了复用布局，把不同机制套成同一种卡片搬运图。** 先明确完整对象是什么、如何分工、局部发生什么变化、结果如何使用；需要汇总的机制还要画出汇总规则。按知识点决定必要步骤，不把这条思路变成所有图共用的固定流程。动起来只是最低条件，图形必须让读者看见这一步为何改变下一步。

设计或重做概念动画前，查找并实际观察相关成熟教程的图示或动画，记录来源及借鉴的表达方法。把复合教学图拆成可独立理解、独立播放的单概念演示，再按需连接为综合实例；不把参考图的整条计算流程塞进每个概念。具体拆解、来源配色与节奏设计按 [从成熟教学图提炼独立动画](references/mechanism-patterns.md#从成熟教学图提炼独立动画) 执行。

为关键过渡明确“对象与位置 → 操作及触发条件 → 可见变化 → 完成后的证据”。保留必要的环境与上一轮结果，避免通过不断更换框名或清空场景让读者失去参照。详细的取舍和反例见参考文件的“从知识点设计画面”部分。

图形本身要承担解释因果的工作：读者能从已知条件看出结果怎样产生、状态为什么改变，以及还有什么条件未满足。只有结果、数量变化或对象移动，不足以说明机制。比较方案时保持共同参照，只改变要讨论的因素；有条件的结论应让条件及其影响可见。按 [从结果反推必需的解释](references/mechanism-patterns.md#从结果反推必需的解释) 选择需要补齐的因果环节，不把所有概念套成同一流程。

- 使用明确的状态与事件表达队列、资源、依赖和所有权。按已有架构维护可复现的教学模型，图形和说明都从同一状态生成；动画只表达状态过渡。
- 参数必须改变可解释的结果。给出合法范围、单位、默认值和重置行为；不允许读者随意连线后把非法执行路径称为有效引擎行为。
- 步进、播放、暂停、重置及回看行为要一致。改参数时明确重算或重置，不能继续使用旧场景的队列或计时。
- 同一请求、token 或缓存块跨步骤保持可追踪的身份。用稳定标识与来源颜色对应原件、切片和副本；状态另用边框、标签等表达。计算生成的新值明确显示输入贡献，不能仅靠同色暗示它仍是原数据；需要复制或共享时明确画出副本或引用关系。
- 机制动画必须展示状态之间的连续变化：对象怎样移动、增长、分拆、合并或退出，以及发生变化的条件。只切换文字卡片、数字、标题高亮，或在不变的箭头上循环移动光点，不能算完成机制动画。
- 并发与先后关系由机制决定：同一阶段内没有依赖的独立动作并发播放，不能为了避免遮挡或逐个解说而改为串行，也不能为安置动画添加概念外的队列、路由区或交接阶段。优先简化对象、调整空间布局与路径；有真实依赖的等待继续保留。语义演示中的并发不宣称物理链路必然同时起止。
- 按概念重点安排基础节奏：首次切分、关键计算、合并规则与完成条件留出观察时间，重复且已解释的动作可以加快；不让所有动画或每一步套用同一时长。保留速度滑块、暂停和回看，滑块整体缩放当前时间线而不改变事件依赖或重置进度。具体节奏由制作者根据可读性调整，不要求读者先自行减速才能看懂。
- 暂停在过渡中途时，读者仍应能认出对象、来源、目标与当前动作。播放、单步和回看使用同一逻辑轨迹；减少动态效果模式可直接呈现等价状态与变化说明，不强制播放运动。
- 时间轴必须说明刻度含义。教学步数、假设耗时、真实测量不能混用；没有测量依据的数字标注为教学示例，不输出虚构吞吐或加速收益。
- 区分请求、输出 token、KV、元数据、控制消息和传输完成条件；能访问资源不等于拥有其调度或生命周期。
- 过渡中不提前宣布完成：在途、预留、写入和可用要分别呈现；数值插值仅表示教学呈现进度时须明确，不能伪装成合法中间计算结果、完整请求数量或实测工作量。
- 最终画面保留原因和结果。请求被拒绝后，应能看见具体约束与比较；不能只剩空 batch、归零预算或“等待下一次检查”，迫使初学者回翻才能解释结论。

### 交接双方、载荷与执行边界

图中出现交接、传输或对象移动时，必须在画布内或紧邻箭头的可见图例中说明以下内容，不能仅放在折叠说明或源码链接里：

- **谁向谁交接**：标明发送方与接收方，以及本例相关的组件、进程、设备和主机归属。双向交换、广播或 collective 按实际参与关系画，避免用单向箭头或虚构中央节点替代。
- **传递什么**：明确是 activation（激活张量）、token ID、KV 载荷、地址／元数据还是控制消息；同一请求的不同载荷分开标注。卡片身份与实际传输内容应能对应。
- **跨越什么边界**：区分同进程调用、本地引用／地址映射、设备内访存、跨进程 IPC、GPU 间通信和跨主机通信。这些维度可同时成立；进程、rank、stage、GPU 和主机不能相互代替。
- **去哪里深入**：在对应交接旁提供通往专门章节的可用链接。当前课简要交代边界与载荷，具体通信算法、协议和实现细节按学习主线留给相关章节。

部署关系必须有依据，或明确标为本例教学设定。两个 stage 不自动意味着跨机，两个逻辑模块也不自动意味着跨进程；未知的物理放置应明确未指定。区分控制面和数据面，不凭箭头推断固定协议、直连路径或中转方式。若提供同机／跨机等拓扑切换，双方归属与边界标注必须同步；未建模通信耗时时，不让切换产生虚构时延或性能收益。

检查范围包括主动画、保留的参数实验和相关静态图；按机制选用箭头标签、分组边框或小型拓扑图，不要求所有页面增加同一种说明面板。无需发生物理传输的图，应准确标明本地操作或逻辑关系。

## 4. 让视觉服务理解

长内容先组织阅读层级：先给读者可扫读的机制总览，再按学习问题或策略分组。收益、代价、适用条件使用同一组比较维度；操作示例和完整推导按需展开。相关内容较多时使用就近导航、对照表或原生展开区，不把连续大段文字平铺，也不机械地将每段包装成卡片。关键定义与约束应紧邻结论保持可见，不能把限制藏在折叠层、留下只有收益的摘要。保留内容、证据与可链接锚点；切换与折叠应支持键盘、窄屏和直接访问。

复用现有组件与技术栈，优先采用 HTML、CSS、SVG 和现有模型；复杂规模或交互确有需要时才引入额外库。Mermaid 适合可维护的静态机制图，不假设它或 Dagre 自带完整可拖拽编辑器。

确定场景的视觉焦点、空间分区、字号、间距、颜色语义与运动方向。一次突出当前需要理解的因果关系，其余细节渐进展开；短说明贴近变化位置。颜色之外同时提供文本、形状或图标区分状态。

重构已有课程时，先按 [旧图取舍清单](references/mechanism-patterns.md#旧图取舍清单) 判断替换、合并、补过程或保留。新旧图解释同一件事且旧图没有独立信息时，应收敛为一个入口；不能默认把所有旧播放器折叠堆在新图后面。保留有独立价值的参数分支、精确数值、原课程内容和源码证据，合并前检查它们是否被新图覆盖。

参考视频时，将剪辑节奏转成用户可控的步进、暂停、回看和条件切换。必须实际查看参考作品或画面后才能描述其配色、构图和动画；不能根据作者昵称或宣传文案推断画风。

按需要配合已安装的 Skills，先阅读其当前指令：

## 5. 给每条机制保留证据

每课使用自己的公开上游 URL、固定 commit、读取时间与仓内源码路径。先核对事实再写解释，不把某课基线套到整个 SGLang，也不把历史私有分支包装成当前上游。

把关键行为映射到文件、函数和固定提交链接。区分源码事实、教学简化、整理者推断和运行观测；阅读源码不代表执行过 GPU/RDMA 或压测。简化模型要说明省略了哪些路径，以及何时结论不再适用。

面向读者的页面与文档不写作者机器绝对路径。外部源码检出目录由参数或环境变量传入，不修改被阅读的源码仓库。

## 6. 按学习行为验收并交付

先验证受影响模型的资源守恒、依赖、释放时机与边界，再验证图形是否忠实呈现。复用已有测试；只为新增机制或实际缺陷补充有区分力的断言，不为低影响文案写复述实现的测试。

在真实浏览器中覆盖正常路径、一个关键约束/异常分支、参数切换和重置。检查当前课相关的移动端、键盘、深浅主题、减少动态效果和无 JS 阅读。共享布局或导航改动扩大到所有受影响入口；单课变更不机械重跑无关全站测试。

验收先检查表达选择：图形是否揭示这个机制独有的结构与因果？读者能否从原始对象连续追踪到分工、局部变化与最终结果，而不是只认出几个移动的术语标签？若必须依赖旁白补出关键计算或对应关系，应重选图形或补齐中间过程。

验收以读者能否解释和预测为准：这一步处理什么、数据如何改变、为什么现在还不能继续、改变一个条件后结果为何不同。页面数、帧数、运动距离和通过测试数量不能替代这些判断。不读长文也应看出：谁在做什么、数据在哪里、为什么等待、改变条件后发生了什么。对关键步骤实际截图并观察，检查文字遮挡、箭头方向和运动含义。

交付机制动画前，按 [动画过渡验收](references/mechanism-patterns.md#动画过渡验收) 检查同一对象的起点、中间态和终点，实际操作中途暂停、恢复与回看。仅验证步骤编号变化、终态截图或存在动画标签，不足以证明动画合格。

整站复核须逐章记录“保留 / 补充 / 重画 / 整合”的理由，保留也要说明独立教学用途；按 [逐章复核规则](references/lesson-review.md) 核对输入完整性、控制变量、离散数量与旧入口迁移。

阅读层级验收：能否先识别机制、再选择该机制下的场景？无需读完长段落，能否找到当前问题、收益与代价？折叠后是否仍保留关键条件，链接是否能直达对应解释？

交付前核对标题、正文、图例、动画各状态、条件选项与自测：术语准确，首次出现有解释，缩写和编号有明确含义，且不依赖读者知道制作过程中的对话。

交接验收：仅看画面能否辨认双方、载荷和进程／设备／主机边界？本地引用是否与真实传输区分？切换条件、暂停与回看时标注是否仍正确，相关章节链接是否可达？

交付说明修改了什么学习行为、哪些验证已通过、哪些源码或运行边界仍未验证。确认变更范围、引用与生成一致性，清理本次无用临时文件；发布按用户授权和当前项目规则执行。
