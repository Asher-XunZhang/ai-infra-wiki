# Pages 交互图补充与复核规则

新增、修改或审查 Pages 交互图时，先明确它要回答的学习问题，再选择表达方式。规则适用于主动画、选读实验和局部机制图；复核范围是本次任务涉及的图，不因一项规则更新就自动重画全站。

## 每处评估：需要呈现多少细节

**每处图都要判断是否适合“总览／模块过程／源码细节”的渐进呈现。** 先让读者认出本课的问题、关键变化和结果，再按需展开实现。三层是可选的阅读方式，不是必须凑齐的三个播放器；单一问题用两层、局部展开或一张完整图已经清楚时，保留简单方案。

| 层级 | 回答的问题 | 默认呈现与展开边界 |
| --- | --- | --- |
| 总览 | 谁在做什么，数据发生什么变化，为什么能继续或仍在等待？ | 保留最小完整因果链、输入输出、对象身份、必要的进程／设备边界和放行条件。概括内部步骤，避免一开始列出全部字段、公式、源码函数与参数 |
| 模块过程 | 哪个真实模块处理了它，交接了什么，期间谁可并行推进？ | 展开执行主体、关键中间状态、载荷和资源变化；按问题加入同一时钟下的执行轨道。不是把总览的方框放大或只换成函数名 |
| 源码细节 | 哪些字段、分支与完成条件落实了这个行为？ | 对应当前事件展示必要字段、队列／引用、公式、函数及固定提交锚点；保留源码事实与教学假设的边界，不铺开与当前问题无关的整段代码 |

选择依据与复用要求：

- **适合完整三层：** 一张图同时涉及多个执行主体、状态提交或资源归属，且源码字段已经挤占主线；各层必须有独立学习价值。
- **适合两层／局部展开：** 主线短且聚焦，复杂度集中在一张输入表、一个树节点、一个预算条件或一段公式。无需增加第三套布局。
- **保留现状：** 已有清楚的渐进入口，或页面本身是源码阅读／依赖分析工具。复用现有精简视图、详情、聚焦和深链接；不能为了统一按钮复制内容或删除独有场景。
- **分开四种操作：** 机制选择决定“学什么”；场景参数改变“在什么条件下”；追一批／看一轮决定“看谁或哪一段”；细节层级决定“同一件事展开多少”。焦点切换不自动算作已有三层，控件也不必各占一整行；默认只留当前问题必需的选择。
- **守住课程分工：** 基础章解释通用概念，实现章解释固定版本怎样组织它。架构对照两侧使用可比的抽象层级，但不强求相同模块边界；保留各自版本。源码导读可直接作为深读入口，不重复制作基础概念动画。

### 切换层级时保持什么

三层使用同一事件模型和一只时钟。仅切换细节时，保持场景、参数、请求／batch 身份、教学时刻、播放或暂停状态、速度及当前指标；支持链接恢复该视图和进度。改变机制或实验条件按该图的重置规则处理，不能与详情展开混为一谈。

总览节点对应明确的子模块／事件集合，展开后仍能定位原来的对象和时刻；收起后能回到所属阶段。内部可折叠，关键依赖、等待、可用条件、取消和释放边界不能消失。并行活动不能因合并轨道变成串行，也不能因合并参与方暗示共同屏障。

如果一条总览区间覆盖了多段活动及其间的等待，说明它表示阶段范围，不能涂成“GPU 一直忙”或据其长度计算利用率。信息折叠不能改变统计端点、样本集合、指标值或源码版本。

参照[性能观测课](sglang/performance-engineering/index.html)：先看 P/D 请求与采样边界，再展开模块轨道，最后查看字段和公式。可复用其状态保持方式，不要求其他课照搬轨道数量或指标布局。第二、三章的逐节取舍见[可视化细节层级复核](VISUALIZATION_LEVELS_REVIEW.md)。

## 每处评估：是否需要同一时钟下的执行轨道

**每一处交互图都应分析是否需要补充类似泳道图／甘特图的“同一时钟下的执行轨道”；有必要时加入。** 判断的是它能否帮助读者看清谁正在执行、谁在等待、等待什么、其他参与者此时能否继续，而不是图中是否恰好存在多个模块。

| 学习问题 | 建议 |
| --- | --- |
| 跨进程、rank、CPU/GPU 或工作线程的先后依赖；流水线；异步提交与完成；并行计算／传输 | 优先加入，共用横向时间轴，按实际执行主体分轨 |
| 准入、资源释放或完成通知依赖多个条件；需要解释等待期间其他工作能否继续 | 加入必要参与者和条件轨道，直接标出等待原因与解除条件 |
| 数值变换、查表、地址映射、对象引用或单步状态变化；时序关系已由主图清楚表达 | 可不加入；保留更适合该机制的图形，说明无需增加轨道的理由 |

对本次涉及的每处图，在已有审查记录或交付说明中简记“加入／复用／不加入、理由、需要解释的依赖与并行关系”。已有合适时间轴时直接复用，不再叠加一套重复播放器；历史图的结论应在实际复核后更新。

## 加入后的表达要求

- **一个时钟、一套控制。** 主图、数据／引用状态、轨道活动和时间游标共用播放、暂停、步进、速度及任意拖动；回拖能够恢复一致状态。讲解步骤与执行活动区间分别建模，不能把串行步骤简单铺成多行后宣称并行。
- **先有依赖，再排时间。** 用固定源码或有来源的机制说明确认触发、等待和完成条件。串行依赖不能重叠；独立活动不为排版方便强行串行。源码允许的合法交错可用教学示例呈现，并明确所选配置与假设，不把“可能并行”写成“必然同时”。
- **分清执行主体与载荷。** 轨道按当前问题需要区分 Scheduler／工作线程、CPU／GPU、通信活动等；硬件放置有依据或明确为示例。箭头标明控制消息、激活、KV、结果或本地引用，不能把本地引用变化画成跨设备数据搬运。
- **提交、在途、完成分别可见。** 异步调用返回不等于 GPU／传输完成；通知发送、通知到达、载荷可用及消费者准入也不能合为同一时刻。等待条写明对象或条件；空闲与阻塞等待采用不同样式及文字，不能只靠颜色区别。
- **时长与证据对应。** 教学时间明确标注“不代表实际耗时”；不从条块长度推导性能收益。实测轨道须给出采集来源、时间单位和配置。建组、加载等一次性准备不能画成每轮重复工作。
- **布局围绕问题收敛。** 默认只显示解释当前机制所需的轨道，详情按需展开。主体、数据与游标在播放中保持可追踪；不能靠缩小字号或改变并发关系解决拥挤。

## 数据传递：完整箭头与活动区间内的持续脉冲

**传递关系使用完整、方向明确的箭头；在实际传递活动区间内，沿该路径持续播放短划线／亮段脉冲。** 采用第二章连线上连续流动的视觉方式，不用缓慢长出箭头表达传输进度。路径从一开始就能辨认来源和目标，脉冲表示这条路径此时有活动，不表示一份载荷反复发送。

### 先定义连线语义

| 连线 | 静态表达 | 何时有脉冲 |
| --- | --- | --- |
| 数据传递 | 带方向的路径，标出载荷，如 input IDs、激活、KV、token 结果；注明必要的源／目标设备 | 对应复制、发送／接收或结果提交事件正在发生时；若事件实际包含排队等待，不能让整个等待区间都呈现为正在搬运字节 |
| 控制消息 | 与数据线可区分的线型或标记，并写明通知／ACK／许可等内容 | 消息发送与传播期间；瞬时通知可短暂强调，后续等待由状态或轨道表达，不持续冒充消息在途 |
| 本地引用 | 较弱的静态线，就近标注“引用”，连接容器与被引用对象 | 不因引用持续存在而播放传输脉冲；实际读取或更新值时，另标出该操作及其来源、目标 |
| 依赖／等待 | 连接具体前置事件与消费者，标明等什么；与载荷路径区分 | 只表达依赖状态，不用传输脉冲替代等待；条件满足与消费者启动分别由事件模型决定 |

同页语义统一，短图例就近可见；用标签、线型或端点补充颜色，不只靠颜色区分。默认一条短划线箭头同时表达方向和活动；确需背景底线时，底线与活动亮段共用同一路径，不能错位形成无解释的双线。必要的双向消息分别标明方向与内容。跨层切换可隐藏内部路径，但仍保留边界上的载荷和交接条件。

### 脉冲怎样随时间变化

- 由教学时钟和事件活动区间计算脉冲相位，例如在活动区间内使用 `phase = (time - event.start) * visualSpeed`。暂停冻结，拖动和回拖确定性恢复，整体速度控制同步影响相位；切换细节层不另起动画。避免独立墙钟或失控的 CSS 无限动画使页面暂停后连线仍在流动。
- 传输开始前和结束后停止脉冲。发送提交、数据在途、完成通知、接收方可用及资源释放分别按源码模型更新；首个亮段经过终点、循环次数或箭头画满，都不能触发“完成”。瞬时事件只强调该次交接，不为可见性凭空延长机制耗时。
- 脉冲间隔、个数和移动速度是视觉编码，默认不代表包数、token 数、字节数、带宽或真实网络延迟。确需表示离散载荷数量时，用带身份的对象或计数明确表达，不能让循环光点承担两种含义。
- 并行传递在各自合法活动区间一起显示；串行依赖保留门槛。多路重叠先调整端口、路径、标签和视觉权重，不能为避免遮挡把真实并发排成逐条播放。
- 起点接到真实发送者或结果持有者，终点接到真实消费者或被更新字段。节点、端口、箭头和脉冲共用几何数据，缩放与滚动后仍贴合。边上说明传的是什么，不能只留下无名圆点、菱形或短条。
- 减少动态效果时以静态路径高亮和“传递中”文字提供等价信息；不强制运动。机制过程仍须展示输入、状态变化与完成后的结果，不能只在静态架构图上加循环脉冲就宣称完成机制动画。

### 已有案例怎样复用

[第二章连线样式](engine-comparison/atlas.css)中的 `ia-wireflow` 可作视觉参照；复用前检查播放器是否真正控制其相位，不能直接把无限 CSS 动画当作统一时间模型。[Req 状态专题](sglang/request-state/state.js)的 `flow()` 已用教学时刻计算短划线相位，并把引用线独立绘制。

该专题还给出一个端点取舍：CPU 正在消费的 Q0 与仍在 `result_queue` 中的 Q1 分开。提交脉冲从 **Q0 的可读结果** 指向 **Req.output_ids**；batch／队列对 Req 的引用用弱线标注“引用”。不能从 Q1 队列画一条模糊连线来代替 Q0 的结果提交。这个案例用于说明“谁持有结果、谁更新什么”，不要求其他图照搬 Q0/Q1 命名。

## 验收

核对一个关键依赖前后和一个实际存在的并行区间：前置条件未满足时消费者不能启动；允许继续的活动不被虚构的全局屏障阻塞。检查等待解除、异步完成和释放条件与源码一致。若机制本身串行，则检查其串行原因，不为验收制造并行。

实际查看默认视口、连续播放中途、暂停及逆向拖动后的画面；确认主图与轨道同步、载荷去向清楚、条块和标签可读，并检查窄屏及减少动态效果设置。模型测试不能代替可视验收。保留源码事实、教学时序假设与未执行运行验证的边界。

涉及细节分层时，在同一场景、同一中间时刻逐层切换，核对对象身份、活动／等待状态、完成条件、指标及进度不变；播放中切换不重启，暂停中切换不自动播放。检查展开后能找到对应事件，收起后关键因果仍然可读，深链接和源码入口可达。默认视口不能只剩控件或要求读者先阅读一屏字段才能看到过程。

涉及脉冲时，至少观察开始前、传递中、完成后与回拖后的画面：完整箭头始终方向明确；活动只发生在对应区间；暂停后相位不再变化；引用／等待没有误表现为传输；并行路径按依赖同时活动。查看一个具体载荷的起点、终点与完成后的状态变化，不能只验收“线在动”。

每处复核简记：学习问题、现有入口、细节方案及理由、轨道方案及理由、连线语义与脉冲区间、必须保留的条件、复用位置、已验证与未覆盖范围。按改动影响选择验证，不把简单静态说明扩成整站动画回归。
