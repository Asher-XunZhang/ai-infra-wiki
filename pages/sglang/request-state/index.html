本课追踪什么实现

沿同一个 Req 核对队列成员、batch 引用、状态字段和资源归属；在同一时钟下观察普通、分块、回撤、取消与异步路径。

需要回顾原理：Batch 调度：动态组批、连续批处理与 Chunked Prefill

从问题理解实现

同一个 Req 可以被多个容器引用，GPU 工作与 CPU 输出提交也有不同完成时刻。必须把状态字段、容器成员与资源归属并排观察，才能判断请求正在推进还是在等待。

“请求在哪里”通常没有单一答案。Req 保存请求字段，列表与 batch 保存它的引用，执行结果可能仍在途，KV 又有独立的保护和回收条件。

五条路径分别改变什么？

正常：选批、结果处理、下一轮合并

普通请求先加入 waiting_queue。PrefillAdder 选中后，Scheduler 从 waiting 过滤已接纳成员，建立 ScheduleBatch 并准备输入。Prefill 的结果处理追加首 token；随后一轮先过滤上一 Extend batch，再将可继续请求合入 running_batch。本例 running 为空，直接指向上一 batch 对象；已有运行成员时则走 merge_batch。

Decode 结果触发停止条件后，资源处理先发生，后续 filter_batch 再移除完成成员。过滤引用与释放 KV 各有职责。

分块：离开 waiting，不代表已经能 Decode

中间块由 chunked_req 保持续算关系。下一轮缓存已算前缀、把它从旧 batch 中排除，再由 add_chunked_req 续算。它不需要每块重新经过 waiting_queue。最后一块选好后，chunked_req 返回 None；最终 Prefill 结果才产生有效首 token。中间块取消由 pending_chunked_abort 路径协调，本课的取消对照不覆盖该支线。

回撤：交还执行资源，保留普通文本进度

容量不足时，retract_decode 选择可回撤请求；release_req 不把私有尾部新插入缓存，解除保护并尝试驱逐，再 reset_for_retract。普通 token 输入保留 output_ids，重新加入 waiting。再次准入会用原输入和已生成文本构造输入并重新匹配前缀；只有未命中部分需要重新计算。

图中选定前缀已被驱逐的场景，R2 保留运行，随后释放容量。它不表示每次回撤都重算全部输入。Beam、input_embeds、PD Decode 主机备份等路径有独立条件，不能套用本例。

取消：等待中直接移除，运行中先提交待结束标记

等待中的普通请求可以直接从 waiting_queue 删除，并回告前端；此分支不需要把 finished_reason 先改成 ABORT。运行集合中的请求则设置 to_finish，保持正常结果处理与资源收尾入口。图中 Normal 路径还执行一轮 Decode，再由 update_finish_state 将待取消原因提交为终态。

不能把这解释为所有后端都精确再计算一个 token，也不能把内部 output_ids 的一次追加当成成功响应已交付。

Overlap：队列空了，消费函数也可能还在等结果

CPU 提交当前批后保存 batch.copy() 与结果引用，再取出旧结果。popleft 在调用 process_batch_result 之前；函数内部仍可能等待 copy_done。浅快照保留当次执行的成员视图，Req 对象继续共享。

主图分开显示 result_queue 与 CPU 当前消费区：Q0 取出后只出现在消费区，Q1 仍留在队列；提交脉冲由消费区的可读结果直接连到 output_ids。同一时钟显示下一批 GPU 计算可以继续。CPU 尚未读到 EOS 时，额外一轮可能已经提交；后续必须排空结果，并跳过已经 finished 或 retracted 的 Req。单一 forward stream 中的相关 GPU forward 按依赖先后执行。

先预测，再拖动时间验证

R1 已不在 waiting，output_ids 仍为空，它是否丢失了？

不一定。分块场景中，batch 与 chunked_req 正在持有同一个 R1。观察输入 KV 增长和最后一块结果，才知道是否仍在推进。

to_finish 已是 ABORT，为什么 finished_reason 还是 None？

这是待提交的取消原因。运行中取消借用正常结果路径完成回应和清理；直接提前设置 finished_reason 可能让请求被过滤而失去响应路径。

finished_reason 已设置，为什么还看得到 batch 引用或 Q2？

逻辑结束、资源收尾、成员过滤和已提交结果排空发生在不同位置。Overlap 中还需消费先前提交的结果，并跳过完成请求的额外输出。

请求行归还，是否表示对应 KV 已经可直接重新分配？

不是。RadixCache 仍可持有这些 KV；解除请求保护后只是满足可驱逐条件。只有实际驱逐或直接归还后，allocator 才能复用相应空间。
