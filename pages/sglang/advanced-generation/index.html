候选与可提交状态为什么要分开

官方投机文档展示候选生成与验证，并说明扩大候选会增加资源成本。XGrammar 作者则从下游程序需要合法结构出发，在每轮采样前屏蔽不合法 token。两类机制都让引擎需要维护额外状态，不能只观察最终输出文字。

具体实现与执行轨道以 279339f113 固定 Git 对象为准；官方文档与作者文章只说明背景，不替代版本约束。 资料读取：2026-11-09。

GPU 已接受，为什么 CPU 输出可能还没有提交？

Overlap 将设备工作和 CPU 结果消费拆开。已计算的候选、有效路径、物理预留和用户输出需要分别记账。

展开机制与具体例子

EAGLE V2 Verify 产生 accept_index / accept_lens，树路径整理 KV、predict 与 hidden；发布新长度后 Draft Extend 刷新后继输入。结果 D2H 可与下一轮 Draft 交叠，CPU 随后结算 Req。

取舍与条件：更多草稿并不自动更快；单链与树、普通 Attention 与递推状态的整理路径不同。教学时钟只表达依赖，不表达性能。

编译规则可以共享，为什么 matcher 必须按请求创建？

ctx 是可复用的编译结果，matcher 则记录某请求已接受的前缀。直接共享进度会让新请求从别人的规则中途开始。

展开机制与具体例子

缓存 miss 返回编译 Future 并进入 grammar_queue；hit 调用 XGrammarGrammar.copy 共享 ctx、新建 matcher。CPU 填请求行 mask、搬到 GPU 后应用，结果回 CPU 才推进该请求。

用一个例子理解

规则为 yes 或 no：R1 已输出 y，它后面只能沿相应合法路径推进；R2 尚未输出，不能继承 R1 的 matcher 进度。

取舍与条件：额外规则处理带来开销，并可能限制可选表达。语法合法只说明符合该规则，不保证字段内容符合事实或业务含义。

树遍历为什么必须 rollback，正式推进为什么还要幂等？

候选的多个兄弟分支必须从共同父状态判断；上一轮结果又可能在本轮 Verify 时尚未被 CPU 消费。

展开机制与具体例子

先运行 grammar barrier，再 DFS 临时 accept / rollback；这些 CPU 工作可与目标 GPU 前向重叠。正式结果用 grammar_advanced 防止重复推进，并缓存 grammar_retained_tokens。

取舍与条件：CPU 规则工作没有及时完成时会延迟后续采样。不能因此把 target forward 也画成必须等待 DFS。

一轮 EAGLE 有哪些不同的“提交”？

EAGLEWorkerV2.forward_batch_generation 在 decode 路径依次组织 Draft、Verify 和 Draft Extend。build_eagle_verify_input 把候选、位置、树遮罩与 retrieve 索引装进 EagleVerifyInput；目标 worker 计算 logits / hidden 并写验证位置的 KV。

eagle_sample 返回 predict、accept_index、accept_lens；本路径的接受长度包含 bonus。单链接受 a、b 后，新增输出是 a、b、z，新增有效目标 KV 对应 r、a、b。树路径可能是节点 0、1、3，此时 _finalize_accept_tree_path 要把 KV、predict 与 hidden 整理到连续前部。topk=1 已连续，不执行这次搬移。

on_publish(new_seq_lens) 发生在 Verify 后、Draft Extend 前；后者刷新下一轮所需的草稿状态。结果异步 D2H 后，CPU 的 _resolve_spec_v2_tokens 才按每请求 stride 读取有效部分、更新 kv_committed_len，输出处理器再追加 output_ids 并检查结束条件。预留长度由分配路径维护，不等于本轮接受长度，也不因拒绝直接归零。

动画把下一轮 Draft 与本轮结果 D2H / CPU 收尾放在同一时钟上；它们可重叠。下一轮 Draft 仍需前轮刷新完成，不能把同一请求的两个完整推理轮次画成互不依赖。

规则上下文、请求 matcher 与词表 mask 分别在哪里？

GrammarManager 按规则类型和文本建立 key。缓存未命中时，BaseGrammarBackend 通过线程池编译，返回 Future，请求留在 grammar_queue；获取有效结果后才具备正常准入条件。无效规则走中止处理。PP / 多 rank 的规则就绪传播不在本课单 rank 图中展开。

命中缓存时 XGrammarGrammar.copy() 复用编译后的 ctx，并构造新 matcher；它不是复制另一个请求已经走过的状态。普通生成由 ModelRunner._preprocess_logits 调用 SamplingBatchInfo.update_regex_vocab_mask，生成每请求 mask、搬到设备并应用，再由 Sampler 选 token；结果处理推进该请求的 matcher。

图里词表只有 y、es、no、!、EOS，用来观察对象边界，不是实际 tokenizer。完整 mask 使用压缩位表示，传到 GPU 的是 mask，编译器和 matcher 仍在 CPU。

树的试走为什么不污染正式规则状态？

固定版本中，GrammarTree.from_device 在 target forward 之前启动树元数据 D2H。forward 提交之后，build_grammar_vocab_mask 先调用 grammar barrier：等待并消费尚未处理的上一轮结果，让真实 matcher 跟上已接受前缀；随后解析树副本并生成 mask。这些 CPU 工作可与本轮 target forward 交叠。

traverse_tree 在访问非 root 节点前检查父节点 mask；合法分支临时 accept，填当前节点的下一 token mask，递归后 rollback。root 已经被上一轮推进，不再 accept。父 mask 禁止的节点被跳过，其未生成行不应伪画为全零；合法验证路径不会进入它。

DFS 返回时 matcher 仍在原真实前缀。目标 logits 和本轮 mask 都到位后才能验证。本轮结果回到 CPU，advance_grammar_fsm 正式推进并缓存 grammar_retained_tokens，grammar_advanced 避免同一结果被推进两次。规则终止时只保留终止前缀；该截断不同于 GPU 候选接受。NGRAM 等 host-draft 路径的同步条件不同，本图不推广到全部投机算法。

混合模型还需要什么额外状态？

普通 Attention 的有效历史由 token 位置及 KV 映射描述；MLA 改变每位置表示，稀疏读取改变本轮访问范围。带 GDN / Mamba 等递推层的模型还须提交接受边界对应的活动状态，不能只修改输出列表。固定 run_eagle_verify 有 commit_mamba_states_after_verify 分支，其内部 scatter / ReplaySSM 路径依模型而异。

本页设备动画固定普通 Attention；模型结构差异保留在配套源码文档。EAGLE、MTP、Ngram 的候选来源、模型输入及组合约束不同，不能从这套图推导所有算法均共享相同时序。
