需要回顾原理：Speculative Decoding：草稿候选怎样验证和接受？

从问题理解实现

投机候选尚未被接受，规则也有各请求自己的进度。执行层必须把“计算过”“允许输出”“正式提交”分开，才能在分歧或约束出现时保持状态一致。

候选与可提交状态为什么要分开

官方投机文档展示候选生成与验证，并说明扩大候选会增加资源成本。XGrammar 作者则从下游程序需要合法结构出发，在每轮采样前屏蔽不合法 token。两类机制都让引擎需要维护额外状态，不能只观察最终输出文字。

为什么验证后还要整理 KV 与模型状态？

候选验证可能为以后被拒绝的位置执行过计算。如果只删掉输出文字而保留错误路径的状态，后续生成仍可能使用不属于正确前缀的历史。

展开机制与具体例子

EAGLE 验证路径根据接受结果组织有效输出与状态。本页用单链贪心例区别 root、接受候选和补出的 token；混合或递推模型还可能需要对应状态恢复。

取舍与条件：整理状态增加工作，且不同模型的回退方式不同。缩短 token 列表不等于所有状态都已恢复，接受率也不能单独证明加速。

为什么有了模型提示词，还需要语法约束状态？

要求输出某种格式，并不等于模型每一步都只会选择合法 token。需要强制满足给定规则时，系统要根据当前已经生成的前缀限制下一步候选。

展开机制与具体例子

XGrammar 路径生成词表 mask，在采样前应用；选择 token 后推进 matcher（规则匹配器）。编译规则上下文可以复用，请求各自的匹配进度不能混用。

取舍与条件：额外规则处理带来开销，并可能限制可选表达。语法合法只说明符合该规则，不保证字段内容符合事实或业务含义。

读图前：术语与编号

Root token（根 token）是前一轮已经生成、用作本轮验证起点的 token，不是整段文本的第一个词。Draft token（草稿候选）尚未提交；accepted prefix（接受前缀）指连续通过验证的候选；bonus token（补出 token）是验证后额外产生的输出，尚未作为下一轮输入计算。

EAGLE、MTP、Ngram 为什么不能直接等同？
候选来源
模型 / 多步预测 / 历史匹配→目标模型验证→有效输出与状态

它们可以共享“提出候选，再验证”的思路，但候选来源、模型训练、输入隐状态、树布局和组合约束不同。投机不是总有第二个神经网络；也不是打开参数就必然更快。接受长度带来的收益，要与草稿、验证和状态整理成本一起测量。

本页只演示 EAGLE 风格的单链贪心语义；随机拒绝采样需使用提议与目标分布，不能按 token 是否相等机械接受。EAGLE 与 MTP ↗ · Ngram 等候选路径 ↗

先预测，再操作

递推状态只有一个槽位，为什么还要保存检查点？

活动状态已被后续输入覆盖。回到更短前缀时，不能只缩短 token 列表；还要恢复对应状态，或按实现重放。选择“混合结构”，观察有效 KV 和活动状态同时回到 t2。

第 3 个候选错了，第 4 个偶然对了，可以保留吗？

本页的链式模型不可以。第 4 个候选建立在错误的第 3 个前缀上；验证必须在第一个分歧处结束这段连续接受路径。

接受 2 个草稿，为什么输出与新增 KV 都是 3 个，却不同？

输出是 a、b、z；新增有效目标 KV 是 r、a、b。r 已在上一轮输出；z 才刚被采样，尚未作为输入产生自己的目标 KV。

同一规则的两个请求，能共用当前 matcher 吗？

不能共享进度。XGrammar copy 复用编译上下文，但建立新的 matcher；否则一个请求已经生成 y，会错误限制另一个请求的首 token。
