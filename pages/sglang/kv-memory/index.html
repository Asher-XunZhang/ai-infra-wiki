本课追踪什么实现

核对请求索引如何映射到物理 KV 页，以及共享保护、缓存保留和驱逐条件。

需要回顾原理：KV Cache 与前缀复用：为什么保存历史 K/V？

从问题理解实现

请求长度不断增长，共享前缀又可能同时被多条请求读取。如果把“请求的第几个位置”直接等同于连续显存，就很难表达非连续分配和共享。

逻辑位置与存储位置为什么分开

PagedAttention 原论文针对 KV 持续增长带来的显存浪费与共享困难，讨论按块管理和非连续存储。RadixAttention 进一步说明跨请求前缀复用。两者帮助理解下面的地址映射与共享保护，但不代表 SGLang 直接使用相同数据结构。

为什么请求行只记录 KV 地址？为什么共享缓存需要保护和驱逐两个动作？

为什么请求行只记录 KV 地址？

逻辑顺序与物理放置分开后，序列仍按位置读取，但实际存储可以来自不同页，也可以引用已有前缀。请求无需拥有连续的一整段物理空间。

展开机制与具体例子

ReqToTokenPool 保存请求到 token 槽位的映射，KV 池保存各层实际数值。本页的请求行、槽号和物理页是不同对象；地址准备完成之后仍要写入本轮数据。

用一个例子理解

R1 的逻辑 p8 可以映射到槽 12；第 ℓ 层读取 K[12] / V[12]。换一层仍用槽 12，但取的是那一层的数值。

取舍与条件：映射增加了一层索引管理，却支持非连续布局。池内归还位置也不等于把预分配 buffer 交还设备系统。

ReqToTokenPool · 本课实现核对 ↗

为什么共享缓存需要保护和驱逐两个动作？

R1 结束时，R2 可能仍在读取同一前缀。即使没有活跃请求，也可能值得把前缀暂留给下一条请求，所以结束请求与归还物理页不能合并成一个判断。

展开机制与具体例子

lock_ref 表达活跃保护，解除保护后节点才可能进入可驱逐集合；驱逐再把位置归还分配器。树索引、请求引用与分配器分别维护相应关系。

取舍与条件：保留缓存能减少后续重算，也占用容量；驱逐腾出空间，却可能增加未来 miss 的计算。不能只凭“请求结束”预测显存立即下降。

读图前：术语与编号

请求行是 ReqToTokenPool 中一个请求使用的映射行：按 token 位置记录它对应的 KV 地址。它不是 KV 数据页本身。逻辑位置 p0、p1…表示序列中的次序；page（页）和 slot（槽位）表示分配器管理的物理存储位置。建立映射、预留位置与写入有效 KV 是不同动作。

一个位置怎样找到每层的 KV？
R1 的逻辑 p8→请求映射：槽 12→第 ℓ 层 K[12] / V[12]

逻辑位置连续，物理页号不必连续。同一个槽号在不同层对应不同数值；请求映射不是 K/V 的第二份存储。

先预测，再操作

6 个位置扩到 8 个，还需要新页吗？

本例不需要。最后一页已有 2 个位置，再写 2 个刚好填满；但这些尾页空位仍属于 R1，不能当成可分给其他请求的空闲整页。

连续 6 个 token 相同，为什么只复用 4 个？

本例 page_size=4，普通 RadixCache 保留完整匹配页。剩余两个相同 token 所在页不完整，需要计算；这与同一请求继续使用自己持有的尾页是两件事。

R1 结束后，共享页可以马上回收吗？

R2 仍持有时不能驱逐。两条请求都结束后，页可以继续留在缓存；直到驱逐，才归还分配器。

空闲页变多，为什么设备显存占用未必下降？

静态 KV 池已经预分配 buffer。请求结束或驱逐归还的是池内位置，不是把整块设备内存交还系统；也不保证把旧字节清零。
