    为什么没把所有名字带 queue 的对象都画成请求队列？

    本图聚焦普通 PD Prefill、PP=3 下的本地请求容器。mbs / last_mbs 是微批槽；last_rank_comm_queue、send_*_work、tensor inbox 维护事件、通信任务或 tensor 消息，不是 Req 排队的下一站。pending_chunk_rids 是 rid 集合，也不是 Req 队列。

    普通分块通过 chunked_req 直接续算，不会每块都退回 waiting_queue。启用乐观 Prefill 后，optimistic_release_and_requeue 才有归还 KV 后重新进入 waiting 或 bootstrap 的路径；本页关闭该模式，没有把这条重试路径混入普通分块。Decode 内部队列也不在本图范围。

    同级可有多个请求同时处于不同队列；本图只追踪 R0，显示的 0 / 1 是该请求的局部示例，不是全服务队列长度。各 PP 级独立执行，不表示同一时刻的全局快照。

    先分清三件事，再理解状态机

    01 / 计算通路

    激活走 PP，KV 去 Decode

    激活连接模型的前后层；每级只生产并发送自己的 KV。首 token 结果沿环回流，不能把这三条通路画成同一根箭头。

    02 / 准入边界

    握手好，也可能还不能算

    共同 good 之后仍要完成本地 metadata 分配；进了 waiting_queue，还要通过选批预算。每一道门挡住的是不同阶段。

    03 / 释放边界

    终态有成功，也有失败

    release 汇总 Success ∪ Failed 的交集；本级复查后按各自结果清理。清理请求引用不等于缓存物理清空，也不证明端到端成功。
