Multi-LoRA：身份、加载、混合组批与缓存隔离

同一基础模型服务多个 adapter：先追名字与身份，再追 GPU 槽位和本轮 token 行，最后核对 KV 与卸载条件。

先修与跨章回看
原理：Transformer 前向总览原理：KV Cache 与前缀复用
五个标识分别负责什么同一个 X，三条请求得到各自的结果身份额度与普通 token/KV 预算分别检查名字相同、槽位相同，仍可能是新缓存身份固定源码

LoRA（Low-Rank Adaptation，低秩适配）用 A/B 矩阵表达权重增量。Multi-LoRA 让多种适配器共享基础权重；本轮仍要为每一条请求选择正确的增量，不能把某个 adapter 永久合进公共 W 后服务所有请求。

本例 R1 用 alpha，R2 用 beta，R3 用基础模型 None。W 是单位矩阵，X=[1,2]；GPU 槽号只是本轮映射示例，r 是低秩维度，不是设备 rank。

五个标识分别负责什么

标识含义为什么不能混用
名字用户选择的 alpha/beta动态重载同名可产生新内部 ID
内部 ID一次 adapter 的身份参与请求与缓存命名空间
槽号本轮 GPU A/B 存放位置可驱逐并装入其他 adapter
低秩 rA/B 的中间维度不是 GPU rank
token 段当前 batch 中属于请求的输入行映射必须随筛选与组批一起更新

同一个 X，三条请求得到各自的结果

行向量约定下，Y=XWᵀ+(alpha/r)(XAᵀ)Bᵀ。本例 alpha adapter 用 A=[1,0]、B=[1,1]、scale=2，得到增量 [2,2]，输出 [3,4]。beta 用 A=[0,1]、B=[1,−1]、scale=1，输出 [3,0]。基础模型仍输出 [1,2]。

先有 CPU 配置与权重，再准备 GPU 驻留；本轮 metadata 才把请求身份、槽位、实际 r、scale 与 token 段交给 backend。装载返回或存在映射，都不能代替所用异步路径的就绪条件。

身份额度与普通 token/KV 预算分别检查

本例额度 3 可容纳 alpha、beta、None；降为 2 时，一条请求等待身份额度。这只是一道准入条件，之后仍需满足普通 token budget、KV 和执行约束。固定源码还考虑 pinned adapter 等额外容量条件。

GPU 权重驱逐、为公平性暂时 drain 运行请求、从名字登记表动态卸载，是三类不同动作。None 也是身份，EMPTY_SLOT 才表示空槽；实际槽号可改变。

名字相同、槽位相同，仍可能是新缓存身份

切换 beta 重载为 uB2，演示它可复用相同物理槽，却不能直接命中 uB 的旧前缀。缓存键要带计算身份；adapter 权重池与 KV 池也分别管理。

旧 ID 不再接收新请求，不等于旧请求已经结束；新的命名空间隔离旧缓存，也不代表旧 KV 已物理释放。动态卸载仍要等待所需请求引用退役，再处理其拥有的资源。

重载场景另给定 beta 的 B=[2,−1]，相同 X 的增量变为 [4,−2]，输出为 [5,0]。名字仍为 beta，内部 ID 和计算身份已经变化。

先预测，再解释

同 batch 的三个请求只用两种 adapter 名字，是否一定只占两种身份？

还要计入基础模型 None，以及固定实现中的 pinned 等约束。

把 beta 换到之前 alpha 的槽，能否继续使用 alpha 的前缀？

不能。槽位不是计算身份；模型、adapter ID 和输入/命名空间仍须匹配。
