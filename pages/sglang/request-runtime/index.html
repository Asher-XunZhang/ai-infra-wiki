先分清进程，才能读懂箭头

这里选择一个 tokenizer worker、一个 detokenizer worker、一个 Scheduler rank 的普通文本生成。HTTP 和 TokenizerManager 在前端进程；Worker / ModelRunner 是本例 Scheduler 进程中的执行组件，不能因为名字叫 Worker 就把它画成另一台机器。

同一个 rid 关联不同对象，不表示它们共享同一块 Python 内存。一次 API 批量输入也不保证对应一次 GPU batch；调度器还要根据缓存、长度、预算和模式选择执行集合。

正常结束：三种“完成”要分别核对

  1. 后端生成完成：Req 记录结束原因，普通路径开始相应资源收尾。
  2. 前端状态完成：输出经过回程，TokenizerManager 标记完成、移除关联状态并通知等待者。
  3. 客户端观察到完成：还取决于响应发送和网络连接，前两项不是网络 ACK。

输入 p1…p4、输出 y1…y3 的普通示例只需三次 forward：Prefill 输入四个 p，随后 Decode 分别输入 y1、y2。最终有六个计算过的位置；y3 被预测出来，却没有再作为输入，所以不能凭“输出三个”推断 KV 也增加三个。

本例默认 page_size=1、无前缀命中与其他持有者。启用可插入的 Radix Cache 时，有效前缀可由缓存接管，请求行仍要释放；关闭缓存时由分配器回收相关 KV。分页尾部、重复前缀、特殊模型和在途操作有各自约束，不能直接按本例个数计算生产显存。

取消：先问请求现在归谁处理

位置普通路径的处理不能做的推断
尚未派发验证失败时清理前端未派发状态不能假想后端已有 KV 要回收
还在等待队列，未开始执行Scheduler 移出队列并回告前端发出取消不等于后端已经处理
已进入运行集合设置 to_finish，再通过结果处理推进结束与资源释放不能理解为立即抢占 GPU 或立即释放全部 KV

演示中的“执行中取消”选择已回传首段文本后取消，再走一次普通 Decode 的结果收尾；并不保证客户端看到额外采样文本。Overlap、Chunked Prefill、PD 传输和特殊缓存的在途状态，需要各自分析。继续阅读 PD Prefill 请求生命周期 时，留意那里额外的握手与交接队列。

用边界定位问题

看到“请求已派发”但迟迟没有回答，沿链逐段找证据：前端是否成功准备和发送 → Scheduler 是否接收并入队 → 是否获得预算进入 batch → 执行结果是否被消费 → 输出是否经过反分词和前端关联 → 客户端连接是否仍在。先确认停在哪一段，再研究该段的队列或对象。

这是定位顺序，不是“某条日志必然说明根因”的规则。资源未归还时，还要区分请求行、请求仍持有的 KV、缓存保留的 KV 和其他在途持有者。

先预测，再操作验证

1. 前端 dispatched=true，此刻 GPU 一定在算吗？

不一定。停在“发送”步骤，Scheduler 尚无 Req。这个标记来自前端派发路径；后端的接收、准入和执行需要各自证据。

2. 正常生成三个输出，结束前应有几个 KV 位置？

本例是 4 个输入 + y1、y2，共 6 个位置。y3 没有进入下一轮 forward。切换输出上限，再在资源交接前核对。

3. 请求槽位释放后，为什么缓存里仍有 KV？

请求行和缓存拥有不同生命周期。停在资源交接步骤，切换前缀缓存再走到同一步：一个保留有效前缀供后续复用，一个归还相关 KV；都不应让请求槽位继续被 R1 占用。

4. 排队取消与运行取消都能立刻删掉所有状态吗？

不能。普通尚未执行的等待请求可直接移除并回告；运行请求先登记待结束标记，经结果处理收尾。在取消已发出、但后端未处理的步骤，两条路径的后端状态都还在。
