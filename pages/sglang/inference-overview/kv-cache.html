RadixCache 与 Attention：前缀索引怎样连接 KV？

把缓存复用落到请求索引、模型调用和生命周期三个接口。

普通自回归文本生成固定提交 · 接口与状态对照源码 279339f113

本课追踪什么实现

连接请求的前缀索引、本轮输入范围与 attention 调用，再进入物理页和回收实现。

需要回顾原理：KV Cache 与前缀复用：为什么保存历史 K/V？

从问题理解实现

知道“旧 KV 可以复用”后，引擎还必须确定哪一段历史已经存在、实际存在哪里、哪些新位置需要计算。前缀树索引把文本前缀匹配与设备缓存地址连接起来。

进入本课图解与源码过程 ↓
复用应当针对相同历史

RadixAttention 作者文章从多次调用共享 prompt 前缀出发，用前缀树管理已算过的 KV，并在容量压力下驱逐。由此要问的是“哪些历史计算完全可以复用”，而不是两段文字表达的意思是否相近。

概念与设计说明：SGLang 作者：RadixAttention（2024-01-17） ↗

这是 2024 年设计背景；本课的命名空间和匹配约束以固定源码为准。 资料读取：2026-10-16。

为什么要维护前缀索引，而不是只比较两句话是否相似？

可复用的是符合计算条件的同一前缀状态，语义相似不足以保证数值相同。系统需要按 token 与相关身份找到精确匹配，再得到可读取的缓存位置。

展开机制与具体例子

本页普通 RadixCache 的 match_prefix 查找 token 序列与命名空间对应的最长匹配，返回设备索引及末端节点；请求据此确定本轮剩余输入范围。

用一个例子理解

相同输入文本若属于不同缓存命名空间，不能仅凭字符一致就共享条目。树节点存的是索引关系，不是复制一整份历史 KV。

取舍与条件：查到索引不意味着已经执行本轮 Attention；还需要保护有效缓存、分配新位置并完成计算。分页与特殊后端的匹配边界要分别核对。

沿实现接口阅读

  1. 选出本轮仍需处理的位置

    Req.prefix_indices → prepare_for_extend

    批次准备按已有 prefix_indices 切取 get_fill_ids 的剩余部分，同时保存前缀长度与本轮长度。

    读到这里核对：“前缀可复用”必须体现为本轮输入范围，不能只看一个命中数字。

  2. 计算剩余位置的新状态

    DeepseekV2AttentionMLA.forward

    以 DeepSeek-V3 为例，MLA 注意力先准备本轮特征，再按后端与批次条件选择计算路径。缓存保存压缩的历史表示及位置相关部分，不能直接套用基础课完整 K/V 的存储示意。

    读到这里核对：地址准备、模型计算和缓存持有是三个责任，不能把它们都叫作“缓存”。

  3. 追踪谁还持有这些位置

    请求结果处理 → 缓存与资源管理

    Prefill 的未完成请求仍有后续工作；处理分块、写入和缓存时，要结合请求状态判断。

    读到这里核对：下一课分别操作请求映射、共享保护和驱逐，不把请求结束等同于物理位置已空闲。
