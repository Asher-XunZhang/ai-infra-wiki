从问题理解实现

引擎需要按 token 前缀找到已有 KV 的位置索引，并保护仍在使用的路径。Radix Tree 的搜索、分裂、插入与驱逐围绕这组索引展开。

复用应当针对相同历史

RadixAttention 作者文章从多次调用共享 prompt 前缀出发，用前缀树管理已算过的 KV，并在容量压力下驱逐。由此要问的是“哪些历史计算完全可以复用”，而不是两段文字表达的意思是否相近。

为什么按 token 前缀查树，而不是比较两句话是否相似？为什么命中、插入、保护与移除不能合成一个动作？

为什么按 token 前缀查树，而不是比较两句话是否相似？

可复用的是同一 token 前缀下已经算出的 K/V；语义相似不能保证数值相同。树节点保存一段 token 和对应槽号，请求命中后只计算剩余位置。

展开机制与具体例子

match_prefix 先把 RadixKey 按 page_size 对齐，再用第一页 token 组定位候选节点；match_at 用指数扩大的比较窗口与局部二分确定匹配长度，最后向下取整到完整页。匹配在节点内部结束时，_split_node 把共享前缀显式化；返回的 device_indices 写入请求的 prefix_indices。

用一个例子理解

R2 只共享前 4 个 token 时，搜索会在 N1 中间分裂出 N2（ABCD）与 N1（EFGH）。变化的是索引节点和 value 切片，K/V 数值没有移动。

取舍与条件：匹配粒度受 page_size 和命名空间约束。查到索引之后，调度准入仍要保护命中路径；索引返回与路径加锁是两个动作。

为什么命中、插入、保护与移除不能合成一个动作？

命中只返回现有索引；插入让新后缀可被复用；锁保护活跃请求使用的路径；驱逐只能选择未锁叶。这四种动作改变不同的树状态。

展开机制与具体例子

prefill 后 cache_unfinished_req 先 insert，再重新 match_prefix、更新匹配结果并移动路径保护；请求结束时 dec_lock_ref 沿路径减锁。只有 lock_ref=0 且无孩子的节点才能进入 evictable_leaves，被 evict 选中。

用一个例子理解

R1 结束后，N3 先成为未锁叶。删除 N3 后，N1 才成为新的候选；R2 仍在使用的 N2（ABCD）一直受保护。

取舍与条件：尽早插入提高复用机会，但匹配结果和路径保护必须同步。结束请求可以保留索引，真正驱逐时才移除节点。

    搜索、插入、保护、移除的精确条件

    下面按固定提交的实际接口拆开四个动作。动画只抽取普通路径；每一步的源码入口仍可回到原文件核对。

    搜索：先对齐页，再比较 token

    1. RadixKey.page_aligned(page_size) 把查询长度向下截到 page_size 的整数倍。本例 page_size=4，所以 8 个 token 的节点只会在 4 的边界上被切开；若 page_size=1，粒度才回到单个 token。
    2. 每一层用“第一页 token 组”作为 child_key 找到候选子节点，进入后由 match_at 用指数扩大的比较窗口与局部二分确定匹配长度，最后向下取整到完整页。候选路由不替代精确比较；真正决定命中长度的是 token 序列，以及 extra_key / cache_salt 等命名空间条件。
    3. 如果匹配在节点的 key 中间结束（本例 R2 只在 ABCD 处命中），_match_prefix_helper 调用 _split_node：新建一个前缀父节点，原来的子节点保留为后缀。value 索引数组按匹配位置切片，K/V 数值没有移动。
    4. 返回的 device_indices 会写入请求的 prefix_indices，末端节点写入 last_node。match_prefix 本身不加锁；调度器准入请求时通过 PrefillAdder._req_inc_lock_ref 保护命中路径。请求再用 prepare_for_extend 去掉已命中部分，只为本轮剩余位置准备输入。

    插入：prefill 后先挂前缀，结束时再收尾

    1. prefill 完成后，cache_unfinished_req 把已算好 KV 的位置索引及对应 token 插入树。这样请求还在解码时，下一条同前缀请求就能命中。插入后它会再 match_prefix 一次，把请求行重写成树返回的槽号，并把锁从旧的 last_node 移到新的末端节点。
    2. 请求结束时，cache_finished_req 处理已提交的完整 KV：必要时插入整段；如果 prompt 边界落在新叶内部，还会再插一次，使 prompt 与生成 token 可以分别被驱逐；先归还重复位置和未对齐尾部，再减少锁；随后 release_kv_cache 才归还请求行。
    3. insert 只接收页对齐的 key 和 value；命中的部分不重复创建节点，未命中的后缀才成为新叶。树里的 value 是槽号数组，不是 K/V 张量。

    保护：锁沿“实际命中的路径”累加

    1. inc_lock_ref(last_node) 从末端节点一路走到 root（不含 root）。路径上每个节点 lock_ref 加 1；从 0 变 1 时，该节点的 token 长度从可驱逐容量移到受保护容量。
    2. dec_lock_ref 反向执行：从 1 变 0 时移回可驱逐容量，再减 1。root 初始就是 lock_ref=1，不参与回收判断。
    3. 锁保护的是这条请求匹配到的路径，不是整个子树。R1 结束后，R2 只锁住 ABCD，所以 EFGH 可以在 R2 仍活跃时被驱逐；反过来，祖先被锁住也不代表后代自动受保护。

    移除：只有“未锁的叶”才是候选

    1. _update_leaf_status 把满足“没有未驱逐的孩子”且 lock_ref=0 的节点放进 evictable_leaves。有孩子、被锁、或已经驱逐的节点都不在集合里。
    2. evict(num_tokens) 按当前驱逐策略从叶集合取节点，先调用 free_segment(node.value) 交给存储层释放，再 _delete_leaf 断开父子关系；本图只展开后者和候选集合的变化。若父节点因此变成无孩子且未锁，会成为新的候选；循环直到回收够或集合为空。
    3. 本页按默认 LRU 假设选择先后；固定源码的 eviction_policy 可以替换策略。因此动画展示的是一条合法的 LRU 顺序，不是所有部署的唯一顺序。
    本例边界

    普通 RadixCache；page_size=4 是教学设定，不是固定默认值，实际值由后端与启动参数解析；只有一个命名空间，省略逐 token 解码。不覆盖 MLA、HiCache 分层回载、SWA / Mamba / 混合状态、投机解码、chunked prefill 与 PD 分离。源码核对不等于运行过 GPU 或做过性能测量。

    2. 再看 prefill 后的插入与请求行重写

      cache_unfinished_req → insert

      插入后重新 match_prefix、写回请求行、移动锁；这是“解码中的请求也能被后续请求复用”的关键步骤。

      evict / dec_lock_ref / _update_leaf_status

      请求结束先减锁；节点要等到成为未锁叶，才可能被 evict 选中并从树中移除。

      读到这里核对：请求结束、可驱逐、节点移除是三个不同状态，不能合成一个事件。

    先预测，再解释

    R2 与 R1 共享前 4 个 token，为什么搜索会新增一个节点？

    因为匹配在 N1 的 8-token key 内部结束。树必须把共享边界显式化，才能让后续请求直接从 4 个 token 处分支；这个动作是 _split_node，而不是等到 insert 才发生。新增的是索引父节点 N2，原有 K/V 数值没有移动。

    R1 结束以后，为什么 N3 还留在树里？

    结束请求使它的路径减锁。N3 只是从“保护中”变成“可驱逐叶”；直到 evict 真正选中它，才会删除节点。这段缓存仍有可能供后续请求命中。

    R2 还在解码时，为什么 EFGH 可以被驱逐，ABCD 不行？

    锁只沿 R2 实际命中的路径累加。R2 只命中 ABCD，所以 N2（ABCD）的 lock_ref=1；N1（EFGH）不在 R2 的路径上，R1 结束后它的锁为 0。等 N1 成为叶，它就能被驱逐。祖先被锁住不会自动保护所有后代。

    为什么驱逐 XYZW 后，ABCD 仍然留在树里？

    删除 N4 只是让 N2 第一次满足“无孩子且未锁”。N2 成为新的驱逐候选，但还未被选择和移除；父节点资格变化不等于立即删除父节点。

    相同文本、不同 cache_salt，会命中同一棵树节点吗？

    不会。本例只说“同一命名空间”这一条路径；extra_key 或 cache_salt 不同的请求会被有意隔离。文本看起来一样也不够，必须 token 序列和命名空间条件都匹配；另外 page_size>1 时匹配长度还要按页向下对齐。
