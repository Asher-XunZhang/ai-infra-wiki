模型结构会改变引擎要管理的状态

DeepSeek-V3 技术报告采用 MLA 与 MoE 来改善计算和存储效率。它们也使引擎不能只套用一种普通 Attention 或稠密 FFN 的执行接口：需要对应的缓存表示、专家路由与并行组织。

概念与设计说明：DeepSeek-V3 Technical Report（2025-02 版本） ↗ · SGLang 官方：Pipeline Parallelism for Long Context ↗

报告用于模型结构；PPProxyTensors 等具体接口以本课固定提交为准。 资料读取：2026-10-16。

为什么 PP 首级、中间级和末级的输入输出不同？MLA、MoE 为什么会影响引擎接口？

为什么 PP 首级、中间级和末级的输入输出不同？

前一阶段已经完成一部分模型层，后一阶段需要在中间特征上继续，而不是重新从 token ID 开始。只有执行到输出头，才得到用于选择下一 token 的词表分数。

展开机制与具体例子

所选 DeepSeek-V3 路径中，首级使用 Embedding；非首级读取 PPProxyTensors 中的 hidden_states 和 residual，再执行自己的层区间。末级交给 logits_processor，其他级返回供接力的中间张量。

取舍与条件：代理张量保存的是层间继续计算所需的数据；各层历史缓存有另一条存储与传输路径。PP 增加激活交接与依赖等待，不保证单个微批次延迟降低。

MLA、MoE 为什么会影响引擎接口？

模型并非总是“每层相同的完整 K/V 加一个稠密前馈层”。缓存格式和计算组织改变后，后端需要知道应当存什么、读取什么、调用哪条实现。

展开机制与具体例子

DeepSeek-V3 的 MLA 使用压缩的历史表示，MoE 按路由组织专家工作。源码类复用 deepseek_v2.py；本课围绕 V3 的调用边界阅读，具体地址与 Triton MLA 路径在执行课展开。

取舍与条件：理解接口可以避免把基础课的简化 K/V 图当作所有模型的实际布局；具体内存与通信成本仍取决于模型配置和后端。

沿 DeepSeek-V3 的实现接口阅读

为什么源码文件叫 deepseek_v2.py？固定版本中的 DeepseekV3ForCausalLM 继承 DeepseekV2ForCausalLM，共用下列模型与层实现。本课追踪 V3 普通生成，不展开 V3.2 的 DSA 路径、投机解码和 TBO（两批重叠执行）。

  1. 进入模型：先把编号变成向量

    DeepseekV2Model.forward

    首个 PP 阶段把 input_ids（token 编号）转换为 hidden states（当前的数字特征），或使用传入的 input_embeds。其他阶段接收上一级的中间结果。

    读到这里核对：同一条请求只在入口做嵌入；后面的阶段接着计算，不会重新分词。

  2. 执行本级的层：参考历史，再加工特征

    DeepseekV2DecoderLayer.forward

    先调用 self_attn；DeepSeek-V3 使用 MLA（多头潜在注意力），以压缩表示保存历史信息。随后调用 mlp：按层配置使用普通前馈网络或 MoE（混合专家，让路由器选出参与计算的专家）。

    读到这里核对：源码用同一个 mlp 字段承接两类实现。别把字段名理解为每层都只有一个普通 MLP；MLA 缓存也不能直接套用基础课完整逐头 K/V 的存储图。

  3. 交出结果：中间特征，还是词表分数？

    DeepseekV2ForCausalLM.forward

    非末级交出 PPProxyTensors 中的 hidden_states、residual，供下一级继续计算；末级经过最终归一化和输出头，由 logits_processor 得到各候选 token 的分数。

    读到这里核对：分数还不是选出的 token。后续采样才决定下一步输出哪个编号。
