分离角色之后，还要协调各级状态

官方 PD 文档将 Prefill 与 Decode 划为不同服务角色。本文进一步沿固定实现追踪 Prefill 各 PP 级的准入与收尾，并将 HiCache 的缓存进度同步单独对照。

概念与设计说明：SGLang 官方：PD Disaggregation ↗

官方文档只用于角色分离的概念背景；三种协调算法、分支和时序以本课固定源码为准。 资料读取：2026-11-09。

为什么共同名单回来，仍不能直接认定本地可继续？

名单反映某次采样的共同观察；metadata 容量、本地 sender 状态和 CUDA event 还分别决定此刻能否执行对应操作。

展开机制与具体例子

Bootstrap 用 good 交集与 bad 并集，再执行本地 finalize；release 汇合终态，再本地复查；HiCache 发布计数，再等待每条本地 ACK 的完成事件。

取舍与条件：根据固定分支解释不同门槛，不把三种路径合成通用 barrier；轨道时间只是一种合法教学安排。

读图边界：时钟、消息与硬件

PP0–PP2 是模型层的三个流水级。示例 TP=CP=1，每级一个 Scheduler 进程和 GPU，物理主机放置未指定。跨级名单走 CPU 进程组，不传激活或 KV；本地 Req 通过相同 rid 关联。跨机网卡与交换机在通信专题展开。

两类 PD 名单沿真实调用顺序展开一次或两次采样旅程；省略无关的空 loop 和 slot 轮转，假设对应 bmbs/tmbs 接收槽位已建立。非末级转发上次保存的回流结果，发生在后续本地迭代。CPU 空隙不代表服务停机；已提交 GPU 工作、KV worker 和 H2D 流可在各自依赖满足时继续。

Bootstrap 的背景 GPU 条表示起点之前已经提交的不同 B0/B1/B2，和等待准入的 R0–R2 不同。Release 的“本地复查暂态”用于演示源码防御分支，不断言某个后端正常执行时必然发生状态倒退。HiCache 展开一轮事件处理；末尾未消费的 ACK 保持在队列中，留待后轮。

时长用于阅读，不是 profiler trace。HiCache 的 CPU event.synchronize 等待与 GPU attention 的逐层 KV 可用门槛是不同机制；本课没有把整批 ACK 收尾画成 GPU 前向前的统一屏障。

谁参与，线上传的是什么？

路径参与者与入口载荷及作用
Bootstrap / Release各级 Scheduler 调用 get_rids；先在本级 Attention TP、再 CP 组归约 poll。每个 Attention DP shard 中，TP=CP=0 的代表跨级收发，接收后再向级内广播。Bootstrap 是 [good_rids, bad_rids]；release 是终态 rid 列表。两者是不同消息、不同本地队列。
HiCache ACK各级 UnifiedRadixCache；PP0 统计计数并在相关组内 MIN，随后对应 PP 通道逐级传播，各级处理自己的 ACK 队列。CPU int64 张量 [write_count, load_count, digest, −digest]。本例无 L3；digest 对应重复回收顺序的校验摘要，示例值为 0。
异步完成的来源KV sender / worker；HiCache cache controller 和 CUDA 完成事件。它们改变本地可观察状态；Scheduler 必须采样或等待事件，控制消息不会把数据复制完成。

Bootstrap：从本地就绪到实际准入

没有协调时，一个级已经取得目的地址，另一级还在握手，不能据此让所有级为同一请求继续。源码用请求 ID 把各级的观察对齐：good = 上游 good ∩ 本地 WaitingForInput，bad = 上游 bad ∪ 本地 Failed；本地已取消请求还会从 good 删除并加入 bad。

汇总沿 PP0 → PP1 → PP2，末级通过异步发送开启回流。PP0 收到后执行 pop_bootstrapped → finalize_bootstrap：先取得 metadata 槽，再初始化 sender，随后进入 waiting_queue。待调度不等于已经执行前向，本轮选批在回流处理之前。

回流载荷会受到本地处理影响。process_bootstrapped_queue 返回实际处理的 good/failed 名单，并保存为后续转发内容。在“PP0 metadata 不足”中，末级最初得到三个 good，PP0 只能准入 R0/R2；后续 PP1/PP2 收到的是 R0/R2，R1 继续留队。名单未覆盖的请求还可在本地被再次检查为 Failed，但不会仅凭本地 WaitingForInput 绕过 good 共识。

“PP1 晚就绪”展示快照语义：R1 在第一次采样后才就绪，本轮已发送的集合不会自动增加它，第二轮重新采样后才能纳入。失败场景保留其独立含义，不能把 bad 并集写成多数投票。

Release：共同终态仍需本地复查

各级发送自己负责层的 KV，完成时刻可以不同。每级从 inflight 队列中采样 Success ∪ Failed，沿 PP 求交集，末级把结果发回。正在传输的级会让对应 rid 暂时退出交集，已经成功的级仍须保持请求持有。

各级收到 release_rids 后，process_disagg_prefill_inflight_queue 再次 poll：不在名单、或本地仍为非终态，就进入 undone_reqs；Success 解除请求的 KV 引用、调用缓存 finish、清理 sender，Failed 进入专门失败处理，完成后归还 metadata 并更新 inflight。

“R1 在 PP1 失败”中 R1 仍能进入终态交集，其他级可能执行各自的成功收尾。这不证明 R1 的端到端推理成功。该列表不是一个所有级成功的投票，也不是 Decode 的调度许可；D 有自己的数据、身份与 metadata 检查。

区分 P 侧收尾与 D 侧就绪

HiCache ACK：统一消费数量，本地确认完成

这里没有请求 good/bad 集合。ACK 是缓存搬运任务的完成记录，包含本地 finish_event 与节点信息。PP0 从队首统计连续就绪数量，遇到第一条未就绪就停止；write 与 load 分别计数。同级多 rank 时，例如 load 计数为 2 和 1，MIN 后只能发布 1。

_pp_sync 让后级先 recv，若还有下一级，clone 后立即 isend 并保存 work。接下来依次调用 writing_check、loading_check。每条 ACK 先 pop，再 finish_event.synchronize()；load 完成后才解除这次回载的 device/host 锁、结束加载保护，host 副本仍可保留。

默认场景中，PP1 收到计数并转发后仍在等待 L1，PP2 已确认自己的事件并继续选批。这个交错说明计数一致不等于同时完成，也不是全 PP 的 MIN 屏障。下一轮先 _drain_async_work 回收之前的 isend，后级较慢时仍会形成真实背压。

“本轮只公布一条”与“load count=0”分别展示截断和空进度：晚到的完成事件不会改写在途计数；即便后级自己的数据已就绪，也不能自行多消费 ACK。digest / −digest 校验回收顺序一致，不能被解释成更多已完成的 ACK。
