调度与结果处理 · Scheduler · ScheduleBatch

为什么需要：请求不断到来，计算与 KV 容量有限，需要决定本轮接纳谁、执行多少。

普通 event_loop_normal 接收请求、获取下一批、执行并消费结果。ScheduleBatch 描述当前批次；结果处理更新请求进度与结束状态，再发出输出 token ID。未结束的请求继续参与后续调度。

KV 管理 · 前缀缓存 · 地址池 · 分配器

为什么需要：复用已有历史，并让新 token 有可写位置；请求结束后还要按共享关系回收。

为什么分开前端、Scheduler 和反分词职责？

接收连接与返回流式结果，需要前端状态；选择下一批工作，需要队列和资源状态；把输出 ID 变成文字，又需要输出处理。把职责说清楚，才能定位“已接收却没有回答”停在哪一步。

展开机制与具体例子

本页普通 Python 路径将 TokenizerManager、Scheduler 和 DetokenizerManager 按启动装配连接；Worker / Runner 是 Scheduler 进程内的执行组件。名称上的分层不自动意味着新进程。

取舍与条件：从职责可以理解这种拆分如何组织独立状态，但仅凭进程数不能断言性能或故障隔离效果。跨进程会增加消息关联与交接工作。

读图自测

图里有 Scheduler、Worker、Runner，就一定是三个进程吗？

不是。本页普通路径里，后两者由 Scheduler 进程内调用。换成多 rank、Ray 或其他启动方式时，需要重新核对进程外框。

两张 GPU 一定对应两个完整模型副本吗？

不是。TP=2 可以是两张卡共同完成一个副本；DP=2 示例则由两个副本分别接请求。PD 又按服务角色接力，同一请求跨两侧推进。

GPU 产生了首 token，客户端就已经看到它了吗？

还要经过结果处理、反分词与响应链。图中采样和可见分开变化；时间测量也需要分别界定。
