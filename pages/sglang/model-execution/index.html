本课追踪什么实现

跟踪模型调用、Worker / Runner 交接、图重放资格与真实计算行。

需要回顾原理：GPU 计算与访存：算力、带宽和 CUDA Graph

从问题理解实现

调度器选好了请求，还不能把请求对象直接当成 GPU 输入。执行层需要把本轮 token、位置、历史地址和模型实现接起来，并判断能否使用已经准备好的执行图。

进入本课图解与源码过程 ↓
减少组织开销，而不改变计算依赖

SGLang 团队的调度文章指出，CPU 仍需选批、分配和匹配缓存，可以在 GPU 计算当前批次时准备下一批。NVIDIA 的 CUDA Graph 文档则解释如何复用执行图来减少重复提交开销。这是两类优化，不能合成一个“GPU 自动加速”开关。

概念与设计说明：SGLang 团队：v0.4 调度设计（2024-12-04） ↗ · NVIDIA：CUDA Graphs ↗

文章说明优化目标；ForwardBatch 的字段和图重放资格按下方源码核对。 资料读取：2026-10-16。

为什么从 ScheduleBatch 转成 ForwardBatch？为什么图重放需要资格检查和图桶？

为什么从 ScheduleBatch 转成 ForwardBatch？

调度关注成员与资源，模型调用关注本轮张量与元数据。区分两种视图，使执行接口不必重新决定哪些请求入批。

展开机制与具体例子

ForwardBatch.init_new 从调度批次整理前向模式、长度、位置和缓存信息，随后 Runner 与选定后端使用这些信息调用模型。后端负责把当前布局接到实现，不能替代请求准入和缓存淘汰策略。

取舍与条件：这种职责分层需要维持元数据一致：token 内容正确但地址、长度或模式错误，计算仍可能读错历史。不能仅检查输入 ID。

为什么图重放需要资格检查和图桶？

已捕获的执行结构有输入规格与路径约束。运行时的请求数量和特性会变化，因此不能把所有批次直接送进同一张图。

展开机制与具体例子

can_run_graph 检查当前批次；符合条件时选取支持的规格，必要时补齐到图桶，并按真实输入行裁回结果。不符合时仍可走对应常规执行路径。

用一个例子理解

本页 3 条普通 Decode 请求放入容量 4 的教学图桶，第四行是 PAD，不是第四条用户请求。

取舍与条件：图桶减少重复提交的机会，需要付出捕获、存储和可能的补齐工作；能进入图与端到端更快是不同判断。

读图前：术语与编号

图桶（graph bucket）是按固定输入形状准备的 CUDA Graph 执行规格；PAD 是 padding（补齐行），不代表真实请求。Eager 指逐次提交常规算子调用，Graph replay 指重放已捕获的操作图。Logits 是采样前的词表分数，不是已经选出的 token。矩阵实验里的 M 表示本轮输入矩阵的行数。

调度决定本轮做什么；执行层把输入、地址和计算实现接起来。

执行层的职责总览
Worker：整理输入→Runner：选择执行方式→模型：网络计算
Attention backend：地址与适配→kernel：具体设备工作

下方是模型计算内部的一段，其他线性层、Norm 等也有自己的实现入口。backend 不拥有请求准入和缓存淘汰策略；kernel 返回中间张量，不会直接替整套模型生成最终回答。

先预测，再操作

准备好查询和压缩 KV，就能直接计算了吗？

还需要正确的历史 KV 地址、长度、层身份和本轮元数据。示例先准备索引，再写入本轮 MLA 状态并执行计算；缓存不是基础课里的完整逐头 K/V。

3 条请求填进容量 4 的图桶，会返回 4 条回答吗？

不会。补齐行不属于真实请求；普通 Decode 输出按真实 token 行数裁回，再交给后续采样。

没有走 CUDA Graph，是否说明 GPU 没执行？

不是。Eager 仍然调用模型和设备算子。Graph 改变提交与重放方式，不是请求是否执行的开关。

为什么算力翻倍，理想下界可能不变？

若访存项仍更长，缩短计算项不改变两者的最大值。切换 M=1 与 M=256 比较；实际利用率还需运行测量。
