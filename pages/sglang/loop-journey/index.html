    普通循环：先闭合本轮，再选择下一批

    用 R1 的一次 Extend 和一次 Decode 把链路接起来。一次请求跨过多轮 loop；一次 batch 的成员也可以在后续选批时改变。

    1. 接收与选择：接收 R1，选成 B0；准备 token 范围、长度、请求索引与 KV 地址。CPU 知道“写哪儿”，GPU 才负责写出各层 KV。
    2. 设备执行：prompt H2D → 模型层 → logits → 采样 t1。输出 token 写入设备 FutureMap；它不是一份新的 KV。
    3. 结果提交：CPU 需要可读结果后，更新 output_ids、输出和完成条件。R1 还未结束，继续保留上下文。
    4. 下一轮：B1 Decode 在 GPU 从 FutureMap 取 t1，结合历史 KV 算出 EOS；CPU 读到它才将 R1 标为完成。
    5. 收尾：后续选批过滤 R1，按缓存策略释放或保留 KV；没有当前批时进入 idle。普通循环的 Python 顺序不表示每个 CUDA 调用都同步阻塞。

    预测：B0 的 run_batch 返回后，CPU 是否可以不检查结果可读性就提交 t1？

    Overlap：提前规划，按依赖提交

    CPU 的排序、分配、元数据整理和结果处理也需要时间。Overlap 为这些工作与 GPU 执行提供重叠窗口；不承诺任何工作负载都能完全隐藏 CPU 开销。

    1. 输入依赖：forward_stream 等 schedule_stream 已提交的准备工作；未来 token 在 GPU 中由前一批写入，下一批再读取。
    2. 共享缓冲依赖：schedule_stream 的后续写入必须在前一 forward 读完共享内容之后。WAR 是“先读后写”的设备顺序；CPU 仍可做不冲突的规划。
    3. 结果依赖：copy_stream 等输出就绪，CPU 在 copy_done 上等待可读结果。提交 B1 后处理 B0，result_queue 保存对应 batch 元数据快照与结果引用。
    4. 结束与排空：CPU 晚读到 EOS 时，下一批可能已经提交。完成标记阻止追加额外有效输出；无新 batch 仍要处理旧队列，不能跳过在途工作的收尾。
    哪些条件会改变这条主线？

    连续 Prefill、语法或投机路径可要求先处理旧结果；延迟采样可能依赖上一批已提交的语法状态。本例关闭这些路径。CUDA Graph 改变提交方式，不等于 Overlap；本例也不把数据副本或 batch.copy() 解释为深拷贝全部 GPU 数据。

    预测：勾选“暂缓 B0 的 copy_done”，来到等待处：B1 是否还没有提交？

    PP：一轮负责当前批，也可能处理旧批

    PP0 负责模型前段层，PP1 负责后段层与采样；每级各有 CPU Scheduler、本地 batch、GPU 和本地 KV。本例两条请求各占一个 microbatch，便于追踪；真实 microbatch 可以包含多条请求。

    1. M1 的主路：PP0 组批 → GPU0 前段层 → 激活到 GPU1 → 后段层与采样 → 输出回到 PP0 → PP0 处理 → 转发 PP1 → PP1 处理。各级 KV 留在本级。
    2. PP0 的 L1：当前槽 1 提交 M2，接着接收并处理旧槽 0 的 M1，最后才能发送当前 M2 的激活。depth=0 的这个顺序解释了“旧结果迟到为什么拖住当前批”。
    3. PP1 的 L1：提交 M2 后段并发送其输出，再等 M1 结果环回。它与 PP0 的 L1 不要求同一时刻开始或结束。
    4. 空槽仍要收尾：PP0 L2 没有新 M1，但仍转发旧 M1、处理 M2；随后两级继续排空 M2。逻辑完成、消息回环完成与槽位复用是不同检查点。
    slot、async depth 与普通 Overlap 的边界

    pp_loop_size = pp_size + pp_async_batch_depth；本例 2 + 0 = 2。mbs / last_mbs / running_mbs 按槽保存不同生命周期状态。开启 async depth 会改变输出预处理相对 launch 的顺序；本图不外推其时序。固定基线对 PP 关闭普通 event_loop_overlap，PP 自己仍可在不同 GPU 和 CPU 之间安排重叠。

    预测：在“看一轮”中选 PP0 · L1，当前计算与结果处理分别属于谁？

    对象速查：请求、批次、microbatch、slot 与 loop
    • 请求 Req：用户的一次生成任务，保存输入、已提交输出与完成状态，可跨多个执行批次。
    • 执行批次 ScheduleBatch：本轮一起进入执行的请求集合及其元数据；B0、B1 在图中表示不同执行实例。
    • PP microbatch：一份穿过模型各 stage 的执行工作。M1 / M2 是图中的身份，各 stage 分别持有对应的本地对象。
    • slot：PP 环形数组的可复用下标，不是 GPU、模型层或物理 KV 页。同一槽后续可装不同批次。
    • loop：本地调度推进。本课 L 表示一次普通 while 迭代，或 PP 内层 for 的一次槽位迭代；外层 while 还会遍历所有槽。
    • stream / event：设备工作的排队轨道与完成标记。wait_event / wait_stream 建立设备顺序；event.synchronize() 在调用线程等待事件。
