注册工作流与缓存亲和（独立基线）↗

“限流”与“超时”要先确定在哪一层
Gateway 额度 / 队列→Runtime 等待队列→实际执行与响应体

Gateway 的额度与等待、Scheduler 的排队 / 运行时限、客户端的等待期限分别维护自己的状态。客户端超时不会自动证明后端已取消；收到响应头也不证明流式响应体已经完成。重试还需要判断请求是否可能已经执行，不能只凭“没有收到结果”就宣布此前没有生效。

本页只实现 Runtime 等待队列容量与两条取消分支；Gateway 额度、重试和熔断细节见服务治理源码专题 ↗。

先预测，再操作

R1 一直没输出，/health_generate 可以返回 200 吗？

可以。所选实现看全局回程活动，其他请求的回包也可能让检查通过。切到“R2 活跃，R1 仍等待”观察两件事同时发生。

Worker 健康，就一定会被选中吗？

不一定。Round-robin 还会过滤熔断器不允许的实例；模型、角色等条件在候选集合上另有边界。

队列容量 2，是否代表最多只能有两条在途请求？

不代表。图中还单独存在执行中的 R0，Gateway 和前端也有各自登记。先明确你数的是哪一个对象。

健康入口已返回 503，为什么退出还会等下去？

仍有请求登记未结束，或新流量继续到达，都可能阻止正常排空。发送 ShutdownReq 后还要观察 Scheduler 是否实际退出。
