本课追踪什么实现

核对启动、探活、路由、队列准入、取消和退出时各组件的责任。

需要回顾原理：请求路由与取消：服务在线为何还没收到回答？

从问题理解实现

服务管理要回答几个不同问题：能否接收连接、能否选中实例、请求是否进入计算、取消后是否已收尾。需要不同观测与控制，避免用一个健康状态替代全部判断。

进入本课图解与源码过程 ↓
服务可访问，还要观察请求是否推进

官方可观测性入口区分指标、逐请求追踪和日志。观察服务总体状态后，还需要沿目标请求核对排队、计算和回包；本课进一步用健康检查与退出流程说明每种信号能证明什么。

为什么健康检查不能证明某条请求正在前进？为什么退出需要先停止新投递，再等待排空？

为什么健康检查不能证明某条请求正在前进？

探活检查的对象与具体业务请求可能不同。整体回程有活动时，一条因资源或其他原因等待的请求仍可能没有输出。

展开机制与具体例子

本页固定版本的生成探测路径会观察全局回程活动，因此“R2 活跃、R1 等待”可以同时发生；追踪 R1 仍需它自己的 rid、队列与执行证据。

取舍与条件：探测能较轻量地判断某类服务状态，但覆盖范围有限。不能把 200 当作每个请求、每个 GPU 或整个数据面的完好证明。

health_generate · 本课实现核对 ↗

为什么退出需要先停止新投递，再等待排空？

如果旧请求尚未结束，新请求又持续到达，服务很难达到可退出状态；直接终止也可能截断响应和在途工作。

展开机制与具体例子

本页分别观察不再接纳、前端登记排空、发送 ShutdownReq 与 Scheduler 实际退出。客户端断连、等待超时和进程退出也各有自己的处理入口。

取舍与条件：等待排空有时间成本，也依赖上游是否停止投递。超时或已发退出消息，都不能单独证明执行进程已经消失或资源已释放。

“限流”与“超时”要先确定在哪一层
Gateway 额度 / 队列→Runtime 等待队列→实际执行与响应体

Gateway 的额度与等待、Scheduler 的排队 / 运行时限、客户端的等待期限分别维护自己的状态。客户端超时不会自动证明后端已取消；收到响应头也不证明流式响应体已经完成。重试还需要判断请求是否可能已经执行，不能只凭“没有收到结果”就宣布此前没有生效。

本页只实现 Runtime 等待队列容量与两条取消分支；Gateway 额度、重试和熔断细节见服务治理源码专题 ↗。

先预测，再操作

R1 一直没输出，/health_generate 可以返回 200 吗？

可以。所选实现看全局回程活动，其他请求的回包也可能让检查通过。切到“R2 活跃，R1 仍等待”观察两件事同时发生。

Worker 健康，就一定会被选中吗？

不一定。Round-robin 还会过滤熔断器不允许的实例；模型、角色等条件在候选集合上另有边界。

队列容量 2，是否代表最多只能有两条在途请求？

不代表。图中还单独存在执行中的 R0，Gateway 和前端也有各自登记。先明确你数的是哪一个对象。

健康入口已返回 503，为什么退出还会等下去？

仍有请求登记未结束，或新流量继续到达，都可能阻止正常排空。发送 ShutdownReq 后还要观察 Scheduler 是否实际退出。
