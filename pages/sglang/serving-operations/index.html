本课追踪什么实现

从问题理解实现

为什么健康检查不能证明某条请求正在前进？

网关只并发探测选中的一对 P/D，Runtime 又以本地回程活动判断生成探测。健康成功与真实跨端交接是不同证据。

展开机制与具体例子

tokio::join! 并发调用两端 /health_generate；本地探针使用 fake bootstrap，last_receive_tstamp > tic 即可通过。两端 200 不验证真实 P→D KV 传输，也不覆盖所有副本。

取舍与条件：探测能较轻量地判断某类服务状态，但覆盖范围有限。不能把 200 当作每个请求、每个 GPU 或整个数据面的完好证明。

P/D 同时派发，为什么结果仍有处理顺序？

两份 HTTP 请求并发推进，不意味着任一返回都能直接变成最终响应。

展开机制与具体例子

execute_dual_dispatch_internal 在同一 handler 中 poll 两个 send future。D 先完成会存入 decode_early；先检查 P 的结果，P 成功后才处理 D。P 失败则返回其错误并丢弃 pending D future，后端取消仍需 Runtime 检测与 Scheduler 处理。

取舍与条件：派发并发与结果依赖并存；关闭连接不是跨端原子回滚。

HTTP 完成、ReqState 删除与传输资源安全回收由不同主体负责。

为什么退出需要先停止新投递，再等待排空？

如果旧请求尚未结束，新请求又持续到达，服务很难达到可退出状态；直接终止也可能截断响应和在途工作。

展开机制与具体例子

这里只对 P 发 SIGTERM：本地健康入口返回 503，正常 watchdog 等本地 rid_to_state 排空，再派发 ShutdownReq 并观察 Scheduler 退出。已取得 KV 的 D 请求可继续执行；摘流是显式给定的部署条件。

取舍与条件：等待排空有时间成本，也依赖上游是否停止投递。超时或已发退出消息，都不能单独证明执行进程已经消失或资源已释放。

哪些普通队列规则不能直接套到 P/D？

固定版本的 _add_request_to_queue 在普通模式才执行 _abort_on_queued_limit，随后加入 waiting_queue；Prefill 进入 bootstrap_queue，Decode 进入 prealloc_queue。这不表示 P/D 没有容量限制，而是容量与准入发生在各自的机制中。

_poll_timeout_aborts 的 waiting timeout 只扫描 waiting_queue；running timeout 检查执行 batch 的 forward_entry_time。不能拿这两个计时器覆盖 bootstrap、prealloc 或 transfer 的全部等待。动画的“D 等待超时”明确从 KV 已接收、进入 waiting_queue 的时刻开始。

取消要沿当前持有者处理

所在位置取消动作后续条件
P bootstrap / inflight通知 sender.abort；PP 条件另有 prepare_abort各队列沿失败、传输退役与本地收尾路径推进
D preallocreceiver.abort；并非统一直接 pop后续轮询失败并回告；有无已分配资源取决于所处阶段
D transferreceiver.abort；满足开关及通知条件时记录 ACK，并留置接收资源完整 drain ACK 或源码的 hold timeout 分支；超时释放不等于得到 drain 证明
D waiting移除等待引用、回告前端，再走 Decode KV 释放这里的等待请求已经可能占有接收 KV
运行中的 Req设置 to_finish=ABORT由后续结果处理提交终态与收尾，不直接抢占已提交 kernel

以上不是无条件覆盖每个内部列表的承诺；例如该基线 Decode 的部分暂存等待列表在源码中明确注释尚不受 /abort_request 覆盖。场景只演示具名队列；PP、HiCache、重试、模型特殊状态要分别沿对应条件分析。

先预测，再拖动时间验证

D 先回了错误，网关会立刻跳过 P 吗？

此基线的双派发先并发 poll，D 提前响应会写入 decode_early，但循环仍等 P 结果。P 失败走 P 失败分支；P 成功后才取出或等待 D 结果。

P HTTP 失败，是否要等 D 自己的传输超时？

pending D future 会随 P 失败返回而丢弃，连接关闭可促使 D 检测断连。D 检测、AbortReq 消费、队列退役仍是后续事件。P 连带取消不计成 D 自身熔断失败。

客户端断流是否立刻中止 GPU？

不是。网关流任务丢弃上游流，Runtime 的取消任务随后检查并发送 AbortReq。已提交设备工作仍遵守执行依赖，运行中 Req 通过结果处理提交结束状态。

P 的退出标记能阻止所有直连新请求吗？

不能由该标记单独推出。普通 watchdog 等待本地登记排空，部署侧仍需停止新投递；D 不是这个本地等待条件的参与者。非健康或强制退出另有绕过等待分支。
