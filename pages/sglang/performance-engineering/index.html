先确定秒表放在哪一层
客户端等许可→HTTP：发出 → 首包 → 结束

工具的单请求 TTFT 从 adapter 发请求前开始，到第一个有内容的包。E2E 在后续流数据到达后结束；许可前等待另记。服务端 time_stats 的起止点不同，不能直接把两者之差命名为网络耗时。

看到 TTFT 上升，下一步采什么证据？
相同请求 ID→排队 / 执行区间→CPU / GPU / 通信 Trace

先按请求关联端点时间，再检查长区间的依赖：等许可、等 batch、等前序 GPU 工作，还是等传输。CPU 提交时间不等于 GPU 执行时长；多流算子重叠时，把所有 kernel 时长相加也不是请求延迟。只缩短非关键路径可能没有端到端收益。

先预测，再操作

用户多等了 120 ms，工具 TTFT 一定增加吗？

不一定。若多等在客户端 semaphore 之前，adapter 的秒表还没开始。选择“客户端许可多等”与“Scheduler 多等”比较。

ITL 都是 40 ms，证明模型均匀生成吗？

不能。后 3 个 token 一起到达时，120 ms 的包间隔可以被均摊为三个 40 ms。包内真实生成时刻没有被测到。

Prefill 耗时减半，吞吐为什么只提升 1.33 倍？

在本例中 Prefill 原本占一半，Decode 没变；总时长降到原来的 3/4。真实服务还要看排队、重叠和其他成本。

P95 下降的同时，为什么服务可能更差？

若较慢请求失败，它会退出成功延迟分布。应同时看成功率、输出量、负载和原始错误；不要只看变好的一列。
