PD 分离 · Prefill 侧 · PP=3

先看懂一轮 loop，再跟踪一份 batch

PP0、PP1、PP2 都是 Prefill 内部的流水级。本页把细小操作合并成大步骤：看看每一级一轮在忙什么，或跟着一份 batch 从准入走到 KV 传输和释放。Decode 是图外接收方。

M1–M5 表示五份 micro-batch，与详细版编号一致；“大颗粒”指操作分组。本例每份 batch 只含一个请求，三份状态槽位 s0–s2 循环复用，pp_async_batch_depth=0。时间 u 为示意值。

记住这四件事，就能读这张图

  1. loop 是调度线程的一轮工作。一个 L# 外框对应一次本地 for mb_id 迭代，里面可能准备 M3、处理旧 M1，并清理更早的请求。相同 L# 在不同 PP rank 上不同时发生。
  2. 提交 forward 不等于 GPU 已算完。loop 视角画 CPU 调度区间；batch 视角单独显示本级 GPU 前向，以及计算前后经历的等待。GPU 可以跨越 CPU loop 边界。
  3. 有些事属于共享队列。bootstrap 检查、L2 ACK、控制共识可能处理多个请求或历史状态，不能统一归到当前 M#。M1–M5 在本例共同准入，进入 waiting queue 后再依次选批。
  4. 算完还没结束。旧结果回流、本地结果处理、KV 发送和释放各有条件；收到 output 不等于 Decode 已收全 KV，传输结束后也可能继续等待释放共识。
为什么把很多小步骤合并成这五组？

按源码中的连续顺序合并：A → 检查状态；B+C → 缓存与选批；D+E → 提交前向；F+G+H → 结果与共识；I → 转发保存。空槽不会凭空多出 forward，缺失的分组会标为“本轮跳过”。

bootstrap 的本地轮询在前、共识回流和准入在后；若强行合成一个连续时间段，会掩盖它跨轮推进的事实。因此它在第一组检查状态，在第四组推进共识。L2 ACK 检查与当前 batch 的缓存准备则合到第二组，但说明中仍区分共享队列与当前 batch。

batch 视角按该 batch 的状态区间组织，包含排队和等待。它不表示每段时间都有 CPU/GPU 在执行该操作，也不把共享阶段解释为该 batch 独占资源。两条“激活接续”线概括前向到下级输入就绪的链条，包含发送提交和传输等待；精确逐步依赖请看详细版。

数据与源码边界

两种视角都由详细版的同一份模型自动派生，保留相同的示意起止时间和 M#、L#，没有重新编排执行顺序。源码固定于 SGLang 72d5c5bb73；使用 CUDA、HiRadix L2、depth=0 的完整 Prefill 成功路径。
