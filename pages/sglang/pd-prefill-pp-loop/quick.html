PD 分离 · Prefill 侧 · PP=3

在每一轮 loop 中，跟踪一份 batch

PP0、PP1、PP2 都是 Prefill 内部的流水级。每个大方块是一轮 loop；选择 M1–M5，可在同一张图上高亮相关操作，并沿下方进度带看它跨过哪些 loop、何时计算、传 KV 和释放。Decode 是图外接收方。

M1–M5 表示五份 micro-batch，与详细版编号一致；“大颗粒”指操作分组。本例每份 batch 只含一个请求，三份状态槽位 s0–s2 循环复用，pp_async_batch_depth=0。时间 u 为示意值。

包含该 batch 的操作　 多请求共享操作。高亮整个大步骤表示“其中包含”，不代表整段都归该 batch。未高亮的通用队列操作仍保留。

每级下沿的 M# 进度带与 loop 共用时间轴：a 准入/排队 → b 准备 → c GPU 前向 → d 等结果/处理 → e KV 在途 → f 等共识/释放。点击进度段查看对应 loop。

记住这四件事，就能读这张图

  1. loop 是调度线程的一轮工作。一个 L# 外框对应一次本地 for mb_id 迭代，里面可能准备 M3、处理旧 M1，并清理更早的请求。相同 L# 在不同 PP rank 上不同时发生。
  2. 提交 forward 不等于 GPU 已算完。大方块画 CPU 调度区间；高亮 batch 后，下沿进度带显示它的 GPU 前向及计算前后经历的等待。进度带跨过方块边界，就表示本级线程已经进入后续 loop，而该 batch 仍在计算、传输或等待。
  3. 有些事属于共享队列。bootstrap 检查、L2 ACK、控制共识可能处理多个请求或历史状态，不能统一归到当前 M#。M1–M5 在本例共同准入，进入 waiting queue 后再依次选批。
  4. 算完还没结束。旧结果回流、本地结果处理、KV 发送和释放各有条件；收到 output 不等于 Decode 已收全 KV，传输结束后也可能继续等待释放共识。
为什么把很多小步骤合并成这五组？

按源码中的连续顺序合并：A → 检查状态；B+C → 缓存与选批；D+E → 提交前向；F+G+H → 结果与共识；I → 转发保存。空槽不会凭空多出 forward，缺失的分组会标为“本轮跳过”。

bootstrap 的本地轮询在前、共识回流和准入在后；若强行合成一个连续时间段，会掩盖它跨轮推进的事实。因此它在第一组检查状态，在第四组推进共识。L2 ACK 检查与当前 batch 的缓存准备则合到第二组，但说明中仍区分共享队列与当前 batch。

同一张图中的 batch 进度带按生命周期区间组织，包含排队和等待，不表示持续占用 CPU/GPU。大步骤高亮依据原模型明确记录的对象和实际 release 名单；M1–M5 共同接收/准入的操作用虚线。未明确标出请求成员的通用 bootstrap / 终态轮询不会被擅自归给某个 M#，它们仍在 loop 中显示。

数据与源码边界

loop、batch 进度与高亮归属都从详细版的同一份模型派生，保留相同的示意起止时间和 M#、L#，没有重新编排执行顺序。源码固定于 SGLang 72d5c5bb73；使用 CUDA、HiRadix L2、depth=0 的完整 Prefill 成功路径。

本例 M2 / M4 有 host hit；未展开中间 chunk、L3、失败恢复、Decode 内部与级内 TP / CP。图不是 profiler trace，不能用条块长度推算吞吐或加速比；槽位占满也不必然产生空泡。查看完整假设与源码锚点。
