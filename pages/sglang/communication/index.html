为什么不能把所有箭头都理解为同一种通信？

进程间请求消息、PP 激活、组内集合通信和跨 P/D 的 KV 交接有不同对象与结果约定。只知道“跨 GPU”无法确定该调用哪个接口、等待什么完成条件。

为什么收到 Success 还要检查身份和其他参与者？

多个源 rank 可能分别负责一部分数据，同一 rank 的重复通知不能补足缺失的另一个；迟到或不匹配的元数据也不能让当前请求继续。

接收路径按参与者和请求信息核对状态，必要时等待元数据或缓存回载，再提交到 Req。bootstrap_room 是本例交接匹配使用的标识之一，不是物理地址。

读图前：术语与编号

Rank 是通信组内的参与者编号；buffer 是一段存储；stream 是 GPU 任务的有序执行队列。room 标识一次 P/D 交接，metadata index 是本地元数据槽位，二者不能混用。P 和 D 的页号分别属于各自的 KV 地址空间。

哪些操作异步推进，哪些必须等待？

PP 发送端依次提交长度、描述和张量的 isend，保留 work 与 payload；发送函数返回不等于接收完成。接收端逐项分配并调用 irecv / wait。本图选择 NCCL 默认非 CPU 阻塞 wait：CPU 可以继续投递 residual 和 forward，GPU 仍按 stream 依赖等待数据。

Collective 由两端 CPU 提交，GPU 前序任务、通信和同一 stream 的消费者保持顺序；CPU 返回后可继续主机工作。KV 的 Scheduler 入队后与传输 worker 分开推进；本例 batch_transfer_sync 同步等待的是 worker。所选普通批量路径先完成 K/V，再发末块 aux，成功后才通知终态。

Decode 的来源通知、metadata 可见、HiCache 恢复和各 D 参与者本地条件可以独立准备。HiCache → metadata → MIN → room 身份是检查次序，不是准备工作必须逐项开始的次序。异常路径中 P0/P1 各自排空，D 保留地址并轮询 ACK 或 deadline。

执行语义另核对 PyTorch v2.8.0：WorkNCCL.wait 与 NCCL stream 语义。这不是 SGLang 依赖版本声明；CPU blocking wait、其他后端或 stream 配置需另行分析。未测量实际并发率或网络包的并行度。

怎样读硬件路径、控制流与数据流？

主机外框区分同机与跨机；框内 CPU 执行 Scheduler、调用通信 API，DRAM 保存请求、描述与普通 CUDA 路径的 aux。GPU 执行模型与设备算子，HBM 保存激活和 KV。网卡负责主机与网络之间的搬运，交换机在本例只转发。

紫色虚线表示请求/控制信息或本地调用依赖；蓝、金、粉色实线分别表示 GPU 张量、KV 和 CPU aux 数据。aux 虽然包含 room、output_id 等元数据字段，仍需复制实际缓冲区内容；Success 是随后发送的状态通知。判断控制或数据用途，不能只看它是否放在 CPU 内存中。

跨机示例指定 GPUDirect RDMA 可用，GPU 载荷经 PCIe、网卡与交换机写入对端 HBM，不画成先复制到 CPU DRAM。控制信息和数据可以共用这些物理设备；颜色不表示两张独立网络，也不表示控制消息使用 RDMA。同机示例选择 NVLink / PCIe P2P，不使用外部网卡与网络交换机；机内桥接器和 NVSwitch 未展开。实际系统也可能选择其他路径，图中没有模拟回退。

先预测，再操作

NCCL 调用返回后，画面为什么仍显示“待执行”？

因为本路径把任务提交到 CUDA stream，设备仍可在处理前序任务。同一 stream 的消费者依靠执行顺序读取结果；这里没有额外插入全设备同步。

P 的 page 7 必须写到 D 的 page 7 吗？

不必。页号各属于本地池，由交接元数据给出对应关系。切换 KV 搬运的目标页布局，A/B/C 的逻辑顺序不变，但物理落点和连续传输段数改变。

两个 Success 通知一定代表两个源端完成吗？

不一定。源码按源端 rank 身份去重；同一个 rank 重复通知不能代替另一个 rank 完成。

元数据非零后，请求一定能继续吗？

HiCache 启用时，恢复门槛先于 metadata gate 与参与 rank 的 MIN 归约生效；最后还要通过 room 身份检查。用“不匹配”场景观察请求被终止，无法进入可调度队列。
