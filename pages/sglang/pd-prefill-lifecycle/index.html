从问题理解实现

在本页 PP=3 的 Prefill 案例中，每级计算并持有自己的层状态。首 token 已经生成后，这些资源可能仍被 KV 传输使用，因此需要继续跟踪请求直到各级完成本侧收尾。

隔离计算之后，资源仍有跨侧依赖

官方 PD 文档用阶段分离减少 Prefill 与 Decode 的调度干扰；这并不消除状态交接。沿本课的一个请求看，计算结束后还必须追踪源数据何时不再被传输使用，才能解释 inflight 的存在。

为什么请求已经完成 Prefill，还会留在 inflight？为什么 release 名单回来还要本地复查？

为什么请求已经完成 Prefill，还会留在 inflight？

计算完成只说明本级数值已经得到，不说明传输不再读取它。保留请求与源 KV 的关联，才能在后续轮询中识别谁仍未结束、谁可以收尾。

展开机制与具体例子

inflight 表示已经进入交接但尚未完成本侧处理的集合。沿原有 12 步分别查看计算、结果回传、传输终态名单和本地释放，不把它们压成一个“完成”事件。

取舍与条件：这样能区分持有原因，但会延长源资源占用。慢接收方或慢链路可能反过来限制 P 侧接纳新请求。这里是依赖推导，不是性能测量。

为什么 release 名单回来还要本地复查？

名单反映一轮协作收集到的状态，本地 poll 可能因传播和观察时刻不同仍未进入终态。若只按名单释放，就会忽略此刻本地尚未满足的条件。

展开机制与具体例子

所选源码对名单内请求重新检查本地 Success / Failed；仍处于中间状态的请求继续保留。传输终态名单包含失败，不能直接称为“所有请求成功”。

取舍与条件：多一道检查保留了本地状态边界；错误路径的资源处理还取决于传输协议，不能从教学正常路径推出任意故障下都可立即释放。

    接入与准入 / 02

    三级各自建 Req，进入 bootstrap 队列

    同一条 R 沿流水线传播，各级建立自己的请求对象和 KV sender。三个流水级共享请求标识，各自管理本地资源。

    PP0Req R + sender₀
    PP1Req R + sender₁
    PP2Req R + sender₂

    请求复制：PP0 → PP1 → PP2；三个本地 bootstrap_queue

    展开实现过程与调用关系

    PP0 从前端收请求；PP1、PP2 从上一级接收请求对象。每级 ingest_requests → handle_generate_request 构造本地 Req；PP loop 在本地迭代后部转发 recv_reqs。

    Prefill 模式的 _add_request_to_queue 把 R 加入 disagg_prefill_bootstrap_queue。create_sender 绑定 bootstrap_room 和 pp_rank；pending_bootstrap=True。本地 max_new_tokens 被设为 1，用于 Prefill 侧预算估算，后续长文本生成交给 Decode。

    请求状态
    每级：新建 Req → bootstrap_queue
    推进条件
    等待 Decode 侧目的 KV 索引等握手信息就绪；创建 sender 本身不代表可以计算或发送。

    展开实现过程与调用关系

    展开实现过程与调用关系

    PP1接收转发的 t₀
    PP2接收绕回的 t₀

    展开实现过程与调用关系

    CUDA 路径中，PP2 发送末级输出给 PP0；非末级转发上一轮保存的 pp_outputs，因此结果继续 PP0 → PP1 → PP2。各级接收输出，准备 GenerationBatchResult，安排必要的 D2H，并在 CPU 处理前等待 d2h_event。

    PP=3、depth=0 时环长为 3。当前前向用 mbs[mb_id]，结果处理用 mbs[(mb_id+1)%3]：两者属于不同槽位。R 不会在每次本地循环都从接入走到释放。只有单条 R 时，也需要后续空计算迭代把结果和控制消息排空。

    推进条件
    目标槽位存在、对应 output 已接收，且 D2H 事件已完成。

    process_batch_result_disagg_prefill 将 t₀ 追加到本地 req.output_ids，维护未完成请求的缓存引用，再把 R 加入 disagg_prefill_inflight_queue，随后调用 send_kv_chunk(last_chunk=True)。这是每级自己的先后关系，不要求等三级都处理完结果才一起发送。

    用状态串起这 12 步

    bootstrap_queue → waiting_queue → EXTEND batch → inflight_queue → done / 移出

    这是每个 PP rank 的本地请求轨迹。一个 Req 可以跨多个 loop 存活；batch 是某次计算的集合；slot 是循环复用的存储位置。三个 rank 上同 rid 的 Req 并不是同一个 Python 对象，也不能把 slot 释放等同于请求 KV 释放。

    主线之外，哪些地方会多走几步？

    长 prompt：Chunked Prefill 会重复哪一段？

    重复“准备下一块输入 → 三级前向 → 对应结果处理”，逐步填充同一请求的 KV。中间块维护 chunked_req / inflight_middle_chunks，并可发送已完成的 KV 范围；非最终块会将尾部不足一页的内容延后。最终块才走主线中的首 token、最终 metadata 和 inflight 收尾。不能把每个 chunk 都画成新请求，也不能假设所有 KV 都等最终块才开始传。

    前缀命中：减少的是计算还是传输？

    P 侧 prefix cache 命中缩短待算范围；D 侧已有前缀通过 bootstrap 返回，决定 start_send_idx。两者是不同位置的缓存状态。若启用 HiCache，选批前还会推进缓存事件，命中主存的 KV 需要按实现回载。本页冷缓存示例不插入 L2/L3 时间条，也不假定存在整批 H2D barrier。

    失败、取消或一直排队：从哪里定位？

    bootstrap_queue 卡住：查握手、目的索引、good/bad 共识和 metadata 容量。waiting_queue 卡住：查 PrefillAdder 预算与请求/KV 槽位。已前向却未交接：查 output 槽位、D2H 事件和本地结果处理。inflight 不下降：查 sender.poll、终态交集、release 回流与本地复查。

    bootstrap 的 bad 名单包含失败及已中止请求；传输阶段的终态交集也包含 Failed，失败进入专门清理路径。这里的共识表示允许一致收尾，不能把它当成“三个级均传输成功”。乐观 Prefill 还可能在握手完成前计算、重试或重新排队，本页关闭这一路径。
