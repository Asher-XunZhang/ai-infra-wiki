先认清一条请求经过什么

客户端把文本送到服务的 HTTP 入口。Tokenizer（分词器）把文本变成 token ID；Scheduler（调度器）组织执行；GPU 先做 Prefill，处理输入并采样首个输出 ID，再做 Decode，继续生成。Detokenizer（反分词器）把输出 ID 变回文字。图中的 IPC 是同一主机上进程之间的消息，不是跨机器传输。

本图用 R1 表示一条请求，t1 表示它的首个输出 token。SSE（Server-Sent Events）让服务把结果分块送回；一个网络块不必等于一个 token。图里先观察 t1 的文本回程，同时下一轮 Decode 可以继续。首字可见后，还要核对流尾和结束原因，才能判断这条请求怎样结束。

先播放正常场景，分别停在“客户端可见 t1”和“完整响应”处；再切换取消场景，比较取消通知返回时 GPU 是否仍在工作。总览与模块过程共用进度，展开源码注解可回查当前步骤。

发非流式，再单独检查 SSE

在 ai-infra-wiki 仓库根目录运行随课采集器。输出目录必须是新的目录；脚本保存服务身份、实际请求、原始响应、SSE 事件和本地观测时刻，不预设模型会返回哪句话。

python3 -B scripts/serving_labs.py smoke \
  --url http://127.0.0.1:30000 \
  --output runs/study-smoke-01 \
  --prompt 'The capital of France is' --max-new-tokens 8

采集器先读取 /model_info 与 /server_info，再各发一次非流式和流式 /generate。两次生成是独立请求；不把相同文本、缓存状态或耗时当作前提。浏览器不直接连接你的推理服务。

原始证据检查什么
HTTP 状态与响应体协议成功是否伴随业务错误
meta_info.id与本次请求及服务日志关联
prompt_tokens / completion_tokens实际 token 计数，不能按字数猜
finish_reason 与 SSE 结束是否完整结束、提前停止或异常
启动和同时间范围的服务日志把前端响应与后台状态对齐

例如只看见“Paris”还不能收工：这是首个非空文本；接着核对完整流尾、finish_reason 和实际计数，再用 rid 关联日志。非流式响应只能记录完整响应到达时刻，不能从中还原首 token 时间。

取消与退出，要等谁收尾？

交互中的取消场景展示：客户端通知停止时，Decode 可能仍在途；取消通知、完成标记和资源退役不能画成同一动作。随课取消探针在流式请求取得实际 rid 后发送 /abort_request，保存通知响应与流尾；通知返回本身不能证明 GPU 资源已经归还。

python3 -B scripts/serving_labs.py cancel \
  --url http://127.0.0.1:30000 \
  --output runs/study-cancel-01 --max-new-tokens 64

取消实验要使用足够长的输出预算，仍可能遇到请求先自然结束的情况。以实际 rid、通知响应和原始流尾为准；stop/length 表示正常结束条件，不能因为发过通知就改称取消成功。后台资源是否退役，另查同一请求的服务日志或资源观测。

退出时在启动服务的终端发送中断，保留退出日志并核对自有进程已退役。不要把关闭客户端当作服务退出，也不要对共享机器执行无差别进程清理。

按最早失败的位置定位

现象先检查
启动前失败解释器、实际导入来源、依赖与平台兼容
权重或 tokenizer 读取失败模型路径、完整性、revision 与访问条件
初始化 OOM权重之外的 KV 预算、执行预留和实际驻留对象
探活可用但生成失败请求协议、模型模式、日志、完整业务响应
SSE 只有部分文字流尾、业务错误、finish_reason、客户端期限和后台状态

先保留失败证据，再一次只改一项条件。最小成功只能证明所选通路走通，不能代替精度、并发、长期稳定性或性能验证。

先预测，再解释

模型加载期间探测失败，能否据此判定启动最终失败？

不能。需要结合初始化进度、进程状态和后续就绪；若已有最早异常，则从异常定位。

一次 HTTP 200 是否就是一次完整生成？

还要核对业务响应、实际输出、计数、结束原因和对应服务日志。

首输出后取消，为什么图中 GPU 仍有在途工作？

通知不会抹掉已经提交的设备执行；安全收尾仍需遵守资源使用依赖。
