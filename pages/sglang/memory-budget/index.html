为什么有空闲显存，仍然可能放不下请求？

KV Cache（键值缓存）保存注意力计算中的历史 K/V。本课先把设备可用字节换成 KV 池中的槽位，再按页与请求需求比较。分配器（allocator）管理的空闲页，是这个池里当前还能取走的部分。启动时先为执行留出空间，再把剩余预算换成 KV 槽位；运行时还要检查已持有的缓存、页边界和未来增长。

本课沿普通文本、单实例、一个 rank（本例的一张 GPU 执行分片）、未量化多头注意力（Multi-Head Attention，MHA）静态分页池建立账本。MLA、混合状态、量化元数据、多模态与投机预留需要单独计算，不直接套用本页公式。

从设备字节，算到一批请求的页需求

先沿默认数字算清供给和需求，再试两个变化：取消用户上限，或让每条已有 KV 多一个位置。每次改变条件都会回到起点并暂停。

账本单位与含义不能据此推断
加载前基线与当前可用量GiB；分别在对应采样位置获得加载前基线不一定等于显卡标称容量
运行预留与 KV 预算GiB；给执行和 KV 分别留空间预留降低不保证下一批的临时需求安全

权重、执行 buffers 和 CUDA Graph 占用要按采样时刻记账：当前可用量已经反映的驻留对象，不能再扣一次；之后才发生的捕获或峰值则需另外验证。mem_fraction_static 不是 KV 专用比例。

用同一组数，走完换算

下面固定为交互的默认参数。1 GiB = 2³⁰ bytes，1 KiB = 2¹⁰ bytes；同一个 token 位置在本 rank 的 32 层都要保存 K 和 V，所以一个槽位的成本要把这些层相加。

  1. 先算字节预算。加载前可用基线为 40 GiB；建池前当前可用 20 GiB。运行预留为 40 × (1 − 0.875) = 5 GiB，KV 预算为 20 − 5 = 15 GiB。当前已驻留的 20 GiB 已经反映在当前可用量里。
  2. 每槽位成本。4 个 KV heads × (128 个 K 元素 + 128 个 V 元素) × 32 层 × 2 bytes/元素 = 65,536 bytes/槽位，即 64 KiB/槽位。这里的 4 是本 rank 的 KV 头数，不是 query 头数。
  3. 换成容量，再受上限约束。15 GiB 可支持 245,760 槽位、1,920 页。用户上限 100,000 槽位仅允许 781 个完整页；不足一页的 32 槽位不纳入池，最终容量为 99,968 槽位。
  4. 请求需求按相反方向取整。每条已有 2,048 个 KV 位置，按后续 512 个位置规划，共 2,560 个位置。每页 128 槽位，因此每条需要 20 页；12 条共 240 页，和池的 781 页比较。
15×230 bytes65,536 bytes/槽位=245,760 槽位

容量向下取整，是为了让完整页放得进预算与用户上限；需求向上取整，是为了让每条请求所需的位置都有页可放。下面两条公式里的 P 是每页槽位数，L 是一条请求的已有 KV 与后续规划位置之和，R 是请求条数。

池页数=⌊min(字节换算槽位数,用户上限)P⌋
整批需求页数=R×⌈LP⌉

为什么每条多一个位置，会多出一整页？默认对照把已有 KV 改为 2,049，其他条件不变。每条共 2,561 个位置，20 页只有 2,560 槽位，因此必须取 21 页。每条尾页空 127 槽位；12 条共需 252 页，其中尾页空位共 1,524 槽位。不同请求的尾页不能合并后统一取整。

默认池的载荷近似是 99,968 × 64 KiB = 6.102 GiB。15 GiB 预算中其余约 8.898 GiB 没有纳入本页的 KV 池容量；它不是已经分给其他用途的内存，也不自动扩大这里列出的运行预留。这张图是预算账本，不是实际张量分配快照。

这些参数是教学值，不对应某个模型或硬件实测。规划假设各请求长度相同、无共享前缀、整个 KV 池可用于这批需求；未模拟当前池内其他占用、逐轮准入、请求行上限或提前停止。引擎运行时会逐步申请页，不会因为这份保守规划就立刻为每条占满未来长度。

运行时增量：新增三个 token，为何只需要一页？

这是独立的 P=4 小例子，不使用上面 P=128 的默认池。已有 KV 已经占有页时，本轮只从空闲页集合中取得新增页；不能再把整条请求的规划页数当作新增申请量。

下一轮再增长时，R1 和 R3 都跨页，需求又会变化。尾页空位仍属于持有该页的请求；普通分页池允许非连续空闲页，不能把页号零散直接判定成无法分配。共享、Beam、投机和分配 helper 的保守准备量需沿各自路径核对。

看到 OOM，先问发生在哪本账

启动预算不足：检查加载前基线、权重和已驻留对象、运行预留及特殊状态。已有池但准入失败：检查真正可分配页、受保护前缀和本轮需求。执行时 OOM：再检查 activation、采样、Graph 或后端临时分配；扩大 KV 池可能反而挤压这一部分空间。

把实际启动日志、模型配置、池容量和失败批次一起保存。仅凭显卡监控的一项百分比，无法区分池内缓存保留与设备层泄漏。

先预测，再解释

static fraction 从 0.875 调到 0.95，为什么不保证运行更安全？

它在此公式中缩小执行预留并扩大 KV 预算，但实际 activation、Graph 和临时需求并没有因此消失。

用户把 token 上限设得比 profiling 结果更大，会强行扩大池吗？

不会。本页先取 profiling 容量与用户上限的较小值，再按页取整；真实池还受模型与实现的其他约束。

2 条请求各需 1 个位置，每页 128 槽位，是否只需要 1 页？

本课无共享前缀，每条都要各自的一整页，因此共 2 页、256 槽位。不能把两条先合成 2 个位置，再只向上取整一次。

调大字节预算后，为什么最终池仍是 99,968 槽位？

默认的用户上限 100,000 槽位比字节预算能支持的容量更小。只要这个上限仍然生效，最终仍是 781 个完整页。使用“保持其他条件，取消用户上限”观察字节预算的作用。

能不能把 Host 空闲槽位加到 GPU 空闲槽位上，立即接纳请求？

不能。Host 副本要先经过设备分配、回载和读取依赖。继续阅读 HiCache 课。
