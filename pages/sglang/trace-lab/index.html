从“哪条最长”，走到“它在等什么”

Trace 记录事件，定位需要进一步建立调用、设备活动、依赖和请求的对应关系。CPU 范围不等于 GPU 执行时间，kernel 累计时长不等于整机墙钟，空白区间也不能单独证明设备空闲。

本页附带 PyTorch/Kineto 的历史 ResNet-50 实测训练记录片段，保留原时间戳与时长，用来练习读取真实 CPU/CUDA 事件。它不是 SGLang 或 LLM 推理跑分。采到自己的 SGLang Trace 后，可以导入同一个查看器，按原记录继续核对。

pid 标识记录中的进程，tid 标识该进程中的线程或设备执行轨道；GPU stream 是设备工作队列，不能仅凭编号理解为一张 GPU。CUDA runtime 条带记录主机发起操作的区间，kernel 条带记录设备执行区间。correlation ID 用于寻找提交候选；同名事件或靠得很近都不足以证明配对。

先点击“关联一组 CPU/GPU 事件”，比较主机调用与设备执行的起止；再定位整段最大记录空档，观察 CPU 提交与采集覆盖。点击事件、候选或统计表都会把目标移入窗口。放大只改变观察范围；窗口统计会随之重算，事件本身不会变快。

查看器保留 pid/tid 和原事件字段；时间轴只将选定片段的最早事件移为显示零点，不改写相对时间差。correlation 只能给出候选提交关系：多进程 ID 冲突、缺失或重复时，不擅自选一个作为唯一因果。

采一段自己的 SGLang 记录

先用最小部署课建立自己的实验服务，再在服务端文件系统中选一个新的可写输出目录。下面采用固定源码的普通 profiler 路径：SGLANG_PROFILE_V2=False，立即启动、非分阶段、无并发采集请求；CPU/GPU 活动，先关闭额外 shape/stack 记录。

# 服务端启动终端：先设置，再按最小部署课启动服务。
export SGLANG_PROFILE_V2=False
# 然后执行最小部署课的 sglang serve 命令；已启动的服务需在新配置下重新启动。

# 客户端，在 Wiki 根目录：路径字符串由服务进程解释。
python3 -B scripts/serving_labs.py profile-start \
  --url http://127.0.0.1:30000 \
  --server-output-dir ./profiles/study-trace-01 \
  --output runs/profile-control-01

# 另一次明确的负载：可使用 smoke 或一段短的 benchmark。
python3 -B scripts/serving_labs.py benchmark \
  --url http://127.0.0.1:30000 \
  --input scripts/serving-labs/requests.example.jsonl \
  --rate inf --concurrency 1 --output runs/profile-workload-01

python3 -B scripts/serving_labs.py profile-stop \
  --url http://127.0.0.1:30000 \
  --output runs/profile-stop-01

环境变量由服务进程读取；只在运行采集器的客户端设置它，不会改变远端服务。./profiles/study-trace-01 相对服务进程的工作目录，既不是浏览器下载目录，也不一定是 Wiki 目录。

启动控制返回不等于采样窗口已完成；停止控制返回后仍要逐 rank 核对文件存在、可解压、事件非空和身份正确。远程 URL 不会自动把服务端 Trace 下载到本机；从服务端取回对应文件后再导入。采集与导出本身会扰动执行，因此不能拿带 profiler 的吞吐直接替代无采集基准。

空档与重叠，怎样避免读错？

本页统计“窗口内被记录的 GPU 活动并集”，重叠事件只占一次墙钟；“GPU 事件累计时长”则把每条区间相加，可能大于窗口。两者都只覆盖本文件、本窗口和识别出的 GPU 事件，不是硬件利用率。

例如一个 20 ms 窗口中，两条 stream 各记录 10 ms 且完全重叠：活动并集为 10 ms，累计时长为 20 ms，另外 10 ms 只知道没有识别到 GPU 活动。若文件只有 CPU 事件，本页只能说明缺少 GPU 证据，不能给出“GPU 空闲”的诊断。

GPU 区间之间没有记录时，先检查 CPU 是否尚未提交、数据/通信/同步依赖、图捕获或 profiler 覆盖缺口。查看器可以定位这段区间，不能自动证明是哪一种原因。核对 CUDA runtime 和请求/batch 日志后再收窄假设。

跨机器的 monotonic 时钟不能直接相减。合并 rank 文件也不自动校准时间；本页保留各 pid/tid，不把看起来对齐的条带当作跨机器因果证明。需要全局时序时先建立真实时钟与消息关联证据。

先预测，再解释

两个 stream 同时各执行 10 ms，设备活动并集一定是 20 ms 吗？

不是。完全重叠时并集为 10 ms，累计区间为 20 ms；两者回答不同问题。

一个 cudaLaunchKernel 的 CPU 调用很短，能否说明对应 kernel 也很短？

不能。提交调用与设备执行分别记录，异步执行还要核对对应关系和依赖。

某个区间没有 GPU 事件，是否就能把它命名为调度器空泡？

不能。缺少活动记录也可能来自采集范围、未记录工作或其他依赖，需补充提交、同步和请求证据。
