PD Disaggregation：Prefill 与 Decode 为什么分离？

先观察共享资源，再拆成两个服务角色，并把新增的交接过程走完。

可单步操作原理与实现分开来源与教学边界

先看：Batch 调度：动态组批、连续批处理与 Chunked Prefill · AllReduce、AllGather 与数据传输：结果何时可用？

读长输入与逐步续写有不同的工作形态。在合并部署中，它们共享实例资源；分开角色可以分别安排资源，但一条请求必须把已算出的状态交给下一侧。先看这笔交换。

先想清楚：这一课解决什么问题？

长输入需要处理许多已知位置，续写则不断处理少量新位置。两种工作共用资源时可能互相影响；PD 分离尝试让它们独立配置和调度，同时引入状态交接成本。

01

为什么先考虑隔离 Prefill 与 Decode？

长 Prefill 可能占据较长一次执行，使已有请求迟迟拿不到下一段输出。分离后，可以分别安排输入处理和持续续写的资源，针对首 token 等待与输出间隔设置不同目标。

这不是说所有 Prefill 永远受算力限制、所有 Decode 永远受带宽限制；批大小、上下文、模型与硬件都会改变瓶颈。分离的收益来自具体工作负载下的资源安排。

依据：DistServe · Prefill / Decode 分离的动机

02

为什么交接 KV，而不是让 Decode 从头再读？

Prefill 已经计算出前缀的状态。如果 Decode 能接收匹配的 KV，就能在已有结果上继续；若从头重算，会重复之前的输入工作。代价是传输载荷、接收容量、请求身份匹配与调度等待。

作部署决策时，要比较一整条路径

  1. 合并部署：排队 → Prefill → 继续 Decode，状态可在当前服务组内使用。
  2. 分离部署：P 侧排队与计算 → 状态传输及 D 侧就绪 → D 侧续写。
  3. 只有减少的干扰与排队等收益足以覆盖额外交接成本，服务目标才可能改善。

这是依赖顺序，不是所有系统都严格串行执行的时延公式；实现可能重叠传输与其他工作。

依据：DistServe · Prefill / Decode 分离的动机

03

什么时候不必为了分离而分离？

低并发、短输入或传输成本占主导时，合并部署可能更简单有效。也可以先通过分块与调度减少干扰，再判断是否需要独立角色；两类手段可以组合，但兼容性需核对实现。

PD 划分的是服务阶段，两侧都需要执行各自阶段所需的模型计算。PP 划分的是模型层，两侧各承担不同层；不能把 P、D 当成模型前半段和后半段。

试着解释

把 Prefill 和 Decode 分开后，为什么仍可能变慢？

展开解释

请求增加了状态交接和目标侧就绪等成本。若减少的干扰与等待不足以抵消这些成本，端到端表现可能变差。

术语速查

实例
对外提供服务的一组运行资源；可以由一张或多张 GPU 组成。
P / D 角色
P 处理输入并产生首个输出；D 接过状态继续生成。本课两侧都覆盖完整模型。
交接
传递请求对应的 K/V、首 token 和配对信息；不是每条请求都把模型权重重新传一遍。

对照算例，回看机制与取舍

Colocated / Disaggregated Serving：资源共享与隔离

图用长输入 B 与正在续写的 A 表示两种工作。合并模式中它们进入同一个服务组；角色分离后分别进入 P 和 D。资源隔离不等于更快，增加的状态交接可能抵消收益。

KV Transfer 与 Readiness：Decode 为什么还要等待

D 需要能读取的正确 KV，以及匹配的请求信息，并通过自己的准入条件。P 发出载荷时，D 的接收区还未就绪；数据到达后也不自动等于开始执行。

PD 与 PP：服务角色分离和模型层切分

按前后模型层接力是 PP；PD 分的是输入处理与续写阶段。每个角色内部都可以再使用 TP 或 PP。第二章再进入 PP=3 的具体状态和源码。

图解 · 合并部署与 PD 分离

合并部署在同一服务组接着算；PD 分离把续写交给另一服务组，因此要交接 KV 与请求状态。

PD / PP：服务角色与模型层的分工

“同一个实例”可以由多张 GPU 组成。合并部署中，它承担 Prefill 和 Decode。PD 分离中，P 服务组和 D 服务组各自具备执行完整模型的能力，内部还可以分别使用 TP、PP 等并行方式。

直觉上像两组工人处理同一份工作：P 负责读完上下文并准备起笔，D 接过记忆继续写。交接的是当前请求的状态；模型权重在服务启动时就已加载。

PD Disaggregation：排队、状态与交接成本

展开排队、状态与成本的差异
观察点合并部署PD 分离
排队与调度P、D 工作共享实例资源，可能相互影响两侧分别排队和扩容，还要协调交接
KV 的位置本实例保存，后续原地使用需要让 D 获得可用的对应状态
第一个输出Prefill 后采样，再进入结果处理通常由 P 采样，并随交接状态让 D 继续；可见时机取决于响应路径
执行门槛仍有 KV 容量、准入和批次约束还要处理接收状态、元数据、缓存回载等条件
资源收尾本地请求与缓存生命周期管理P 的发送和 D 的接收分别有完成与释放边界
成本与收益省去跨角色交接，部署较直接可隔离负载并独立配比资源，但增加传输、协调与双侧容量成本

PD 分离并不保证每条请求都更快。输入很短、交接很慢或某侧排队很长时，额外成本可能超过收益。需要在实际流量和硬件上测量。

自测 · 把 P 部署在前 16 层、D 部署在后 16 层，是 PD 分离吗？

这是按层拆分的直觉，更接近 PP。PD 分离按 Prefill / Decode 的执行阶段分工；每个角色的服务组都要覆盖完整模型层。
