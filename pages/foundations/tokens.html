Tokenization 与 Embedding：文字怎样变成模型输入？

从你能读懂的文字开始，看清片段、编号、位置与向量是四件不同的事。

可单步操作原理与实现分开来源与教学边界

从这一课开始，不要求推理知识。

你输入的是文字，模型内部做的是数值运算。我们先不画 GPU，也不假设你已经知道 token：下面用同一句中文，逐步看它怎样变成模型能接收的输入。

先想清楚：这一课解决什么问题？

文字已经能存成 UTF-8 字节，但存储编码没有回答两个问题：模型每次处理多大的文字单位？这个单位要用什么可学习的数值表示？Tokenization 决定单位与编号，Embedding 为这些编号提供参与计算的向量。

01

已经有文字编码，为什么还要 Tokenization？

UTF-8 是一种把文字编码为字节的方式，解决的是怎样保存和还原文字。例如一个汉字通常需要多个字节；它没有规定语言模型每一步该预测一个字节、一个字，还是更长的片段。Tokenization（分词／标记化）为模型选定这套处理单位，并把输入变成有限词表中的 token ID 序列。

把整句话当成一种单位，会不断遇到词表里从未出现的新句子。把句子拆成可复用的单位，则能组合出大量未见过的表达。单位越细，覆盖新文本越容易，但同一句话通常需要更多位置；单位越大，序列可能更短，词表与罕见单位的学习负担却可能增加。

处理单位的取舍
单位选择带来的便利需要付出的代价
完整词常见词可以一个单位表示新词、词形变化和多语言会扩大词表；中文还需决定词边界
字符或字节基础单位少，更容易覆盖新文本相同文本通常变成更长序列，模型需组合更多单位理解它
子词或可变长片段常用片段合在一起，罕见内容拆开表示需要训练并固定分词规则；切分不一定符合词义或词根

依据：分词算法与词表取舍 · Hugging Face

02

子词怎样产生？看一个 BPE 合并例子

BPE（Byte Pair Encoding，字节对编码）的一类分词训练方法，从较小单位出发，反复合并训练语料中高频的相邻单位。训练后保留词表与合并规则，编码新文本时按规则切分；服务端不是每收到一句话就重新学习一套规则。

中文教学示例：给“我爱机器学习”应用已学好的合并规则

  1. 从单个汉字开始：我 · 爱 · 机 · 器 · 学 · 习（6 个单位）
  2. 按假定规则先合并“机”+“器”：我 · 爱 · 机器 · 学 · 习（5 个单位）
  3. 再合并“学”+“习”：我 · 爱 · 机器 · 学习（4 个单位）
  4. 再合并“机器”+“学习”：我 · 爱 · 机器学习；最终得到 3 个 token

这是以字符为起始单位的 BPE 教学示例，假定上述规则已从训练语料学好；这里只演示应用规则，不重新统计频率。“机器学习”能否合成一个 token 取决于实际词表与规则，并非根据词义判断。本例不是 Qwen 分词器的实测结果；字节级 BPE 的起始单位则是字节。

背景：子词为什么成为一种实用选择？

2016 年 Sennrich 等将 BPE 用于机器翻译的子词表示，针对罕见词和未见词难以处理的问题。它使词表里的较小单位能够组合表示新词。WordPiece、Unigram 等也用于构造子词词表，但训练方法不同，不能把所有分词器都称为 BPE。

字节级 BPE 可从完整的 256 种字节建立基础覆盖，再合并常见片段。一个 token 可能含多个字符，也可能只含某个字符的部分字节，因此不能把 token 数直接当作字数。

依据：分词算法与词表取舍 · Hugging Face · Sennrich 等（2016）· 子词与罕见词

03

有了 ID，为什么还需要 Embedding？

ID 只负责区分身份。假设“猫”的编号是 1、“狗”是 2，数字接近并不能说明词义接近；把整张词表重新编号、同时重排对应的表示，含义并不会因此改变。直接把 ID 当作大小参与计算，会带入编号本身没有的关系。

一种表示方式是 one-hot（独热编码）：词表有多少项，就准备多少个位置，当前 ID 对应的位置为 1，其余为 0。这能明确身份，却让所有不同单位同样不相似，而且向量可能很长。Embedding（嵌入）用一张可训练的表，把每个 ID 对应到一行较短的稠密向量（各维可以是不同的数，不再只有一个位置为 1），供后续矩阵运算使用。

从独热向量到查表：同一个操作的两种写法

教学 Embedding 表 E：4 个 ID，各有 3 个数
ID向量 E[ID]ID=1 时的权重
0[1, 0, 0]0
1[0.2, 0.8, −0.1]1 ← 选这一行
2[0, 1, 0]0
3[0, 0, 1]0
  1. 假设词表有 4 项，每项用 3 个数表示：Embedding 表 E 的形状是 4 × 3。
  2. ID = 1（编号从 0 开始），独热向量是 [0, 1, 0, 0]。
  3. [0,1,0,0] × E = E[1] = [0.2,0.8,−0.1]。实际查表直接取这一行，无需先构造巨大独热向量。

数值与词表大小均为手算假设，不是动画中的真实 token ID，也不是某个模型训练得到的权重。

依据：Embedding 查表与参数形状 · PyTorch 2.9 · 动手学深度学习 · 独热表示与词嵌入

04

这一行数从哪里来，为什么能帮助预测？

Embedding 是模型参数的一部分。训练时，模型根据上下文预测后续 token，把预测与训练目标比较，再依据预测误差调整包括 Embedding 在内的参数；训练中的梯度用于指出怎样调整才能减小误差。某些单位如果在相近的上下文里发挥相似作用，训练可能学出有用的表示关系；这不是手工给每一维命名为“动物”“颜色”等属性。

普通推理使用已经训练好的参数，不会因为当前用户输入一句话就修改 Embedding 表。同一个 ID 查到相同的初始 token 向量，随后各层结合位置和允许读取的上下文，形成不同的上下文表示。这正是下一步需要 Attention 的原因。

背景：学习表示并不依赖 BPE 才出现

2003 年 Bengio 等的神经概率语言模型已经联合学习词的分布式表示与语言概率模型；2017 年 Transformer 则使用学习到的嵌入作为后续注意力层的输入。这里列的是代表性工作：输入单位怎样选择、表示怎样学习，是相关但不同的设计问题，并不是 BPE 出现后才有 Embedding。

05

换一个分词器，为什么不能直接沿用原模型？

模型训练时已经把某些 ID 与 Embedding 表的行、输出词表的位置绑定。任意换词表或编号，会使同一个 ID 指向不同内容；即使 ID 没超出范围，也可能得到错误输入。分词器、词表、特殊 token 和模型权重需要匹配。

聊天模板还决定角色、消息边界等如何进入输入。它负责组织对话，不负责把词义写进向量。观察下方算例说明时，区分真实分词得到的 ID、图中为解释维度而设置的向量，以及未加入的聊天模板。

依据：分词算法与词表取舍 · Hugging Face

试着解释

把所有 token ID 重新编号，文字的含义会改变吗？

展开解释

如果同时重排输入 Embedding 的行、输出词表的对应位置，并保持全部相关约定一致，单纯换编号不改变表示。只换分词器、保留原模型映射则会错配。ID 用于索引，数值大小本身不表达语义。

术语速查

token
分词器采用的一个文本单位。可能是一个词、半个词、多个字，或字节片段。
词表与 ID
词表给每个单位分配编号；编号是查表用的索引，不是意思大小。
向量
一组有顺序的数。Embedding 按 token ID 取出一行向量，交给后续模型计算。

对照算例，回看机制与取舍

Tokenization：为什么不把整句话编成一个 ID？

句子的组合几乎没有尽头，不可能为每句新话都准备一行词表。拆成可以反复使用的单位，就能用有限词表拼出许多输入。拆得太细会让序列变长；每个完整词都收进去，又会扩大词表。实际模型使用与训练时匹配的分词器。

Token ID 与位置：编号相同，上下文仍可能不同

在第二个例子里，两次“学习”的 ID 相同，但一个在第 2 个位置，一个在第 4 个位置。后续模型还会结合位置信息与上下文处理它们。p1 这种符号仅表示位置，不能再标成实际 token ID。

Chat Template：聊天请求怎样包装

真实对话通常包含角色、历史消息和特殊标记。聊天模板会把这些内容组织成模型训练时约定的形式。这里为了看清分词，只编码原始句子，未添加聊天模板；也没有加载模型权重。
