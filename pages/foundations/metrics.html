一条消息含两个 token，间隔还怎么解释？

分别到达：一个消息对应一个 token；一起到达：一个消息包含两个 token

客户端可直接观察消息到达时刻；合包后，不能把包间隔直接当作每个 token 在服务端的生成间隔。

看尾部慢请求，与统计成功请求，有什么不同？

P50 / P95：定位延迟分布中的位置；成功率：分别计数成功与失败

分位数先对固定样本排序；成功率另看成功数与总请求数。失败样本如何处理要明确约定。

01

为什么要分别看 TTFT、ITL 和总时间？

从约定起点 t₀ 到首个输出 t₁ 是 TTFT。从上一项到下一项的单个间隔是 ITL。若能取得首尾输出时刻，且 N 个输出超过一个，首尾时间差除以后续间隔数就是本课的平均 TPOT。N 个点只有 N−1 个间隔。式中的 E2E 从请求发出算到末项可见。

例子在 0 ms 发出，三个输出分别在 100、140、180 ms 可见，TTFT 为 100 ms，两段 ITL 都是 40 ms，TPOT 也是 40 ms。若最后两项同包到达，可以报告包间隔；知道 token 总数时也能按所声明的客户端口径算首尾平均，但不能还原包内各 token 的时间或引擎计算间隔。

TTFT=t1−t0ITLi=ti−ti−1TPOT=tN−t1N−1E2E末项=tN−t0

依据：NVIDIA NIM Benchmarking · 计时端点和口径

02

为什么平均值会遮住问题？

先说明样本集合与分位数算法。图用 nearest-rank，把 n 个成功样本排序后向上取整选第 k 项。20 个样本取第 19 项，即 190 ms；若最慢两项变为失败，18 个成功样本会取第 18 项，即 180 ms，同时成功率降到 90%。

这个下降来自统计人群变化。比较两组配置时，需同时核对成功与失败、输入输出长度和到达负载。第三章的固定 benchmark 用线性插值算 P95，因此相同样本也可能与本课 nearest-rank 的结果不同；先对齐方法，再对齐数字。

k=⌈0.95·n⌉

03

吞吐提高了，为什么用户体验仍可能下降？

图里沿一个 10 秒窗口计数。4 条完成请求对应 0.4 请求/秒，10 个输出 token 对应 1 token/秒。两者使用相同的窗口，分子不同。基准工具还可能根据测量目标选择统计窗口内到达的输出，或只统计窗口内完成请求的输出，比较前要对齐。

Goodput 按指定服务目标计入达标工作，例如每秒完成并满足 TTFT 与 TPOT 阈值的请求数。吞吐上升而达标比例降低时，要用同一个阈值和窗口重新计数。

请求吞吐=窗口内完成请求数窗口时长输出吞吐=窗口内计入的输出 token 数窗口时长

依据：DistServe · Prefill / Decode 分离的动机 · Google SRE · 延迟、流量、错误与饱和度

Throughput：请求吞吐与 token 吞吐

请求吞吐和输出吞吐使用同一个 10 秒窗口，分别更新请求计数和 token 计数。观察窗口关闭时这两个计数的单位，避免用其中一个替代另一个。

术语速查
TTFT
从规定起点到首个输出可见的时间。测量工具的具体起点必须说明。
ITL / TPOT
ITL 关注相邻输出间隔；TPOT 通常概括首个输出之后每个后续 token 的平均时间。
吞吐与百分位
吞吐是单位时间完成的工作量；百分位描述样本分布中的位置，两者都依赖统计范围。
QPS / 输出 token 吞吐
同一统计窗口内，成功请求数 / 输出 token 总数分别除以窗口秒数。
