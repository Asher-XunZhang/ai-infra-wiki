01

为什么要分别看 TTFT、ITL 和总时间？

TTFT（Time to First Token，首 token 延迟）描述从约定起点到首个输出的等待；ITL（Inter-Token Latency，token 间延迟）描述后续输出间隔；端到端时间覆盖整条请求。一个请求开头等很久、之后很流畅，与开头很快、之后频繁停顿，是不同体验。

客户端计时还会包含网络和消息合并影响。一条消息携带多个 token 时，不能把消息间隔直接当作每个 token 的引擎计算耗时。记录指标必须写清在哪一侧、从哪个事件开始计时。

沿用本课的一条客户端时间线

  1. 请求在 0 ms 发出，输出在 100、140、180 ms 到达。
  2. 首个输出等待为 100 ms；两个后续间隔都是 40 ms；最后一个输出到达用时 180 ms。

是假设时间线。这里每次到达按一个 token 计；结束消息或连接收尾若另有延迟，需要单独说明。

02

为什么平均值会遮住问题？

少数请求等待特别久，可能被许多很快的请求稀释。除了平均值，还应观察延迟分布与分位数；例如 P99 表示样本中约 99% 的观测值不高于该水平，仍需注明样本和计算方法。

比较两个配置时，输入长度、输出长度、到达负载、并发和成功请求范围都要尽量一致。否则一次结果变化可能来自工作量变化，而不是优化本身。

依据：Google SRE · 延迟分布与服务监测

03

吞吐提高了，为什么用户体验仍可能下降？

更大的批次可能提高单位时间内完成的工作量，也可能让请求多等待。Goodput（有效吞吐）进一步关注满足指定服务目标的工作量；计算时要写清目标阈值和计数单位。

例如要求首 token 和输出间隔都达标，就不能仅凭输出 token 总数增加宣布优化成功。排队延迟、错误率和资源饱和度需要一起看；动画中的理想数字也不能替代固定负载下的测量。

依据：DistServe · Prefill / Decode 分离的动机 · Google SRE · 延迟、流量、错误与饱和度

试着解释

吞吐翻倍但 P99 延迟也翻倍，是否可以宣布优化成功？

展开解释

需要先看目标。若服务要求尾延迟达标，就必须检查新结果是否满足阈值；吞吐和延迟不能互相替代。

术语速查

TTFT
从规定起点到首个输出可见的时间。测量工具的具体起点必须说明。
ITL / TPOT
ITL 关注相邻输出间隔；TPOT 通常概括首个输出之后每个后续 token 的平均时间。
吞吐与百分位
吞吐是单位时间完成的工作量；百分位描述样本分布中的位置，两者都依赖统计范围。
QPS / 输出 token 吞吐
同一统计窗口内，成功请求数 / 输出 token 总数分别除以窗口秒数。

对照算例，回看机制与取舍

TTFT / ITL / TPOT / E2E：各自测量哪个区间

本例在 0 ms 发出，100、140、180 ms 收到三个输出。首输出等待是 100 ms，后续两个间隔都是 40 ms，TPOT 是 (180−100)/(3−1)=40 ms。只输出一个 token 时，不能用这个式子除以零。

Streaming Chunk：网络分包与 token 间隔

如果后两个 token 在 180 ms 的同一包里到达，就没有观察到它们各自的生成时刻。包间隔不能直接当作模型的逐 token 计算耗时。第二章会结合实际工具的口径进一步拆开。

P95 与失败样本：统计口径怎样影响结论

教学样本是 20 个成功请求，采用 nearest-rank：排序后第 19 个值是 P95。把最慢的一组变成失败再排除，成功样本的 P95 可以下降，但服务并没有因此更可靠。不同库的百分位插值约定可能不同。

Throughput：请求吞吐与 token 吞吐

最后一个场景固定观察 10 秒，窗口内成功完成 4 条请求，共产生 10 个输出 token。请求吞吐是 4÷10=0.4 请求/秒，输出吞吐是 10÷10=1 token/秒；不是对四条请求各自的速度求平均。本例只计成功完成请求的输出，不含输入 token；实际测量也必须写清样本和窗口约定。

最慢请求失败并被排除后，成功样本的 P95 下降，足以证明服务变好吗？
