TP、PP、DP、EP、SP 与 PCP/DCP：多卡怎样分工？

分别观察计算、模型层、请求、专家、激活和上下文怎样分工；沿数据交接理解每种方法的收益与代价。

可单步操作原理与实现分开来源与教学边界

先看：GPU 计算与访存：算力、带宽和 CUDA Graph · Attention 与 Q/K/V：模型怎样参考上下文？

先从 TP 的手算和 PP 的依赖开始，再看完整副本 DP 与专家 EP。随后比较 SP 的激活布局转换，以及 CP 在 Prefill / Decode 阶段的不同分工：PCP 切 Query 行，DCP 分散历史 KV。它们可以组合，但不是同一个开关。

先想清楚：这一课解决什么问题？

多卡可能用于装下模型、服务更多请求，或缩短某段计算。三种目标要求的分工不同；需要先决定切分哪一种对象，再判断结果之间有什么依赖和通信。

先问哪里不够

装不下权重、接不住请求、放不下长上下文，切的是不同对象。先选一个目标，只展开相关策略；这是阅读入口，不是性能排名，也不表示只能选一种。

权重 / 模型层装不下

先分清整份权重、层间流水和 MoE 专家。它们分担的对象不同，不能互相替代。

张量并行

TP
分担
单个算子的权重矩阵与计算；输入维切列、W 切行，或 W 切列后按输出列拼接。
不消失
总参数量与总乘加数；本例仍是 8 乘、4 加，权重来自同一份 W。
代价
局部结果要相加或拼接，跨卡通信；每卡只持有权重分片，激活或临时缓冲还可能复制。
边界
相邻算子的布局决定是否需要通信；TP 组可以作为更大配置的一部分。
看输入维切分 ↗看输出维切分 ↗

流水线并行

PP
分担
连续模型层；Stage 0 执行 L1–L2，Stage 1 执行 L3–L4。
不消失
单个 MB 仍要按 L1→L4 逐层经过两个 stage；两个 MB 示例合计 8 段层计算，单 MB 示例两侧各 4 段、同在第 4 格结束。
代价
激活交接、填充/排空气泡与 stage 间负载不均；两个 MB 示例两 stage 合计 12 GPU·时隙，其中 4 格是气泡；单 MB 示例两 stage 合计 8 GPU·时隙，其中 4 格为空闲。
边界
PP 是层间流水，不是 Prefill/Decode 分离；1 MB 与 2 MB 工作量不同，不能当等量性能比较；单 MB 自身仍可对照采用前后的依赖与空闲。
看两个 MB ↗看单 MB ↗

专家并行

EP
分担
MoE 层的专家参数与专家计算；token 按路由被派发到持有专家的 rank。
不消失
总专家数与 top-2 分支数；每个 token 仍只算被选中的专家，稀疏激活不是 EP 新增的。
代价
dispatch/combine 激活交换；专家参数均分不保证负载均衡（本例 4/4 与 6/2）。
边界
只适用于带 MoE 专家的模型；不切 dense 权重，也不能当成所有模型的省显存开关。
看均衡路由 ↗看热点路由 ↗

DP 不在这一组：它复制完整模型，不能解决一份模型装不下。SP 也不在这一组：它不减少权重，但可减轻 TP 组内逐 token 激活的重复保存。TP/PP/EP 可组合，但组合后的通信、气泡、负载与支持范围要按具体引擎和拓扑核对。

模型装得下，但请求多

先把目标定在并发容量，而不是单条请求延迟；DP 复制的是执行容量，不是把一条请求的矩阵拆小。

数据并行

DP
分担
不同请求；每条请求仍经过一个完整模型，图中 R1、R2 分别到两个副本。
不消失
单条请求的矩阵计算、层数与 KV 读写；每个副本都保留完整参数。
代价
本例每副本一张 GPU：1→2 个副本就是 1→2 张 GPU 和 2 份完整权重；另有每副本 KV/状态、请求路由与负载均衡。
边界
只有请求足够多、能并行或合批并被调度时，容量才可能转成吞吐；不保证单请求延迟下降。一个副本内部还可以组合 TP/PP，“副本”不等于“一张 GPU”。
看完整副本 ↗

单副本也可以 batch：图中把两条请求分到两个副本，是为了看清复制成本，不是说一个副本只能串行。两个反例：一份模型本身装不下时，DP 不能解决；单条请求算得慢时，DP 也不会拆它的矩阵。

Prefill 行多 / Decode 历史长

长上下文不是一个阶段。Prefill 的压力在 Query 行与计算，Decode 的压力在每轮读取历史 KV；下面是两个独立教学例。

Prefill 上下文并行

PCP
分担
同一条长 prompt 的 Prefill Query/token 行；连续切分或前后配对改变行的归属。
不消失
每行仍需因果范围内的历史 K/V；总因果配对数仍是 36。
代价
远端 K/V 的交换或暂存；因果遮罩造成负载不均（连续 10/26，前后配对 18/18）。
边界
本例用 AllGather 副本，不保证每卡 KV 驻留减半；配对数不是耗时或加速比。
看连续分片 ↗看前后配对 ↗

Decode 上下文并行

DCP
分担
Decode 时按上下文位置分散的历史 KV；每卡读一部分历史，再合并当前 Query 的局部 Attention。
不消失
总历史位置仍是 4；每卡读 2 个不等于总读取或总算力减半，当前 Query 仍要看全部允许历史。
代价
每步 Decode 交换局部 O 与归一化量 Z/LSE；短上下文时通信可能占主导，ITL 可能变差。
边界
必须按 Z 加权：两片局部 O 分别为 2、6，Z 分别为 2、6 时，加权结果为 5；两片 Z 分别为 2、2（局部 O 仍为 2、6）时，结果为 4。局部平均只在 Z 相等时碰巧正确。
看不等权 ↗看等权 ↗

不是二选一：PCP 与 DCP 是不同阶段的分工；8 个 Query 位置与 4 个历史位置是两个独立例子，不拿两图数值做速度比较。它们也不等于 TP/PP：TP 切算子，PP 切层。与切块的关系：Chunked Prefill 是按轮分段时间切块，不是 PCP/DCP 的卡间分工；可以组合，但支持范围要另核。

逐 token 激活占用（SP）

长上下文除了历史 KV，逐 token 区域的激活也会随序列长度增加。经典 SP 在 TP 组内沿序列切分这部分激活，减少每张卡的重复副本；它不改变历史 KV 的分片方式，也不等于全程显存减半。

经典序列并行

SP
分担
同一 TP 组内、逐 token 区域的序列行；长序列时每卡只保留本地行，减少这部分激活的重复副本。本例每卡完整行由 4 变为 2。
不消失
不新增 GPU；不改变总 KV、完整 Attention 上下文、模型权重与总计算。激活分片本身仍占空间，只是不再每卡复制整段。
代价
进入 TP 区域前 AllGather，离开时 ReduceScatter；总通信取决于实现与原 TP collective，不能笼统写成固定新增两次。
边界
这是 Megatron 经典 SP 的教学布局，不声称是某引擎的通用开关；它不替代 PCP/DCP 对历史 KV 与 Attention 上下文的分工，也不把激活分片等同于 KV 分片。
看 TP+SP 布局 ↗

SP 通常与 TP 一起出现，也可放进更大的 PP/DP 配置；实际支持范围按引擎与拓扑核对。它减轻的是 TP 组内逐 token 激活的重复保存，不减总 KV，也不代表全程显存减半。

Decode 阶段 · 另一个例子

DCP 不把一个新 Q 切成 Prefill chunk

Decode 时，同一个新 Q 读取按上下文位置分片的历史 K/V；各片得到局部 O 与 Z，再按 Z 合并。它不在这张 Prefill 的轮次轴上，也不把新 Q 逐块 Prefill。

TP / PP / DP / EP / SP / PCP / DCP 采用前后速览

固定同一输入、模型和工作量；下表只列核心差异，下面的动态图把对象、资源和时间关系展开。乘积项、层数、行数、配对数、位置数与教学时隙都是计数，不是实测性能。

同一算例的七项对照
机制未采用采用后代价与边界
TP1 张 GPU；W 有 4 个权重格；8 个乘积项、4 次加法，得到 Y=XW。2 张 GPU；每卡 2 个权重格、4 个乘积项。切输入维时每格只有 1 个乘积，每卡 0 次局部加法，合并再加 4 次；切输出维时每格 2 乘 1 加，每卡 2 次局部加法，合并只按列拼接。两侧系统都仍是 8 乘、4 加；权重来自同一份 W；合并与通信是新增成本，不折算成实测加速。
PP1 张 GPU 保存 4 层；两个 MB 共 8 段层计算，用 8 个教学时隙。2 张 GPU，每卡保存 2 层；同样 8 段层计算，第 6 格完成；2 张卡合计 12 个 GPU·时隙，其中 4 格是填充/排空。同一 MB 仍须逐层经过两个 stage；两侧横轴使用同一时隙刻度；时隙等长只表示依赖和重叠，不是实测耗时。
DP1 份完整模型；1 条共享执行路径；两请求可同批或先后进入；每请求仍做 2 层计算。2 份完整模型；2 条独立执行路径；每请求仍做 2 层计算，输出仍分别对应。参数存储从 2 个层块变为 4 个；单请求计算不减少；吞吐是否增加取决于请求量、合批与调度。
EP1 张 GPU 保存 4 个专家；4 个 token 各选 2 个专家，8 个专家分支都在本卡。均衡路由 t1 选中 E0/E2，输出 3。2 张 GPU，每卡 2 个专家；总专家、top-2 与每个路由条件内的 t1 输出不变。均衡路由 t1 仍为 3；热点路由改选 E0/E1，t1 输出 2.5。均衡时两 rank 各 4 次激活；热点时 6 / 2。跨卡分支要 dispatch 激活并 combine 返回；两种路由本例都合计 4 次跨卡派发/返回，但来源不同。参数 2/2 均分不保证计算均衡；MoE 的稀疏激活收益不是 EP 独有。
SP同一 TP 组 2 张 GPU；逐 token 区域每卡复制 p1…p4 共 4 行。TP+SP 仍是同一 2 张 GPU；每卡 2 行（p1/p2 与 p3/p4），经 AllGather 进入 TP 区域，再由 ReduceScatter 回到分片。不新增卡；总通信取决于实现和原 TP collective，不能笼统写成新增两次；不改变 KV 总量或完整 Attention 上下文。
PCP1 张 GPU 负责 Q1…Q8；Qi 允许 i 个配对，1+…+8 = 36 对。2 张 GPU；连续切分 10 / 26，前后配对 18 / 18，总数仍 36；Query 行归属改变。每行仍需因果范围内的历史 K/V；本例 AllGather 副本，不保证每卡 KV 驻留减半；配对数不是耗时或加速比。
DCP1 张 GPU 读取 p1…p4；不等权分支 exp=[1,1,3,3]、Z=8，结果为 5；等权分支 exp=[1,1,1,1]、Z=4，结果为 4。2 张 GPU 各读 2 个位置；不等权分支 Z=2/6、局部 O=2/6，按 Z 加权合并为 5；等权分支 Z=2/2、局部 O=2/6，合并为 4。每步 Decode 交换一轮 O/Z。局部平均只在 Z 相等时碰巧等于加权结果；不等权时局部平均为 4，不是正确答案 5。Z=2/6 只属于不等权分支，不能与等权的 Z=2/2 混用；每步新增局部结果与统计量通信，4→2 是读取位置数。

PP 还保留单 MB 分支：单 MB 示例两侧各 4 段层计算、同在第 4 格结束，两 stage 合计 8 GPU·时隙，其中 4 格为空闲；1 MB 与 2 MB 工作量不同，不能当等量性能比较，但单 MB 自身仍可对照采用前后的依赖与空闲。DP 的单副本也可 batch，图中不把单实例画成只能串行。EP 的 4/4 与 6/2 是 rank 激活负载，不是参数量；热点改变路由与 t1 结果，但同一路由条件内采用前后输出相同。SP 不新增 GPU；经典 SP 减轻 TP 组内逐 token 激活副本，但不改变总 KV，也不把激活分片等同于 KV 分片。PCP 的单卡基线并入同一面板，连续/前后配对仍可选。DCP 的 5 与 4 分属不等权与等权分支，Z=2/6 与 Z=2/2 也按分支区分，不混用结果。

为什么卡更多，单条请求不一定更快？

拆分后每个参与者可能少算一些，但还要传输张量、等待依赖并承担负载不均。以两张卡分摊工作为例，理想计算时间减半只是一个组成部分，通信和等待并不会自动减半。

因此比较方案要同时固定工作量、模型、硬件和服务目标。DP 常用于增加同时处理请求的能力；PP 的填充、排空气泡与 TP 的通信成本不同；PCP/DCP 的收益也取决于上下文长度。具体优势与代价在各策略下并列保留。

术语速查

术语速查 · 英文全称与含义
TP：张量并行
把某个计算及其参数拆开，多卡共同完成。局部结果可能需要拼接或求和。
PP：流水线并行
把模型层划分到依次执行的流水线阶段（PP stage）；后一个 stage 必须等待前一个 stage 的激活（activation，中间特征张量）。本例 Stage 0 执行 L1–L2，Stage 1 执行 L3–L4。
DP：数据并行
本例指多个完整模型副本分担不同请求；每个副本内部仍可由多卡组成。
Microbatch：微批次
MB1 / MB2 中的 MB 指 microbatch。它是一次送入流水线的工作单元，可含多条请求。本例 MB1={R1,R2}、MB2={R3,R4}；两者都经过相同的两个 stage。实际 batch 如何形成由引擎调度决定。
Stage 与 rank
Stage 是模型层的执行分工；rank 是进程在某个通信组中的编号。本例一个 stage 对应一张 GPU，这不是两种术语的通用定义。
Pipeline bubble：流水线气泡
某 stage 因等待激活或没有后续微批次而出现的空闲时隙。不是一次有效计算，也不能仅凭图中空格推算真实吞吐。
EP（Expert Parallelism）
专家并行：把 MoE 专家参数和计算分到不同 rank，按路由派发 token 激活并合并结果。
SP（Sequence Parallelism）
本课采用 Megatron 经典定义：LayerNorm 等逐 token 区域的激活沿序列切分，通过 AllGather / ReduceScatter 与 TP 计算区域转换。
CP（Context Parallelism）
上下文并行：沿同一请求的上下文位置分工，必须解决 Attention 对其他分片历史的依赖。
PCP（Prefill Context Parallelism）
预填充上下文并行：把长 prompt 的 Query/token 行分给多个 rank；每行仍需访问因果范围内的 K/V。
DCP（Decode Context Parallelism）
解码上下文并行：把历史 KV 按上下文位置分散存放，再合并当前 Query 在各分片上的 Attention 结果。
LSE（Log-Sum-Exp）
分数指数之和的对数；用于数值稳定地合并局部 Attention 归一化量。本例用 Z=exp(LSE) 帮助手算。

展开机制细节与完整说明

Tensor Parallelism（TP）：拆分计算与合并贡献

同一矩阵乘法可沿输入维拆分，再把局部贡献逐元素求和；也可沿输出维拆分，按位置拼接输出。动画用同一个 W 和 X 对照两种做法，采用 Y=XW，结果均为 [[4,6],[10,12]]。实际网络可在相邻算子之间保持分片，通信方式取决于布局。

PP · 沿模型层安排流水线

回到速览 ↑

不同 stage 处理不同层；同一微批次保持层间依赖。

怎样分
Stage 0 执行 L1/L2，Stage 1 执行 L3/L4；MB1、MB2 是两份工作单元。
代价与边界
激活就绪后下游才可计算；填充、排空和通信会留下气泡。
展开机制细节与完整说明

Pipeline Parallelism（PP）：微批次与流水线气泡

PP Stage 1没有收到激活前不能计算。先让 MB1 走过两级，再加入 MB2：Stage 0做 MB2 时，Stage 1可以做 MB1。图中填充和排空仍存在，同一个批次的依赖没有消失。

Activation Transfer：激活怎样跨进程和设备

本例每个 PP stage 由独立进程驱动一张 GPU。相邻 stage 传递微批次的激活张量：同机两卡跨越进程与设备边界；跨机两卡还需经过主机间互联。图中的部署选项只改变位置示意，教学时隙未计真实通信耗时。具体传输与完成条件见通信课程。

DP · 不同请求使用完整副本

回到速览 ↑

每条请求经过一个完整模型，两条回答分别返回。

收益
让多个副本同时服务不同请求；各副本也可组合 TP / PP。
代价与边界
需要复制模型参数和请求状态；单条请求不会因此自动变快。
展开机制细节与完整说明

Data Parallelism（DP）：完整副本分担不同请求

推理 DP 用完整模型副本分别服务 R1、R2。它增加同时处理请求的容量，也复制模型参数和各请求的状态；单条请求不因此自动变快。副本内部可以组合 TP / PP，不能把一个副本等同于一张 GPU。

EP · 按 Router 结果选择专家

回到速览 ↑

先看 token–专家路由表，再追踪派发、计算和加权合并。

收益
分散专家参数和计算，扩大可用专家容量。
代价与边界
Dispatch / Combine 需要交换激活；专家参数均匀放置不保证路由负载均匀。
展开机制细节与完整说明

Expert / Context Parallelism（EP / CP）：专家与上下文分工

EP 分的是 MoE 层里的专家工作，先由路由为 token 选专家；CP 分的是上下文相关计算。它们不是普通请求副本。第二章保留独立算例，不能把所有并行参数简单相乘当成卡数。

EP：专家放置、路由与负载

EP 分散专家参数和计算，让稀疏 MoE 能使用更多专家容量；每个 token 只访问路由选中的部分专家。Dispatch / Combine 带来激活交换，热点专家可能使某些 rank 忙而其他 rank 等待。共享专家、专家内部 TP、容量限制与具体 dispatcher 不在本例展开。

SP · 逐 token 区域保留序列分片

回到速览 ↑

本课采用 Megatron 经典 SP 定义，重点是激活布局。

SP 与 TP
逐 token 区域按行分片；AllGather / ReduceScatter 负责与 TP 区域衔接。
SP 与 CP
CP 还要解决 Attention 对远端历史 K/V 的依赖；同样切序列，不代表范围相同。
展开机制细节与完整说明

SP 与 CP：同样沿序列切分，范围不同

本课的 SP 是 Megatron 经典序列并行：逐 token 算子区域保持激活分片，进入 TP 区域前 AllGather，离开时 ReduceScatter。CP 则让 Attention 本身跨上下文分工，各 rank 必须处理其他分片的 K/V 依赖。两者可组合；SP 名称在其他项目中可能用于更广的序列并行方案，阅读实现时应先核对定义。

PCP · 分担长输入的 Prefill

回到速览 ↑

多卡计算同一条长输入；每行仍需读取其允许范围内的历史。

可能的收益
分担 Prefill 计算与激活压力，在合适模型、后端和拓扑下降低 TTFT（首 token 延迟）。
必须支付的代价
交换 K/V，并可能暂存远端副本；因果遮罩会造成负载不均。
何时值得尝试
长输入的计算压力明显时；短输入或通信主导时，多卡可能更慢。
动画里的证据
连续切分为 10 / 26 个因果配对，前后配对为 18 / 18；这是计数，不是实测耗时。
展开机制细节与完整说明

PCP 的收益：让一条长 prompt 同时使用多个 rank

长输入的许多 Query 行可分配到不同 rank，在合适模型、后端和拓扑上减轻单 rank 的 Prefill 工作与激活压力，可能降低长请求的 TTFT。动画中的连续切分需要 10 / 26 个因果配对；前后配对后为 18 / 18。配对数仅说明不均匀的来源，不是 GPU 实测成本。

PCP 的代价：通信、临时存储与负载不均

各 Query 仍须访问完整的允许历史。AllGather 方案传输并暂存其他 rank 的 K/V；ring 等分块方案降低某些临时峰值，但需要更多阶段与协调。因果遮罩、短输入、padding、前缀命中、并行组合和网络都可能影响收益。PCP 不保证所有实现都降低每卡 KV 占用；短输入或通信主导时，多卡可能更慢。

DCP · 分散长历史的保存与读取

回到速览 ↑

同一个 Decode Query 在多份历史 KV 上计算，最后正确归一化。

可能的收益
减少每卡历史 KV 的保存和读取量，或减少某些 TP 布局的 KV 重复。
必须支付的代价
每轮交换局部结果及归一化统计量；短上下文时可能增大 ITL（相邻输出 token 间隔）。
何时值得尝试
长历史的缓存或读取压力明显时；仍需核对 KV head、TP 布局、batch 与注意力后端。
动画里的证据
局部输出 2、6，对应 Z=2、6：全局输出是 5。必须按 Z 加权，简单平均会得到 4。
展开机制细节与完整说明

DCP 的收益：分散长历史 KV 的保存与读取

普通 Decode 每条请求通常只有一个新 Query，但要读取很长的历史。DCP 把 KV 的上下文位置分散到不同 rank，可减少每卡这部分缓存与读取量，或减少某些 TP 布局的 KV 重复。收益取决于序列长度、KV head 数、TP 布局、batch 和注意力后端；它不自动切分全部模型权重或剩余层计算。

DCP 的代价：每轮通信与正确归一化

各片得到局部 O 与 LSE 后仍须通信并合并；普通 Decode 每轮都支付这类开销，可能增大短上下文的 ITL。示例两片的局部输出为 2、6，归一化量为 2、6，正确全局结果是 5；直接平均得到 4。数值稳定的 LSE 合并、分片页管理、拓扑和后端支持共同决定可用性，不能只看显存节省。

与 Chunked Prefill 的关系

回到速览 ↑

PCP / DCP 讨论多卡如何分工；Chunked Prefill 讨论输入何时分轮计算。

组合边界
空间分工与时间切块可以组合，实际支持范围取决于引擎版本与后端。
展开机制细节与完整说明

PCP / DCP / Chunked Prefill：空间分工与时间切块

PCP 在 Prefill 阶段沿上下文分工；DCP 在 Decode 阶段分散历史 KV 并合并 Attention；Chunked Prefill 把输入分到多个调度轮次。前两者描述多个 rank 如何协作，后者描述何时计算多少位置；可组合，但兼容性必须核对具体引擎版本。
