KV Cache 与前缀复用：为什么保存历史 K/V？

先看哪里在重复算，再看缓存怎样节省这部分工作，以及怎样占用内存。

可单步操作原理与实现分开来源与教学边界

先看：Attention 与 Q/K/V：模型怎样参考上下文？

第二轮续写时，前面的输入还在。对本课的因果 Transformer，历史位置在同一层的 K/V 可以继续使用。先切换“每轮重算”和“保存历史”，再观察缓存从空到写入；不要从“命中几个”开始猜。

先想清楚：这一课解决什么问题？

续写时每轮只增加少量新内容，却反复需要相同历史。KV Cache 用额外存储换取少做历史计算；关键不只是“保存”，而是确认保存的中间结果在下一轮仍然有效。

理解设计核心摘要观察过程术语速查算例与取舍来源

核心算例：分页分配与前缀共享

下面的数值与主动画、动态对照使用同一组教学假设；不展开脚本也能读完。先看 3 个新位置怎样进入一个已有旧页的池，再看两个请求的共同前缀怎样变成一份对象加两个引用。

同一个 8 页池：3 个新位置怎样落位

池子固定为 8 个物理页 × 每页 2 个位置 = 16 个位置。起始时 6 个旧页各有 2 个有效位置，共 12 个；这 6 页仍归已有请求。页 1、页 4 尚未分配，是仅有的 2 个可分配页。新请求需要 p1、p2、p3 三个位置。

连续预留与按需分页使用同一个池、同一组需求
观察点连续 3 槽按需分页
起始状态有效位置 12；6 个旧页归已有请求；页 1、页 4 可分配；总空闲 4 槽，但两个空闲页各只有 2 槽，没有跨页的 3 个连续槽。
放置规则要求 3 个相邻空槽；最大连续空槽只有 2，因此放不下，3 个新位置都没有写入。逻辑页 0 的 p1、p2 映射到物理页 4 的槽 0、1；逻辑页 1 的 p3 映射到物理页 1 的槽 0。2 个逻辑页映射到 2 个物理页。
地址记录没有合法的连续区间。2 条页表映射；另有 3 行逐 token 地址演算，不是 3 条页表项。
结果仍为 12 个有效位置、已分配容量 12、可分配页 2；新请求未放入。有效位置 15（12 旧 + 3 新）；已分配容量 16；可分配页 0；末页余量 1。

3 行地址演算：p1 → 逻辑页 0 → 物理页 4 槽 0；p2 → 逻辑页 0 → 物理页 4 槽 1；p3 → 逻辑页 1 → 物理页 1 槽 0。末页余量 1 指页 1 的槽 1 仍空着；它属于新请求的末页，不是池里还可分配的页。1 个余量不等于 1 个可分配页。

所有权不能合并成一句话：分页后 8 个物理页都有归属，但不能说全部 8 页都属于新请求。6 个旧页仍归已有请求，只有原来的 2 个空闲页（页 4、页 1）被新请求使用。

两个请求共享共同前缀：6 → 3，总 10 → 7

R1、R2 都从共同前缀 p1 p2 p3 开始；之后分别接自己的后缀 a1 a2 与 b1 b2。未共享时两个请求各保存一份前缀；共享后前缀只保存一份，由两个请求引用，后缀仍各自独立。

共同前缀与独立后缀的位置数
对象未共享 · 各存一份共享 · 1 份前缀 + 2 引用
共同前缀 p1 p2 p32 × 3 = 6 个位置1 × 3 = 3 个位置，refs 2
独立后缀a1 a2 与 b1 b2，共 4 个位置仍是 a1 a2 与 b1 b2，共 4 个位置，不合并
总位置6 + 4 = 103 + 4 = 7；省下 3 个前缀位置

复用条件：token 前缀、模型与权重、影响计算的配置/状态都要匹配；任一项不匹配就不共享，回到各自保存。后缀相同或语义相近，不能代替前缀匹配。

引用与驱逐：R1 持有 → R2 接入，refs 从 1 到 2 → R1 结束，refs 回到 1 → R2 结束，refs 为 0。refs 0 只表示没有活跃请求，不等于立即驱逐；缓存仍可按策略保留，驱逐是另一个条件。共享的是前缀对象，不是后缀；R1 先结束也不会提前释放 R2 仍在用的前缀。

这两组数字是容量与位置计数，不是速度、吞吐或显存占用实测；分页的代价是额外页表与不连续访问，共享的代价是引用管理与兼容检查。

理解设计：为什么需要这些机制？

为什么旧 K/V 可以复用，新的 Query 还要重算？缓存省掉什么，又增加了什么？为什么还需要分页和前缀复用？
01

为什么旧 K/V 可以复用，新的 Query 还要重算？

在固定参数、固定前缀的因果 Transformer 中，旧位置不能读取未来 token。新增一个位置不会改变旧位置原先的各层表示，因此它们已经算出的 K/V 也不变，可以保存下来供新位置使用。

新位置的 Query 要与历史 K 匹配并加权组合历史 V。旧 Query 解决的是旧位置的问题，不能代替这个新查询；通常也无需重新生成旧位置的输出。

02

缓存省掉什么，又增加了什么？

缓存省掉重复计算历史 K/V 的工作，却仍需保存并读取历史信息。上下文增长、同时运行的请求增多，通常会增加缓存占用；即使完全命中历史，新的 Attention 和其他层计算仍然要执行。

模型权重是服务许多请求时共用的参数；KV 是由特定输入计算出的状态。二者都可能位于显存，但不能把“装得下权重”当成“还能接任意多长的请求”。

用动画里的位置数对照

  1. 4 个输入位置，再续写两轮：不保留历史时，K/V 位置计算量为 4+5+6=15。
  2. 保留历史时，只需 4+1+1=6；同时需要存放已经得到的历史 K/V。

这里只统计 K/V 对应的位置数，不是全部运算量，更不是 2.5 倍的实测加速。

03

为什么还需要分页和前缀复用？

请求长度事先不确定，为每条请求预留最大连续空间会浪费容量。分页管理把逻辑位置映射到可分配的物理块，让存储按需增长；分配地址与写入可用数据仍是两个动作。

多请求的相同前缀可能复用已经计算的状态，但相同单词出现在不同前文后面并不等价。需要匹配 token 前缀、模型与影响计算的配置，并满足具体引擎的隔离和缓存规则。共享块还有引用与驱逐策略，结束一条请求不一定立即回收它。

试着解释

只改变 prompt 的第一个 token，后面的旧 KV 都能继续使用吗？

展开解释

不能仅凭后面的 token 相同就复用。因果模型的后续表示可能依赖改变了的前文；要重新核对仍然完全匹配的前缀及相关配置。

术语速查

KV Cache
保存已经计算过的历史 K/V。当前 token 仍需计算 Q/K/V，并读取所需历史。
页与槽位
把池内存储按固定数量的位置分组便于管理；地址映射告诉请求的数据放在哪里。页不是一个汉字。
前缀复用
另一个请求在状态兼容、前缀 token 匹配时，可复用已有历史计算；不是复用一段现成回答。

对照算例，回看机制与取舍

KV Cache：省掉哪些历史计算

四个输入位置后继续两轮，本课只统计新计算 K/V 的位置数：每轮重算是 4+5+6，保存历史是 4+1+1。这个比值不是推理加速比；注意力仍要访问历史，其他模型计算也没有消失。

KV Allocation：先分配位置，再写入数值

分页场景从空池开始：先取得一页，再将两个位置的 K/V 写进去；写第三个位置时，再领下一页。图把位置分配与数据写入分开。真实实现中的页大小、对齐和池布局以各实现课为准。

Prefix Sharing：共享前缀与资源回收

同一个共享前缀只占一份物理空间，两个请求分别持有它。R1 结束，R2 仍要读取；R2 结束后，缓存也可能先保留它，直到驱逐才归还池内位置。不能看到请求结束就断言显存立刻下降。

R1 结束，但 R2 仍引用共享前缀，此时能把那份 K/V 当作空闲空间覆盖吗？

自测与解释：R1 结束，但 R2 仍引用共享前缀，此时能把那份 K/V 当作空闲空间覆盖吗？

共享场景中，R1 的连线消失后，R2 的连线仍在；必须保留它仍持有的数据。

Layer-wise KV Cache：同一 token 在不同层的状态

KV 缓存省去历史位置的重复计算；它不是已经写好的答案，也不是模型权重。

Layer-wise KV：每层分别保存历史状态

每层根据自己的输入计算 K/V，后续 token 在这一层读取这一层的历史 KV。hidden states 是本轮逐层传递的中间结果，权重是模型参数，KV 则随上下文增长，三者的内容与生命周期都不同。

前缀复用要求 token 前缀匹配且状态兼容、可用；不是语义相似就能命中。下图假定请求有 8 个输入位置，匹配的前缀已经在可用的设备缓存中。

Decode Attention：长上下文怎样增加 KV 读取

虽然普通 Decode 每轮只有一个新位置，它仍需在每一层使用历史 KV。对稠密 attention 而言，历史越长，访问的数据通常越多。“每轮输入一个 token”不等于“每轮工作量与上下文无关”。

请求结束后可以释放请求占有的资源，也可以把可复用前缀交由缓存管理器保留。缓存保留不意味着这条请求还在 Decode；未来复用也可能需要回载或重新准入。

自测 · 两个 prompt 意思一样，就能直接共用 KV 吗？

不能这样推断。这里讨论的是匹配的 token 前缀和兼容的模型状态；措辞变化或前缀不同可能改变各层计算结果。
