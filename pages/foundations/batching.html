短请求结束后，空出来的位置怎么办？

固定批次：本批全部完成后才接下一批；连续批处理：每轮边界补入等待中的请求

相同请求：A 需 2 轮、B 需 4 轮、C 需 2 轮，容量为 2。格子表示生成轮次，不表示等长耗时。

长输入处理时，已有请求何时能继续生成？

整段 Prefill：先处理完整输入，再执行 Decode；Chunked Prefill：把输入分段，允许 Decode 穿插

同一组工作：4 段 Prefill 与 4 轮 Decode。分块提供交错机会；具体分配取决于调度与资源预算。

凑一批之前，愿意额外等多久？

不额外等：每条到达后立即发出；最多等 3：部分请求合批；最多等 5：第三条到达时凑满

A、B、C 分别在 0、2、4 到达，批容量 3；达到容量或等待上限即发出。这里仅比较入批等待。

01

为什么一起算可能比逐条算更高效？

同一批请求使用同一套模型权重，形状合适时可以让读入的数据服务更多输入并提供更多并行工作。等更大的批要付出排队时间，设备已经饱和时也未必还有同样的收益。

动态组批在执行前决定「何时发出这一批」。连续批处理在一次迭代之后决定「完成的成员何时退出，谁能加入下一轮」。还有第三个约束是准入。即使有空位，新的工作也需要满足 token 预算、KV 容量和调度规则。

依据：GPU 计算与带宽 · NVIDIA · Orca · 迭代级调度

02

多等一会儿的代价由谁承担？

先到的请求要承担凑批等待。低流量时可能一直凑不满，所以调度器需要等待上限；高流量时队列里本来就有足够请求，未必还需要主动等待。组批还需满足兼容性、内存和执行容量，不能只看队列里有几条。

观察同一到达序列，比较三档等待上限（0 / 3 / 5）

  1. A 在 t=0 到达，B 在 t=2 到达，C 在 t=4 到达，容量为 3。
  2. 等待上限为 0：A、B、C 分别在 t=0、2、4 发出，各等 0 个时间单位，共 3 批。
  3. 等待上限为 3：AB 在 t=3 发出（A 等 3、B 等 1），C 在 t=7 单独发出（等 3），共 2 批。
  4. 等待上限为 5：ABC 在 t=4 凑满发出（A 等 4、B 等 2、C 等 0），共 1 批。
Wi=t发出−t到达

等待时间从各请求的到达时刻算到所属批次发出，省略执行和资源竞争。等待上限从当前批最早到达者起算。

依据：Triton · 最大排队等待

连续补位后，为什么还需要 Chunked Prefill？

连续补位后，一轮很大的 Prefill 仍可能让同一执行资源上的 Decode 等待。把长输入切块后，调度器可以在轮次边界重新选择工作，在允许的条件下给续写留出执行机会。块间还要保留已处理部分的状态。

本课固定 A 的 8 次 Decode 和 B 的 8 个输入位置，只改变 B 的 chunk 大小。块小通常提供更多让出机会，却可能增加调度轮次。实际延迟还由每轮安排、设备耗时和资源竞争决定。

术语速查
请求与 batch
请求是一次服务任务；batch 是一次一起执行的工作集合。一次图片分类可用一次调用完成；文字生成通常需要多轮调用。
动态组批（Dynamic Batching）
本课专指执行前聚合已到达的兼容请求。可以设置有限等待，也可以不额外等待；它没有单独规定多轮生成中怎样换成员。
固定批次对照
在本课生成例子中，整批请求全部结束后才接下一批；完成的请求留下空位，不再生成 token。
连续批处理
在轮次边界更新成员，让完成的请求离开，让符合条件的请求加入。
Chunked Prefill
把长输入待计算的位置拆到多个轮次；每块是部分输入，不是一块完整回答。

模型执行的是一批工作。调度器决定谁进入这一批、做多少、何时轮到下一次。

Batch 与 Continuous Batching：请求怎样共享执行

Batch 是一次合起来执行的工作；Continuous Batching 允许批次成员随轮次变化，完成的请求离开，可接纳的新请求加入。Chunked Prefill 把长输入的待处理部分分到多轮，给其他请求留下交错机会。

下面选取合并部署中允许 mixed chunk 的教学场景：A 已经在 Decode；B 带着 8 个新输入位置到达。每轮给 A 一个 Decode 位置，再给 B 一个 Prefill chunk。这个固定策略用来解释机制，不复现 SGLang 的全部预算与优先级。

TTFT / ITL / TPOT：首字等待与后续生成速度

TTFT（Time To First Token）是请求发出到首个输出可见的时间；ITL（Inter-Token Latency）观察相邻输出的间隔。常用的平均 TPOT 把首 token 之后的时间除以后续输出 token 数。它们反映的问题不同。

自测 · 把 chunk 调得更小，一定能同时降低 TTFT 和 ITL 吗？

不能。小 chunk 增加交错机会，也增加执行轮数与调度开销；B 的 Prefill 完成可能更晚。真实延迟还取决于负载、预算、kernel 效率和服务策略。
