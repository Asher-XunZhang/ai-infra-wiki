Speculative Decoding：草稿候选怎样验证和接受？

在普通逐 token 生成之上，增加候选、验证和回退。

可单步操作原理与实现分开来源与教学边界

先看：自回归生成：Prefill 与 Decode 怎样接续？ · KV Cache 与前缀复用：为什么保存历史 K/V？

先回想普通生成：已有内容决定下一 token。投机方法尝试先提出多个候选，再由目标模型验证。下面用单链、贪心规则，追踪候选怎样变成正式输出。

先想清楚：这一课解决什么问题？

普通生成要等待本轮结果才能选下一 token。投机解码先用较便宜的方法猜出一小段，再让目标模型检查；目的是让一次较昂贵的目标调用有机会确认多个输出。

理解设计：为什么需要这些机制？

01

未来未知，为什么验证时又能一起算？

草稿不是已确认答案，但它已经提供了候选输入序列。目标模型可以对这些已知候选位置组织一次因果计算，得到各位置对应的条件分布；这和逐步凭空确定未知未来不同。

验证结果仍依赖候选前缀。贪心例中遇到第一处分歧之后，后续列是在错误候选条件下算出的，必须停止连续接受，使用正确前缀继续。

02

怎样在减少调用时保持目标模型的输出规则？

本课动画采用贪心规则，逐位置检查候选是否与目标选择相同。随机采样要保持目标分布，则需要相应的接受概率和拒绝后的修正采样，不能直接套用“候选等于最高分就接受”。

例如标准投机采样先从草稿分布 q 抽出候选 x，再以 min(1, p(x)/q(x)) 的概率接受；p(x) 是目标模型对同一候选、同一前缀的概率。拒绝后要从 max(0, p−q) 归一化得到的修正分布采样。严格的分布保持结论依赖完整算法条件，不代表任意草稿验证方案都等价。

依据：Leviathan 等 · 算法 1 与概率修正

03

为什么接受率高也不等于一定快？

还要支付草稿生成、目标验证和状态整理的成本。一次验证接受的 token 越多，越可能摊薄目标调用开销；但草稿太贵、验证过长或目标执行本来已很高效时，收益会缩小。

因此既要观察连续接受长度，也要测量完整生成时间。动画里的候选数量只说明一次确认了什么，不直接报告吞吐提升。

试着解释

草稿第四个 token 恰好正确，但第三个被拒绝，能直接提交第四个吗？

展开解释

本课的单链验证不能这样做。第四个位置的验证使用了包含第三个候选的前缀；前缀改变后，必须重新验证后续条件。

术语速查

草稿
尚未确认的候选序列；可以来自小模型或其他提议方法。
验证与提交
验证检查候选是否符合目标规则；提交后才成为有效输出及相关状态。
回退
撤销未被接受的部分，保留有效前缀；不是把用户已看到的任意文字偷偷删掉。

对照算例，回看机制与取舍

Accepted Prefix：为什么只能连续接受候选

第四个候选是在包含第三个候选的前缀下提出的。第三个一旦被替换，第四个依赖的上下文就变了。这个例子的接受范围必须从开头连续延伸，到第一个分歧为止。 本例草稿是“我、想、喝、茶”，目标在第三个位置选择“吃”。即使验证第四列碰巧也给出“茶”，那是沿包含“喝”的输入前缀算出的结果，不能跳过分歧把它提交。

Root / Bonus Token：正式输出与有效 KV 的偏移

验证输入包含上一轮已输出的根 token。新补出的 token 尚未作为输入计算，因此输出列表和有效 KV 列表即使长度相同，成员也不一定一样。图中正式输出为“我、想、吃”，有效 KV 对应“根、我、想”；第二章继续核对 EAGLE 的实现边界。

Acceptance Rate 与开销：何时可能获得收益

提出草稿、验证、整理状态都有成本。接受得多可能摊薄逐步调用开销，接受得少则未必有收益。随机采样下的正确验证还涉及概率分布，不能照搬本例的逐 token 相等判断。
