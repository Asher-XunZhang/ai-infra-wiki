AllReduce、AllGather 与数据传输：结果何时可用？

从两张卡各自持有一组数开始，区分求和、拼接和接收完成。

可单步操作原理与实现分开来源与教学边界

先看：TP、PP、DP、EP、SP 与 PCP/DCP：多卡怎样分工？

形状相同的两组数，可能是同一结果的不同贡献，也可能是不同位置的片段。先切换求和与拼接，看元素如何形成结果；下方再检查通知与载荷为何不能混为一谈。

先想清楚：这一课解决什么问题？

切分计算后，某个结果往往依赖另一设备上的数据。通信既要搬运字节，也要保持结果的数学含义与依赖顺序；“已发出消息”还不足以让下一步安全读取。

01

为什么求和与拼接不能互换？

若两张卡分别计算同一输出的部分贡献，需要逐元素求和；若分别计算不同输出位置，才需要按布局拼接。AllReduce 让每个参与 rank 得到归约结果，AllGather 让每个参与 rank 收齐各 rank 的片段。Rank 是通信组内的参与者编号。

相同输入形状，可以表达不同的含义

  1. 两个局部贡献 [1,2] 与 [10,20]：AllReduce 求和得到 [11,22]。
  2. 两个有序片段 [1,2] 与 [10,20]：AllGather 收集为 [1,2,10,20]。

选择通信算子取决于计算的切分方式，不能按哪个操作名字更熟悉来选择。

依据：集合通信的结果约定 · NVIDIA NCCL

02

异步传输为什么还要确认完成？

异步提交允许程序在传输尚未结束时继续安排别的工作。因此接收了请求信息、获知目标地址，与载荷已经写好并可供消费者读取，是不同事件。接收方要满足相关传输、同步和身份匹配条件后，才能使用数据。

例如先收到“请求 R1 的 KV 将写入块 B”这条控制消息，只能知道归属和目标；块 B 仍可能在写入。具体由哪个事件确认完成、何时能回收，由实现协议决定。

03

通信操作和物理链路怎样区分？

AllReduce 等名称说明参与者最终应该得到什么结果；同机／跨机说明放置位置；实际链路和算法则决定怎么搬。相同的集合通信可以由不同互联和算法实现，不能从逻辑箭头推断固定网络路径。

集合通信还要求各参与者按匹配的调用约定协作。某个 rank 缺席或数据类型、数量不匹配，不能当作普通单机函数继续计算。

依据：集合通信的结果约定 · NVIDIA NCCL

试着解释

收到“数据将写入块 B”的通知，就能读取 B 吗？

展开解释

不能。还需确认载荷完成并满足消费者的同步与匹配条件；控制消息只说明归属和目标，不代表写入已经完成。

术语速查

张量
按形状组织的一组数；图中的两元素数组就是最小例子。
All-reduce / All-gather
前者将参与者的对应元素归约并让各方获得结果；后者收齐各方分片。
发送完成与接收可用
不同接口有不同完成含义；还应检查接收侧数据、身份和依赖条件。

对照算例，回看机制与取舍

AllReduce / AllGather：求和与拼接的区别

[1,2] 与 [10,20] 若是同一结果的局部贡献，求和得到 [11,22]；若是结果的不同片段，拼接得到 [1,2,10,20]。替换通信算子会改变结果，不只是改变速度。

控制面与数据面：通知到达和载荷可用

通知可以描述“数据属于哪个请求、将写入哪里”，真正的数据还要经过搬运。图中通知先到时，接收区仍为空；只有数据和匹配信息都齐备，才标记可使用。

GPU 互联：同机与跨机的数据路径

同机或跨机描述位置；点对点或集合通信描述参与方式；TCP、RDMA 等描述传输路径。不能仅凭图里写了 KV，就推断一定走 RDMA。实现课继续检查各自接口与回收条件。
