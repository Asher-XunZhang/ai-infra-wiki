第一步第二步第三步第四步固定源码

第二章比较两套引擎的职责，本页单独追踪 vLLM V1 普通文本、单 GPU、非投机的阅读路径。V1 指引擎架构，ModelRunner V2 指 Worker 内的执行实现。本课与第二章一样选择支持 V2 的普通自回归 GPU 路径；不支持特性、平台和显式配置的选择与回退，另查 VllmConfig.use_v2_model_runner。

VR1 有 6 个 prompt 位置，最多生成 2 个输出 ID；本例 block size=4，token budget 可选 2/4。这些大小与时长只为账本推演，不是设备配置建议或测量结果。

本例只展开普通单 KV 组与逐轮依赖，不模拟异构 KV 组、投机、跨批异步派发或所有图模式。教学轨道不代表 V2 的实测 stream 排程。

条件切换回到起点并暂停；展开与收起保留当前参数、时刻和播放状态。完整箭头说明载荷；只有明确的传递区间使用持续脉冲，本地引用与等待分别表示。

第一步：输入处理到 EngineCore 请求

先读 InputProcessor.process_inputs：请求输入、模型约束与采样配置如何被整理成 EngineCore 接口，再读 EngineCore.add_request/step。前端可见的请求与引擎内部的执行状态有不同职责。

建立请求身份和计数表：prompt 长度、已知 token ID、num_computed_tokens、采样上限。后续每轮都用同一身份更新它们。

第二步：Scheduler 决定本轮处理几个位置

V1 把等待处理的位置纳入 token 预算，不要求先把全局任务硬分成一个完整 Prefill 阶段和一个完整 Decode 阶段。SchedulerOutput 交付本轮的请求、token 数与 block 等信息。

本例没有命中且预算为 2 时，6 个 prompt 位置分三轮处理。前两轮还未到预测端点；最后一轮才为第一个输出提供本例的采样行。命中一个完整 block 后，仍有末尾两个位置需要处理。

第三步：KV manager 处理 block 命中与分配

读 get_computed_blocks 与 allocate_slots，分清内容匹配、持有引用、分配新块和填充位置。匹配了 4 个位置不等于整条请求都有 KV，分配了第二块也不表示其中四个位置都已经计算。

资源不足与抢占需要回到所选版本的 Scheduler/manager 规则。V1 的重新计算式处理不能按旧 V0 的 CPU swap 心智模型直接解释；重新入队、计数与缓存再匹配各自核对。

图中本请求已分配 block 与已计算记录分别计数。默认命中前 4 个位置，第一轮分配完第二块时，已计算仍是 4；本例设备处理完成并选出 y1 后，前端还要经过输出处理才能收到它。请求引用退役后，绿色边框消失，历史计算记录继续保留；这不表示其他缓存持有者也已经释放。

第四步：Runner 执行后，输出回到下一轮

沿 vllm/v1/worker/gpu/model_runner.py 中的 V2 GPUModelRunner.execute_model 与 sample_tokens，核对本轮输入位置、block 映射、执行状态和采样行，再回到 Scheduler 的结果处理。execute_model 返回并不表示 CPU 已拿到输出；异步复制和结果消费还需等待相应完成条件。

本例最终已知 8 个 ID：6 个 prompt 加 y1/y2。实际只计算过 7 个位置，因为 y2 刚被选出，没有作为下一轮输入写 K/V。块有空位、ID 已知和 KV 已计算是三个不同计数。

先预测，再解释

VR1 已知 8 个 ID，是否必然已经写入 8 个位置的 KV？

不是。末个刚采样的 ID 还没有进入下一轮输入；本例只计算 7 个位置。

V1 与 SGLang 的 token budget 同名，能否直接共用一张实现账本？

不能。对象、计数更新、准入和资源回收要按各自固定源码追踪。
