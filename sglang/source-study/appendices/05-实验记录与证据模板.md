## 1. 先写清楚要证明什么

每轮先用一个可证伪的问题定义目的，例如“该单实例配置能否完成一次原生非流式文本请求”。避免把目的写成“全面验证 SGLang”。

| 项目 | 应填写内容 |
| --- | --- |
| 实验问题 | 一个明确问题或待排除的解释 |
| 成功条件 | 哪些具体输出、状态和检查必须满足 |
| 失败条件 | 哪些错误、超时或不一致会否定本轮目标 |
| 操作边界 | 静态阅读、模拟测试、真实模型或授权部署中的哪一种 |
| 不覆盖内容 | 未进入的模型/拓扑/功能/故障路径 |

只有某个接口成功，就将结论限定到该接口和负载；只有静态分支阅读，就记录为源码结论。

## 3. 各类结论需要什么证据

| 结论类型 | 至少需要 | 不足以支持它的材料 |
| --- | --- | --- |
| 源码分支/字段事实 | 固定 commit、文件/符号、实际条件与调用者 | 只搜到名字，未读分支 |
| 单个测试通过 | 实际命令、环境、退出状态、输出、测试覆盖范围 | 仅存在测试文件或 CI 配置 |
| 一条请求成功 | 请求与完整响应、身份/配置、完成状态、相关日志 | 仅健康 200、部分文本或开端 SSE |
| 性能对比 | 同口径样本、完整负载条件、失败数、计时窗口、对照差异 | 不同条件的单个 tokens/s 数字 |
| 故障处理成立 | 具体故障触发、状态推进、资源与后续请求结果 | 仅异常被捕获、收到 ACK 或日志里写了 cleanup |
| 多节点/分离路径成立 | 真实拓扑、各侧状态、传输/计算与退役证据 | 单机/CPU 模拟或一个节点的日志 |

模板不预先要求执行所有类别；它要求结论不要超过实际证据类别。

## 4. 性能实验追加账本

记录 client/server 观测点，TTFT 的首事件定义，ITL 是 token 还是 chunk，TPOT 的公式与有效样本，吞吐的分子、分母和时间窗口。保留失败/取消/超时数量，不把它们静默从报告中删掉。

对照实验还要记录模型/权重、dtype、设备、并行、输入/输出分布、请求到达方式、预热、缓存命中与运行次数。若多个条件同时改变，应明确承认无法把差异归因到单一改动。

教学算例应直接标记为“算例”，不用看似精确的数值暗示实际测量。

## 6. 取消与资源复用验证追加字段

这些字段帮助后续实验分开“请求已结束”与“旧资源不再被访问”，并非本次已执行清单。静态主线见[02-06](../02-request-lifecycle/06-完成取消与资源释放.md)。

| 记录项 | 应证明或排除什么 |
| --- | --- |
| 取消时点与实际对象位置 | 是首次 waiting、grammar、chunked、running/last，还是回撤后的请求 |
| 目标 rid、前缀与实际匹配集合 | 取消范围与预期一致，不把 API 返回当作命中证据 |
| 前端 dispatched/abort_sent 和后端收到消息的记录 | 区分本地派发、消息处理与结束状态变更 |
| to_finish、finished_reason、相关结果处理时点 | 结束原因何时被消费，是否还有在途结果需要核算 |
| 请求行与 KV 索引、allocated/committed、缓存锁和 free_group | 分开行归还、缓存保留、索引释放与旧字段残留 |
| 实际设备 stream/event 或传输退役证据 | 单个 CPU 标志、API 200 或 mock 断言不足以证明旧写入停止 |
| 后续请求复用、输出与稳定性 | 对复用位置及运行结果做关联；一次成功不能代表所有组合 |
| 取消后的完整响应、异常与前端状态 | 正常输出与直接 AbortReq 回告可能不同，不用简单 delta 拼接掩盖差异 |
| 未覆盖条件 | 明确模型、Overlap、PP、PD、offload、会话等哪些仍未验证 |

模拟测试中使用假对象、mock allocator 或替代网络时，要逐项写出替代范围；不要把模拟环境没有出现的错误写成真实设备安全结论。

## 7. 调度轮次、准入与空闲验证追加字段

以下是后续实验的记录设计；本次仅据[03-01](../03-scheduling/01-NormalEventLoop与调度主循环.md)、[03-02](../03-scheduling/02-连续批处理与队列状态.md)、[03-03](../03-scheduling/03-排序策略与准入预算.md)与[03-04](../03-scheduling/04-ChunkedPrefill与长请求调度.md)静态梳理，没有创建新的调试 patch 或运行实例。

| 记录项 | 为什么需要 |
| --- | --- |
| 实际循环名、生效配置、rank 与功能组合 | 先确认进入普通循环，不能只凭关闭 overlap 推断 |
| 观察位置与时间戳 | 分开 ingest 后、选批后、结果后、last 更新后，避免混用字段 |
| 本轮收到的 rid、waiting 成员、running/last 成员、batch_to_run 与 forward mode | 区分收到、等待、接纳与实际运行；保存当时的值而非仅保存对象引用 |
| forward_ct、每 Req 输出数及客户端接收记录 | 区分循环、执行批、输出 token 和传输分块 |
| paused/gracefully_exit 与控制消息的处理位置 | 区分标志改变与真正跳过或离开循环 |
| is_fully_idle 的失败项、负载发布时点、sleeper 是否存在 | 分开无批次停滞、完整空闲与真正输入等待 |
| 阶段墙钟时间与设备 trace 的独立口径 | 避免把调度阶段耗时等同于 GPU kernel 耗时 |
| filter/merge 前后 Req 身份、keep_indices、请求行与采样/长度行 | 检查行对应关系；仅保留对象地址不足以保存历史状态 |
| chunk 的 prefix 长度、extend 范围、inflight_middle_chunks 与有效输出数 | 区分新增计算、暂时停留、中间结果处理与最终输入完成 |
| 回撤前后 retraction_count、输出历史、资源关系与重新准入记录 | 区分可恢复回撤、abort 与客户端重复提交，不假设沿用旧请求行 |
| 配置策略、本轮活动策略、排序前后 rid 和实际排序键 | 区分构造调整、本轮回退、缓存匹配元信息更新与真正重排 |
| priority 数字方向、缺省处理、抢占开关与差值门槛 | 不能仅凭数字大小或排序结果推断已经允许/完成抢占 |
| processed_tokens_counter、入队快照、forward mode 与 extend_num_tokens | 保留 HRRN aging 的计数来源，不把它直接等同于等待秒数或已完成计算量 |
| 锁前/锁后 available、evictable、锁引用与两份容量偏移 | 分开缓存保护导致的容量变化、估算扣账和后续物理分配 |
| 候选完整/未缓存/页对齐输入、剩余输出估算、new_token_ratio 与截断值 | 写清每个比较采用的长度，避免把预检查与接纳后扣账公式混用 |
| 请求行、microbatch、input/chunk 与其他池预算的单位 | 请求数量、token 容量、状态槽位和显存字节分别记录 |
| add_one_req 返回位置、返回值与 can_run_list 前后内容 | 明确本候选是否已加入；OTHER/NO_TOKEN 都不能单独替代该事实 |
| 首块/续块入口、append、range、prefix 与中间块计数的观察时点 | 分开范围选入、结果完成与缓存交接；返回 req/None 不能单独证明执行 |
| interval 余额、defer/arm 与本地/同步 extend 标志 | 消耗间隔不等于有 Decode 可执行，记录实际 ret 和成员 |
| mixed 预扣量、最终成员、decoding_reqs 与各行 prefix/extend/seq 长度 | 检查预算与实际混入的区别，保持三种长度对应 |
| PP 动态采样的 rank、合成输入、同步范围、样本/拟合系数和失败位置 | 局部启动 profile 与完整在线 PP 延迟分开，不把回退扩大到所有异常 |
| 动态 history_len、基值、smooth factor、上下文/输入上界与实际截断范围 | 保存预测前后及 Adder 的结果，避免只记录最终 chunk size 就推断根因 |

读取测试文件时另记 Mock 的对象、时间源和断言范围。例如 on_idle 负载单测的固定时间与 100 次调用，只是对发布门限的模拟条件；不能作为真实 CPU/网络性能数据。

| finished/retracted 后的跳过分支、额外槽位与其他异步访问 | 有结果跳过不证明所有 KV 或外部传输已经退役 |

## 63. 证据包如何组织

按一次实验建立独立目录，保存原始命令/请求、服务日志、响应或 SSE、环境与配置、结论记录。日志正文用 `.log`，SSE 可用 `.sse`，结构化响应用 `.json`；不要只交一份脱离原文的总结。

节选日志应注明来自哪份完整日志、时间范围或行区间。图片只在它能解释真实 trace 或结果时加入，按 Wiki 规则放到顶层 `images/<topic>/`，在记录中保留条件和图意解读。

重复执行时用新记录保留每轮条件。失败、未执行和受阻都是合法结果；缺失文件不是成功或失败的证据。
